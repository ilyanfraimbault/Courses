::exo-question{label="1." bonne="c" cours="thm-fn-ports"}
Which port numbers are considered well-known, the standard numbers reserved for common services such as HTTP or SSH?

#a
1024 to 49151

#b
49152 to 65535

#c
0 to 1023

#d
1 to 1000

#indice
Pense aux ports de SSH (22), de HTTP (80) et de HTTPS (443) : dans quelle plage tombent-ils tous ? Reste à en connaître la borne exacte.

#solution
Les ports **bien connus** (**well-known ports**) vont de **0 à 1023** : 1 024 numéros, attribués par l'IANA aux services standard — 22 pour SSH, 53 pour DNS, 80 pour HTTP, 443 pour HTTPS. C'est la réponse « 1024 » de la room.

**a** est la plage des ports **enregistrés** (*registered ports*), attribués à des applications sur demande ; **b** est la plage **dynamique**, réservée aux ports éphémères qu'un client prend comme port source ; **d** confond avec le scan par défaut de Nmap, qui ne vise pas les ports 1 à 1000 mais les 1 000 ports les plus courants, d'après ses statistiques.

Réponse : $\boxed{\text{c}}$
::

::exo-question{label="2." bonne="a" cours="thm-fn-ports"}
What does the `-p-` switch tell Nmap to scan?

#a
Every port, from 1 to 65,535

#b
The 1,000 most common ports, as with no option

#c
Only the well-known ports, below 1024

#d
Only the ports found open by the previous scan

#indice
Dans `-p 1000-1500`, le tiret sépare les deux bornes d'une plage. Que se passe-t-il si on les omet toutes les deux ?

#solution
`-p` choisit les ports : `-p 80` (un seul), `-p 1000-1500` (une plage), `-p 22,80,443` (une liste). Une borne omise vaut **1** au début et **65535** à la fin : `-p-` scanne donc **tous les ports, de 1 à 65 535** — exhaustif, mais lent. Le port 0 ne se scanne que si on le nomme.

**b** est le comportement sans aucune option `-p` ; **c** se demanderait avec `-p 1-1023` ; **d** prête à `-p-` une mémoire qu'il n'a pas : Nmap ne relit pas les résultats d'un scan précédent pour choisir ses ports.

Réponse : $\boxed{\text{a}}$
::

::exo-question{label="3." bonne="d" cours="thm-fn-detection"}
Which switches detect the target's operating system and the versions of its services?

#a
`-sO` for the operating system, `-sV` for the service versions

#b
`-O` for the operating system, `-V` for the service versions

#c
`-sV` for the operating system, `-O` for the service versions

#d
`-O` for the operating system, `-sV` for the service versions

#indice
Méfie-toi de la casse et du `s` : chez Nmap, une même lettre peut désigner deux options sans rapport.

#solution
`-O` (la lettre O majuscule) active la **détection du système d'exploitation** (**OS detection**) : Nmap compare les réactions de la pile TCP/IP de la cible à sa base d'empreintes. Il demande root, et il est bien plus fiable avec au moins un port ouvert et un port fermé. `-sV` active la **détection des versions** (**version detection**) : des sondes applicatives qui donnent le logiciel et sa version exacte, de quoi chercher les CVE. `-A` active les deux à la fois, avec les scripts par défaut et `--traceroute`.

**a** — `-sO` est le scan des **protocoles IP** (TCP, ICMP, IGMP…) que la cible prend en charge, pas la détection du système ; **b** — `-V` affiche la version de **Nmap** lui-même, puis s'arrête ; **c** intervertit les deux rôles.

Réponse : $\boxed{\text{d}}$
::

::exo-question{label="4." bonne="b" cours="thm-fn-sorties"}
Which switch is paired with the wrong description?

#a
`-vv`: verbosity level two

#b
`-oA`: results saved in the grepable format only

#c
`-T5`: the fastest timing template

#d
`-A`: OS and version detection, default scripts and traceroute

#indice
Trois descriptions sont exactes. Rappelle-toi l'option que la room conseille pour ne lancer un scan qu'une seule fois, puis le citer dans un rapport.

#solution
La seule association fausse est **b** : `-oA` (*output to all formats*) enregistre les résultats dans les **trois** formats majeurs d'un coup — `nom.nmap` (normal), `nom.xml` (XML) et `nom.gnmap` (grepable). Le format grepable seul s'obtient avec `-oG`, le normal seul avec `-oN`, le XML seul avec `-oX`. La room recommande `-oA` : on ne scanne qu'une fois, et on garde de quoi citer le scan dans le rapport.

Les trois autres sont exactes : **a** — `-v` augmente la verbosité, `-vv` la porte au niveau deux ; **c** — `-T5`, *insane*, est le plus rapide des six gabarits, de `-T0` à `-T5`, et le plus bruyant ; **d** — `-A`, le mode agressif, active `-O`, `-sV`, les scripts par défaut (`-sC`) et `--traceroute`, mais ni le timing ni la verbosité.

Réponse : $\boxed{\text{b}}$
::
:::

:::exercice{titre="Tasks 4-6 — TCP Connect and SYN Scans" theme="La réponse d'un port fermé selon la RFC, puis les options du scan connect et du scan SYN"}

::exo-question{label="1." bonne="c" cours="thm-fn-tcp"}
Which RFC originally specified how TCP behaves, and what does a closed port send back to a SYN?

#a
RFC 793, and the closed port answers with a SYN/ACK

#b
RFC 791, and the closed port answers with a RST

#c
RFC 793, and the closed port answers with a RST

#d
RFC 768, and the closed port does not answer at all

#indice
Les RFC fondatrices d'Internet ont des numéros voisins : retiens celle de TCP, sans la confondre avec celle d'IP. Quant au port fermé, rien n'y écoute, mais la machine est bien là pour répondre.

#solution
**TCP** a été spécifié par la **RFC 793** (1981) ; la **RFC 9293** l'a remplacée en 2022 en reprenant ses règles — selon sa version, la room attend l'une ou l'autre. Une connexion s'ouvre par la poignée de main en trois temps : SYN → SYN/ACK → ACK. Un SYN qui arrive sur un port **fermé** reçoit un segment **RST** (*reset*) : la machine répond, mais refuse la connexion, et Nmap classe le port **closed**.

**a** — le SYN/ACK est la réponse d'un port **ouvert**, le deuxième temps de la poignée de main ; **b** — la RFC 791 décrit **IP** ; **d** — la RFC 768 décrit **UDP**, et un port TCP qui ne répond rien est classé **filtered** : un pare-feu a jeté la sonde.

Réponse : $\boxed{\text{c}}$
::

::exo-question{label="2." bonne="a" cours="thm-fn-connect-syn"}
Which switches launch a TCP connect scan and a TCP SYN scan?

#a
`-sT` for the connect scan, `-sS` for the SYN scan

#b
`-sS` for the connect scan, `-sT` for the SYN scan

#c
`-sC` for the connect scan, `-sS` for the SYN scan

#d
`-sT` for the connect scan, `-PS` for the SYN scan

#indice
Le *T* du scan connect vient de **TCP** : c'est le scan TCP le plus simple, celui qui ouvre une vraie connexion. Reste à trouver la bonne option pour le SYN.

#solution
**`-sT`** lance le **scan connect** (*TCP connect scan*) : Nmap demande au système d'ouvrir une vraie connexion, poignée de main **complète**, puis la coupe. Aucun privilège n'est requis : c'est le défaut sans root. **`-sS`** lance le **scan SYN**, dit **half-open** ou **stealth** : Nmap envoie un SYN, lit la réponse, et répond RST au SYN/ACK au lieu de finir la poignée de main. Il forge ses propres paquets, donc demande **sudo** : c'est le défaut en root, et il est impossible sans ces droits.

**b** intervertit les deux ; **c** — `-sC` lance les **scripts par défaut** de NSE, ce n'est pas un type de scan ; **d** — `-PS` est le **ping TCP SYN** de la découverte d'hôtes, qui cherche si la machine répond, pas l'état de chacun de ses ports.

Réponse : $\boxed{\text{a}}$
::
:::

:::exercice{titre="Tasks 7-9 — UDP, NULL, FIN, Xmas and ICMP Scans" theme="Le silence d'un port UDP, les drapeaux des scans NULL, FIN et Xmas, la réponse de Windows, le ping sweep d'un réseau"}

::exo-question{label="1." bonne="b" cours="thm-fn-udp"}
During a UDP scan, a port gives no response at all, even after Nmap sends the probe a second time. How is the port marked?

#a
filtered

#b
open|filtered

#c
closed

#d
open

#indice
Un service UDP ouvert ne répond souvent rien à un datagramme vide. Et un pare-feu qui jette le paquet, que renvoie-t-il ?

#solution
Un port UDP **ouvert** ne répond souvent **rien** à la sonde ; un pare-feu qui jette le paquet non plus. Faute de réponse — Nmap renvoie la sonde une seconde fois pour s'en assurer —, il ne peut pas trancher : le port est marqué **open|filtered**. `-sV`, qui envoie de vraies requêtes du service, aide ensuite à décider.

**a** est l'état d'un port **TCP** resté muet pendant un scan SYN ou connect ; **c** demande un message **ICMP port unreachable** (type 3, code 3), que la cible renvoie par convention quand un port UDP est fermé ; **d** demande une **réponse UDP** venue du port, ce qui est rare.

Réponse : $\boxed{\text{b}}$
::

::exo-question{label="2." bonne="d" cours="thm-fn-furtifs"}
Which Nmap scan sets the URG flag in its probes?

#a
The NULL scan, `-sN`

#b
The FIN scan, `-sF`

#c
The SYN scan, `-sS`

#d
The Xmas scan, `-sX`

#indice
Un seul de ces scans lève plusieurs drapeaux à la fois ; les autres en lèvent un seul, ou aucun.

#solution
Le scan **Xmas** (`-sX`) lève **FIN, PSH et URG** : dans une capture Wireshark, le paquet « s'allume comme un sapin de Noël », d'où son nom.

**a** — le scan **NULL** n'en lève **aucun** : l'en-tête des drapeaux vaut 0 ; **b** — le scan **FIN** ne lève que **FIN** ; **c** — le scan **SYN** ne lève que **SYN**, comme le premier temps d'une poignée de main.

Ces trois scans sans SYN servent surtout à l'**évasion de pare-feu** : beaucoup de pare-feu jettent les SYN entrants vers les ports bloqués, mais laissent passer les autres paquets. Les IDS modernes les repèrent pourtant.

Réponse : $\boxed{\text{d}}$
::

::exo-question{label="3." bonne="a" cours="thm-fn-furtifs"}
An Xmas scan reports every port of a host as closed, while a SYN scan of the same host finds ports 80 and 443 open. What is the most likely explanation?

#a
The host runs Microsoft Windows, which answers these probes with a RST on every port

#b
A firewall in front of the host silently drops all of the Xmas probes

#c
The host runs Linux, which answers these probes with a RST on every port

#d
The Xmas scan was launched without root privileges, so its results are wrong

#indice
La RFC qui définit TCP veut qu'un port **ouvert** ignore ces paquets sans SYN. Tous les systèmes la suivent-ils ?

#solution
D'après la RFC de TCP, un paquet sans SYN, RST ni ACK reçoit un **RST** s'il arrive sur un port fermé, et **rien** s'il arrive sur un port ouvert : RST → closed, silence → open|filtered. Mais **Microsoft Windows** — comme beaucoup d'équipements Cisco — répond RST à tout paquet TCP malformé, que le port soit ouvert ou non : tous les ports paraissent fermés, alors que le scan SYN a bien vu les ports 80 et 443 répondre SYN/ACK. Les scans NULL, FIN et Xmas sont inutiles contre Windows.

**b** — des sondes jetées sans réponse donneraient **open|filtered**, pas closed ; **c** — Linux suit la RFC : ses ports ouverts 80 et 443 se seraient tus, et seraient sortis open|filtered ; **d** — sans root, Nmap refuse de lancer un scan Xmas et s'arrête : il ne rend aucun résultat.

Réponse : $\boxed{\text{a}}$
::

::exo-question{label="4." bonne="c" cours="thm-fn-sweep"}
How would you perform a ping sweep of the 172.16.x.x network, whose netmask is 255.255.0.0?

#a
`nmap -Pn 172.16.0.0/16`

#b
`nmap -sn 172.16.0.0/24`

#c
`nmap -sn 172.16.0.0/16`

#d
`nmap -sN 172.16.0.0/16`

#indice
Deux choix à faire : l'option qui s'arrête après la découverte d'hôtes, et le préfixe CIDR qui correspond à un masque dont les deux premiers octets valent 255.

#solution
`-sn` (*no port scan*) dit à Nmap de **ne scanner aucun port** : il se contente de découvrir les hôtes actifs. En root, ses sondes sont un ICMP echo, un SYN vers le port 443, un ACK vers le port 80 et un ICMP timestamp — remplacés par des requêtes ARP sur le réseau local ; sans root, de simples connexions vers les ports 80 et 443. Le masque **255.255.0.0** compte 16 bits à 1 : en notation CIDR, `172.16.0.0/16`, soit les adresses de `172.16.0.0` à `172.16.255.255`.

**a** fait l'inverse : `-Pn` **saute** la découverte, suppose tous les hôtes actifs et scanne leurs ports ; **b** — `/24` correspond au masque 255.255.255.0, et ne couvrirait que `172.16.0.x` ; **d** — `-sN`, avec un N majuscule, est le scan **NULL** des ports TCP, pas un ping sweep.

Réponse : $\boxed{\text{c}}$
::
:::

:::exercice{titre="Tasks 10-12 — NSE Scripts" theme="Le langage des scripts, leurs catégories, la recherche d'un script et ses dépendances"}

::exo-question{label="1." bonne="b" cours="thm-fn-nse"}
In which language are NSE scripts written, and where does Kali store them?

#a
In Python, in `/usr/share/nmap/scripts/`

#b
In Lua, in `/usr/share/nmap/scripts/`

#c
In Ruby, in `/usr/share/metasploit-framework/modules/`

#d
In Lua, in `/etc/nmap/scripts/`

#indice
Ce n'est pas le langage des modules de Metasploit : c'est un langage léger, conçu pour être embarqué dans un autre programme.

#solution
Les scripts du **Nmap Scripting Engine** (NSE) sont écrits en **Lua**. Sur Kali, ils sont rangés dans **`/usr/share/nmap/scripts/`**, un fichier `.nse` par script, avec leur index `script.db` ; plus de 600 sont livrés avec Nmap.

**a** — Python sert à bien des outils de sécurité, mais pas aux scripts NSE ; **c** — Ruby et ce dossier sont ceux des modules de **Metasploit**, la confusion classique ; **d** — le langage est le bon, mais `/etc` garde des fichiers de configuration : les scripts vivent avec les autres données de Nmap, sous `/usr/share/nmap/`.

Réponse : $\boxed{\text{b}}$
::

::exo-question{label="2." bonne="d" cours="thm-fn-nse"}
Which category of NSE scripts would be a very bad idea to run against a production environment?

#a
safe

#b
discovery

#c
version

#d
intrusive

#indice
La documentation de Nmap y range les scripts trop risqués pour être dits sans danger : ils peuvent planter la cible ou épuiser ses ressources.

#solution
La catégorie **intrusive** regroupe les scripts que Nmap ne peut pas classer **safe** : le risque est trop grand qu'ils **plantent la cible**, consomment beaucoup de ses ressources (bande passante, processeur) ou passent pour une attaque auprès de ses administrateurs. Sur un système en production, c'est la catégorie à proscrire.

**a** est justement l'inverse : des scripts conçus pour ne pas planter les services ni saturer le réseau ; **b** regroupe les scripts qui en apprennent davantage sur le réseau — registres publics, annuaires, SNMP ; **c** complète la détection des versions, et ne tourne qu'avec `-sV`.

Réponse : $\boxed{\text{d}}$
::

::exo-question{label="3." bonne="c" cours="thm-fn-recherche"}
You search Nmap's scripts folder for SMB scripts. Which one determines the operating system of an SMB server?

#a
`smb-enum-shares.nse`

#b
`smb-vuln-ms17-010.nse`

#c
`smb-os-discovery.nse`

#d
`smb-enum-users.nse`

#indice
Pour lister les candidats, la room cherche `smb` dans les noms de fichiers du dossier des scripts, ou dans son index `script.db`. Lis ensuite les noms : ils disent ce que fait chaque script.

#solution
`smb-os-discovery.nse` cherche, par le protocole SMB (ports 445 ou 139), le **système d'exploitation** du serveur, son nom, son domaine ou groupe de travail et son heure. Pour le trouver, la room montre deux méthodes : `ls -l /usr/share/nmap/scripts/*smb*`, ou `grep smb /usr/share/nmap/scripts/script.db` — un fichier texte, malgré son extension, qui donne le nom et les catégories de chaque script.

**a** liste les **partages** SMB ; **b** vérifie la faille **MS17-010**, celle d'EternalBlue et de WannaCry ; **d** liste les **utilisateurs**.

Réponse : $\boxed{\text{c}}$
::

::exo-question{label="4." bonne="a" cours="thm-fn-recherche"}
An NSE script for SMB lists `smb-brute` in its `dependencies` field. What does that mean?

#a
When both scripts are selected, `smb-brute` runs first, so its results can be reused

#b
Selecting the script automatically launches `smb-brute` as well

#c
The script refuses to run unless `smb-brute` is also selected

#d
The script loads the code of `smb-brute` as a shared library

#indice
Pense à ce qu'un script SMB gagnerait à savoir avant de s'exécuter, si un autre a déjà trouvé des comptes valides. Reste à savoir si ce champ lance quoi que ce soit.

#solution
Le champ **`dependencies`** d'un script NSE liste les scripts qui doivent tourner **avant** lui, **s'ils sont eux aussi sélectionnés**. La plupart des scripts `smb-*` déclarent `smb-brute`, à commencer par `smb-os-discovery` — l'exemple même de la documentation de Nmap : les comptes que `smb-brute` trouverait permettraient aux autres scripts d'obtenir davantage d'informations.

**b** et **c** sont faux : une dépendance ne fait pas lancer le script cité — il faut le sélectionner, avec `--script` par exemple —, et elle n'empêche rien non plus ; elle impose seulement un **ordre** entre les scripts choisis. `smb-os-discovery` fait d'ailleurs partie des scripts par défaut, lancés par `-sC` sans `smb-brute`. **d** confond avec les **bibliothèques** NSE, rangées dans le dossier `nselib`, qu'un script charge avec `require`.

Réponse : $\boxed{\text{a}}$
::

:::exercice{titre="Task 13 — Firewall Evasion" theme="Les options qui retouchent les paquets pour passer un pare-feu ou un IDS"}

::exo-question{label="1." bonne="b" cours="thm-fn-evasion"}
Which Nmap switch appends an arbitrary length of random data to the end of packets?

#a
`--mtu`

#b
`--data-length`

#c
`-f`

#d
`--badsum`

#indice
Par défaut, Nmap envoie des paquets minimalistes, réduits à leurs en-têtes : 40 octets pour un paquet TCP. Laquelle de ces options les allonge ?

#solution
`--data-length <nombre>` ajoute ce nombre d'**octets aléatoires** à la plupart des paquets envoyés. D'ordinaire, Nmap n'envoie que des en-têtes — 40 octets pour un paquet TCP, 28 pour un ICMP echo —, une signature qu'un IDS peut repérer : allonger les paquets rend le scan un peu moins voyant, au prix d'un peu de lenteur.

**a** — `--mtu` fixe la taille des **fragments**, un multiple de 8 ; **c** — `-f` **fragmente** les paquets en morceaux de 8 octets au plus après l'en-tête IP (16 avec `-ff`) ; **d** — `--badsum` envoie une **somme de contrôle invalide** : une vraie pile TCP/IP jette ces paquets, donc une réponse trahit un pare-feu ou un IDS qui ne vérifie pas les sommes.

Réponse : $\boxed{\text{b}}$
::
:::

::extrait-cours{id="thm-fn-ports" titre="Les ports et l'option -p" source="/cours/a1/ethical-hacking/nmap/cours#_2-cibles-ports-et-sorties"}
Un **port** dirige le trafic vers la bonne application d'une machine. Il y en a **65 535** par protocole, TCP comme UDP. Les ports **bien connus** (*well-known ports*) vont de **0 à 1023** : 1 024 numéros attribués par l'IANA aux services standard — 22 (SSH), 53 (DNS), 80 (HTTP), 443 (HTTPS). Viennent ensuite les ports **enregistrés**, de 1024 à 49151, puis la plage **dynamique**, de 49152 à 65535, celle des ports éphémères.

Sans option, Nmap scanne les **1 000 ports les plus courants**. `-p 80` : un port ; `-p 1000-1500` : une plage ; `-p 22,80,443` : une liste ; **`-p-` : tous les ports, de 1 à 65 535** — une borne omise vaut 1 au début, 65 535 à la fin ; `-F` : les 100 ports les plus courants.
::

::extrait-cours{id="thm-fn-detection" titre="Système, versions et mode agressif" source="/cours/a1/ethical-hacking/nmap/cours#_4-versions-système-et-timing"}
**`-O`** : détection du **système d'exploitation** (*OS detection*), par l'empreinte de la pile TCP/IP de la cible ; root, et plus fiable avec au moins un port ouvert et un port fermé.

**`-sV`** : détection des **versions** des services, par des sondes applicatives — le logiciel et sa version exacte, la base de la recherche de CVE.

**`-A`**, le mode agressif : `-O` + `-sV` + scripts par défaut (`-sC`) + `--traceroute`. Bruyant, il ne règle ni le timing ni la verbosité.

Pièges de casse : `-sO` est le scan des protocoles IP pris en charge par la cible ; `-V` affiche la version de Nmap et s'arrête.
::

::extrait-cours{id="thm-fn-sorties" titre="Sorties, verbosité et timing" source="/cours/a1/ethical-hacking/nmap/cours#_2-cibles-ports-et-sorties"}
| Option | Effet |
| --- | --- |
| `-oN fichier` | sortie **normale**, celle de l'écran |
| `-oX fichier` | sortie **XML**, pour les outils |
| `-oG fichier` | sortie **grepable** : une ligne par hôte |
| `-oA nom` | les **trois** d'un coup : `nom.nmap`, `nom.xml`, `nom.gnmap` |
| `-v`, `-vv` | verbosité de niveau un, puis deux |

La room conseille `-oA` : on ne lance le scan qu'une fois, et l'on garde de quoi le citer dans le rapport.

Timing : six gabarits, de `-T0` (*paranoid*) à **`-T5` (*insane*, le plus rapide et le plus bruyant)** ; `-T3` (*normal*) est le défaut. `-A` active `-O`, `-sV`, `-sC` et `--traceroute`, pas le timing.
::

::extrait-cours{id="thm-fn-tcp" titre="La poignée de main et la réponse d'un port fermé" source="/cours/a1/ethical-hacking/scanning/cours#_3-les-états-de-ports"}
**TCP** a été spécifié par la **RFC 793** (1981), remplacée en 2022 par la **RFC 9293**, qui en garde les règles. Ne pas confondre : IP, RFC 791 ; ICMP, RFC 792 ; UDP, RFC 768.

Une connexion s'ouvre par la **poignée de main en trois temps** (*three-way handshake*) : **SYN** → **SYN/ACK** → **ACK**. À un SYN, un port répond :

- **SYN/ACK** : un service écoute, le port est **open** ;
- **RST** (*reset*) : rien n'écoute, le port est **closed** — mais la machine est bien là ;
- rien, ou un ICMP unreachable : un pare-feu filtre, le port est **filtered**.

Un pare-feu peut aussi être réglé pour répondre RST à la place de la machine, ce qui fausse le scan.
::

::extrait-cours{id="thm-fn-connect-syn" titre="Le scan connect et le scan SYN" source="/cours/a1/ethical-hacking/nmap/cours#_3-les-types-de-scans"}
**`-sT`, le scan connect** (*TCP connect scan*) : le système ouvre une vraie connexion, poignée de main **complète**, aussitôt coupée. Aucun privilège : c'est le défaut sans root. Plus lent, et journalisé par l'application.

**`-sS`, le scan SYN**, dit **half-open** ou **stealth** : SYN → SYN/ACK, puis **RST** au lieu de l'ACK ; la connexion n'est jamais établie. Plus rapide, souvent ignoré des journaux de l'application, il passe d'anciens IDS — mais il peut faire tomber un service fragile. Il forge des paquets bruts (*raw packets*) : **sudo obligatoire**, et c'est le défaut en root.

À ne pas confondre : `-sC` (les scripts par défaut), `-PS` (le ping TCP SYN de la découverte d'hôtes).
::

::extrait-cours{id="thm-fn-udp" titre="Le scan UDP" source="/cours/a1/ethical-hacking/scanning/cours#_3-les-états-de-ports"}
`-sU` envoie un datagramme à chaque port :

- une **réponse UDP** venue du port → **open**, ce qui est rare ;
- un **ICMP port unreachable** (type 3, code 3), que la cible renvoie par convention pour un port fermé → **closed** ;
- **aucune réponse**, même après un second envoi → **open|filtered** : un port UDP ouvert se tait souvent, comme un port filtré. `-sV` aide à trancher.

Le scan UDP est lent : `--top-ports 20` le limite aux ports les plus courants.
::

::extrait-cours{id="thm-fn-furtifs" titre="Les scans NULL, FIN et Xmas" source="/cours/a1/ethical-hacking/nmap/cours#_3-les-types-de-scans"}
Trois scans sans drapeau SYN : **NULL** (`-sN`, aucun drapeau), **FIN** (`-sF`, le seul FIN) et **Xmas** (`-sX`, **FIN, PSH et URG** — le paquet « clignote comme un sapin de Noël » dans Wireshark).

D'après la **RFC 793**, un port **fermé** leur répond **RST**, un port **ouvert** ne répond **rien** : RST → closed, silence → **open|filtered**, ICMP unreachable → filtered. Ils ne repèrent donc avec certitude que les ports fermés.

Leur intérêt : l'**évasion de pare-feu** — beaucoup de pare-feu jettent les SYN entrants vers les ports bloqués, pas les autres paquets ; les IDS modernes les détectent pourtant. **Microsoft Windows** et beaucoup d'équipements **Cisco** répondent RST à tout paquet malformé, port ouvert ou non : contre eux, tous les ports paraissent fermés.
::

::extrait-cours{id="thm-fn-sweep" titre="Le ping sweep" source="/cours/a1/ethical-hacking/scanning/cours#_2-la-découverte-dhôtes"}
Un **ping sweep** cherche les hôtes actifs d'un réseau avant de scanner leurs ports. **`-sn`** : découverte seule, **aucun scan de ports**. En root, Nmap envoie un ICMP echo, un SYN vers 443, un ACK vers 80 et un ICMP timestamp — des requêtes ARP sur le réseau local ; sans root, des connexions vers 80 et 443.

La plage s'écrit avec un tiret (`192.168.0.1-254`) ou en CIDR : masque 255.255.255.0 = `/24`, masque 255.255.0.0 = `/16`. D'où `nmap -sn 172.16.0.0/16` pour tout le réseau `172.16.x.x`.

À ne pas confondre : **`-Pn`** saute au contraire la découverte et scanne les ports de toutes les cibles ; **`-sN`** est le scan NULL.
::

::extrait-cours{id="thm-fn-nse" titre="Le moteur de scripts NSE" source="/cours/a1/ethical-hacking/nmap/cours#_5-le-moteur-de-scripts-nse"}
Le **Nmap Scripting Engine** exécute des scripts écrits en **Lua**, rangés sur Kali dans `/usr/share/nmap/scripts/` : reconnaissance, recherche de vulnérabilités, voire exploitation. Les catégories de la room :

| Catégorie | Les scripts qui… |
| --- | --- |
| **safe** | n'affectent pas la cible |
| **intrusive** | risquent de l'affecter — planter un service, épuiser ses ressources : jamais en production |
| **vuln** | cherchent des vulnérabilités |
| **exploit** | tentent d'exploiter une vulnérabilité |
| **auth** | traitent de l'authentification, ou tentent de la contourner |
| **brute** | devinent des identifiants par force brute |
| **discovery** | interrogent les services pour en apprendre plus sur le réseau |

La documentation en compte quatorze, dont **default** (lancée par `-sC`) et **version** (qui ne tourne qu'avec `-sV`). Lancer : `--script=vuln`, `--script=nom1,nom2` ; passer des paramètres : `--script-args` ; lire l'aide d'un script : `--script-help nom`.
::

::extrait-cours{id="thm-fn-recherche" titre="Chercher un script et lire ses dépendances" source="/cours/a1/ethical-hacking/nmap/cours#_5-le-moteur-de-scripts-nse"}
Deux façons de chercher un script en local :

- `ls -l /usr/share/nmap/scripts/*smb*` : les fichiers dont le nom contient `smb` ;
- `grep smb /usr/share/nmap/scripts/script.db` : `script.db` n'est pas une base de données mais un **fichier texte**, qui donne le nom et les catégories de chaque script.

Les noms suivent le schéma protocole-action : `smb-os-discovery` (système, nom, domaine d'un serveur SMB), `smb-enum-shares` (partages), `smb-enum-users` (utilisateurs), `smb-vuln-ms17-010` (EternalBlue). Après avoir ajouté un script, `nmap --script-updatedb` met l'index à jour.

Le champ **`dependencies`** d'un script liste ceux qui doivent tourner **avant** lui **s'ils sont aussi sélectionnés** — `smb-brute` pour `smb-os-discovery`, qui peut réutiliser ses résultats. Il ne lance rien de lui-même et n'empêche rien : il fixe un ordre.
::

::extrait-cours{id="thm-fn-evasion" titre="Passer un pare-feu" source="/cours/a1/ethical-hacking/nmap/cours#_7-les-techniques-dévasion"}
Le pare-feu de Windows bloque l'**ICMP** par défaut : la cible paraît éteinte. **`-Pn`** saute la découverte et traite tout hôte comme actif — au prix d'un scan bien plus long si l'hôte est vraiment éteint.

| Option | Effet |
| --- | --- |
| `-f` | fragmente les paquets : 8 octets au plus après l'en-tête IP, 16 avec `-ff` |
| `--mtu <taille>` | fixe la taille des fragments, un **multiple de 8** |
| `--scan-delay <durée>` | attend entre deux sondes : réseau instable, IDS qui se déclenche sur la cadence |
| `--badsum` | somme de contrôle invalide : une vraie pile jette le paquet, une réponse trahit un pare-feu ou un IDS |
| `--data-length <n>` | ajoute n octets aléatoires aux paquets, d'ordinaire réduits à leurs en-têtes |

Ces options réduisent le bruit, elles ne rendent pas invisible.
::
