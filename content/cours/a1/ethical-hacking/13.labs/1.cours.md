Les cinq labs **Vulnhub** du module ne demandent pas de connaître chaque machine par cœur : ils rejouent, sur des cibles différentes, les mêmes gestes que le reste du cours — reconnaissance, scan, exploitation, élévation de privilèges. Cette fiche ne retient que ce qui peut tomber au contrôle : la **démarche** commune, les **techniques** que chaque lab met en avant, et le **rapport de pentest** attendu pour les labs 4 et 5. Les détails propres à une machine — une adresse IP, un flag, le contenu d'un fichier — sont écartés : ils ne se révisent pas, ils se trouvent le jour du TP.

## 1. La démarche des cinq labs

Chaque lab suit les **cinq phases** du pentest vues au premier cours, appliquées à une machine isolée :

1. **Reconnaissance / scan** — `nmap -sC -sV -p- <ip>` pour trouver **tous** les ports, même non standard, les services et leurs versions ; `netdiscover -r <réseau>` ou `nmap -sn` pour repérer la cible sur le réseau du lab.
2. **Énumération** — pour chaque service ouvert, l'outil qui convient : `gobuster`/`feroxbuster` sur le web, `enum4linux-ng` sur SMB, un client anonyme sur FTP, `whatweb` pour les technologies.
3. **Exploitation** — la faille qui donne un premier accès : une version vulnérable (`searchsploit`), une injection, un identifiant deviné.
4. **Élévation de privilèges** — de l'utilisateur obtenu à **root** (voir la dernière section).
5. **Post-exploitation / rapport** — ce que l'on a prouvé, et comment le corriger.

Le préalable de tout : l'**autorisation**. Un lab définit un **périmètre** (*scope*) — ici, la seule machine fournie. On ne touche à rien d'autre, et chaque paquet envoyé laisse une trace.

Pour les labs **4 et 5**, le livrable est un **rapport** rempli dans `Pentest_Report_Template.docx` : on s'y met dans le rôle du pentester, l'enseignant étant le client.

## 2. Énumérer tous les ports

Le réflexe de **RickdiculouslyEasy 1**, mais valable partout : un scan par défaut ne couvre que les 1 000 ports courants. Cette machine cache des services sur des **ports non standard** — un serveur web haut placé, un **SSH** déplacé loin du port 22. Seul `nmap -p-` les voit.

Ce que la phase d'énumération y rapporte, et qu'il faut savoir reproduire :

- **FTP anonyme** — `ftp <ip>`, identifiant `anonymous`, mot de passe vide : beaucoup de fichiers laissés là s'y récupèrent directement.
- **`robots.txt`** — ce fichier dit aux moteurs quels chemins ne pas indexer ; pour un attaquant, c'est une **liste de répertoires sensibles** toute faite (`/cgi-bin/`, un dossier de mots de passe…).
- **Le code source d'une page** et ses commentaires HTML — un flag, un identifiant, un indice y traînent souvent.

La leçon : **un scan complet et une énumération patiente** trouvent l'essentiel avant toute exploitation.

## 3. L'injection de commande

Toujours sur RickdiculouslyEasy : un script **CGI** prend une entrée (une adresse à « traceroute ») et la passe telle quelle au shell du système. En ajoutant un **métacaractère de shell**, on fait exécuter **sa propre** commande à côté de celle prévue :

```
8.8.8.8; id
8.8.8.8 | cat /etc/passwd
8.8.8.8 && whoami
```

`;`, `|`, `&&`, les accents graves ou `$(...)` enchaînent ou substituent une commande. C'est une **command injection** : elle apparaît partout où une application construit une commande système à partir d'une entrée non filtrée. La parade côté défense : ne jamais concaténer une entrée dans un appel système, valider en **liste blanche**.

## 4. Reconnaître et énumérer un CMS

**VulnCMS 1** héberge plusieurs applications web — un **WordPress**, un **Joomla**, un **Drupal** — sur des ports différents. Le travail : identifier chaque CMS, sa **version**, puis trouver l'exploit public qui lui correspond.

- **Prendre l'empreinte** — `whatweb <url>`, la page `/robots.txt`, les méta-générateurs du HTML, les chemins caractéristiques : `/wp-login.php` et `/wp-content/` (WordPress), `/administrator/` (Joomla), `/user/login` et `CHANGELOG.txt` (Drupal).
- **Énumérer avec l'outil dédié** — `wpscan --url <url> --enumerate` pour WordPress (thèmes, extensions, utilisateurs, versions vulnérables), `joomscan`, `droopescan` pour les autres.
- **Faire correspondre un exploit** — une fois le logiciel **et sa version** connus, `searchsploit <cms> <version>` ou la base Exploit-DB donne le code prêt à l'emploi.

La leçon : **identifier précisément le logiciel et sa version** est ce qui transforme une page web en porte d'entrée.

## 5. De l'injection SQL au shell

Le lab **Pentester Lab** enchaîne, en une seule machine, les étapes vues en cours d'injection SQL. Le chemin à connaître :

1. **Détecter** — un paramètre d'URL (`?id=1`) qui, suffixé d'une apostrophe `'`, casse la requête : l'erreur SQL trahit l'injection.
2. **Injection UNION** — `ORDER BY` donne le **nombre de colonnes**, puis `UNION SELECT` ajoute ses propres données à l'affichage. On lit alors la base : `UNION SELECT table_name FROM information_schema.tables`, puis les colonnes, puis la table des utilisateurs.
3. **Craquer le mot de passe** — les identifiants extraits sont souvent des **hachages MD5** non salés : `hashcat`/`john`, ou une simple base en ligne, redonnent le mot de passe en clair.
4. **S'authentifier** — on entre dans le panneau d'administration avec ces identifiants.
5. **Déposer un webshell** — le panneau permet d'**uploader une image**, mais ne vérifie que l'en-tête `Content-Type` annoncé par le navigateur, pas le **contenu** du fichier. On envoie donc un fichier `.php` (un `<?php system($_GET['c']); ?>`) en déclarant `Content-Type: image/jpeg` : le filtre est trompé, le fichier est servi, et l'appeler exécute du code — c'est le **shell**.

La leçon : une injection SQL ne sert pas qu'à lire des données ; combinée à un **upload mal filtré**, elle mène à l'exécution de code. Côté défense : requêtes **préparées**, et validation du **contenu** d'un fichier, jamais de son seul `Content-Type`.

## 6. Backdoor de service et énumération web

**Basic Pentesting 1** ouvre trois services : **FTP**, **SSH**, **HTTP**. Deux chemins, tous deux à connaître.

**Par le service vulnérable.** La bannière du FTP annonce **ProFTPD 1.3.3c**, une version qui embarque une **backdoor** connue : `searchsploit proftpd` la trouve, et le module Metasploit `exploit/unix/ftp/proftpd_133c_backdoor` donne directement un shell **root**. Le réflexe : lire la **version** d'un service et la chercher dans Exploit-DB.

**Par le web.** Sur le port 80, un scan de répertoires — `gobuster dir -u http://<ip> -w <liste>` ou `dirb` — révèle un dossier caché (`/secret/`) qui héberge un **WordPress**. De là : `wpscan` pour énumérer utilisateurs et extensions, puis la **force brute** d'un identifiant trouvé — `hydra -l <user> -P <liste> <ip> ssh` — pour ouvrir une session SSH, avant d'élever ses privilèges.

La leçon : **une version suffit parfois** (la backdoor), mais quand elle ne suffit pas, c'est l'**énumération web** patiente qui ouvre la voie.

## 7. La reconnaissance et le rapport de pentest

**FunBox CTF** est le second lab noté. Il demande, comme le lab 4, de dérouler la démarche complète et d'en tirer un **rapport**. Ce qui s'y révise :

- **La reconnaissance d'abord** — énumérer tous les services avant d'exploiter quoi que ce soit ; une archive protégée (`.zip`) laissée sur un service se **craque** (`fcrackzip -u -D -p <liste>`, `zip2john` puis `john`) ; des identifiants trouvés quelque part se **réutilisent** ailleurs (le même mot de passe sur FTP, SSH, un panneau web).
- **Le rapport** — attendu dans `Pentest_Report_Template.docx`, il contient :
  - la **démarche** et le périmètre ;
  - les **vulnérabilités** trouvées, chacune décrite et reproduite ;
  - une ou plusieurs propositions de **remédiation** (comment corriger) ;
  - une **matrice de risque** — chaque faille placée selon sa **probabilité** et son **impact**, ce qui donne sa criticité et l'**ordre** dans lequel la corriger.

La leçon : un pentest ne s'arrête pas au `root` obtenu ; sa valeur est dans le rapport qui **priorise** les corrections pour le client.

## 8. L'élévation de privilèges

C'est le dénominateur commun des cinq labs : une fois un premier accès obtenu (un utilisateur simple), passer à **root**. Les pistes à vérifier, de la plus simple à la plus technique :

| Piste | Commande | Ce qu'on cherche |
| --- | --- | --- |
| **sudo** | `sudo -l` | une commande lançable en root, souvent **sans mot de passe** (`NOPASSWD`) — et détournable via **GTFOBins** |
| **SUID** | `find / -perm -4000 -type f 2>/dev/null` | un binaire qui s'exécute avec les droits de son **propriétaire** (root) |
| **cron** | `cat /etc/crontab` | une tâche planifiée en root qui lance un script **modifiable** |
| **noyau** | `uname -a` | une version de noyau avec un exploit local connu |
| **mots de passe** | fichiers de config, historique, `/etc/passwd` | un identifiant réutilisable |

**LinPEAS** (Linux) et **WinPEAS** (Windows) automatisent toute cette recherche. Le réflexe de base, sur n'importe quelle machine : lancer `sudo -l` et chercher les binaires **SUID**.
