::rappel{titre="La boîte à outils du chapitre"}
- Une **table de hachage** associe des **clés** à des **valeurs** : une **fonction de hachage** donne à chaque clé un numéro, la case du tableau où la ranger.
- Deux clés envoyées dans la même case : c'est une **collision**.
- **Adressage fermé** : chaque case contient un **seau** (*bucket*), une structure à part — liste chaînée, vecteur, arbre — qui accueille toutes les clés de la case.
- **Adressage ouvert** : tout est rangé dans le tableau ; une clé qui trouve sa case occupée en essaie d'autres, selon une méthode appelée **probing** : linéaire, quadratique ou **double hashing**.
- En adressage ouvert, on cherche jusqu'à trouver la clé **ou une case vide** ; une clé supprimée laisse une **pierre tombale** pour ne pas briser les chaînes de recherche.
- Sans collision, la recherche est **constante** ; dans le pire des cas, elle est **linéaire**.
- Chaque appel de fonction occupe de la place dans **la pile**, de taille limitée : une récursion trop profonde la fait déborder. On s'en passe avec **une variable** (récursion linéaire) ou **sa propre pile**, rangée dans le tas.
::

## 1. La table de hachage

Une **table de hachage** est une structure de données qui permet d'**associer des clés et des valeurs** : le nom d'un utilisateur et son âge, un mot et sa définition, un nom de variable et son contenu.

On utilise une fonction appelée **fonction de hachage**, qui associe **un nombre** à chaque clé possible. Les valeurs sont enregistrées dans un tableau, **à la position donnée par la fonction de hachage**.

Par exemple, si `hash("Lundi") = 3`, `hash("Mercredi") = 0` et `hash("Vendredi") = 5`, on enregistre les valeurs aux adresses 3, 0 et 5 du tableau :

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| Contenu | Mercredi | | | Lundi | | Vendredi | |

Pour retrouver `"Lundi"`, on ne parcourt pas le tableau : on recalcule `hash("Lundi")`, et l'on va **directement** en case 3.

::exemple{id="ha-ex-hachage" titre="Une fonction de hachage simple : la première lettre" pour="Calculer la case d'une clé"}
Le contrôle d'exemple range des prénoms dans 8 cases avec la position de la première lettre dans l'alphabet : `(key[0] - 'a') % 8`.

- `"alice"` : `'a' - 'a'` vaut 0, case **0** ;
- `"eric"` : `'e' - 'a'` vaut 4, case **4** ;
- `"hanna"` : `'h' - 'a'` vaut 7, case **7** — `h` est la huitième lettre, mais les cases se numérotent à partir de 0 ;
- `"jules"` : `'j' - 'a'` vaut 9, et $9 \% 8 = 1$ : case **1**. Le modulo ramène tout numéro dans le tableau.

La fonction est rapide, mais médiocre : tous les prénoms en `a`, en `i` et en `q` tombent dans la même case.
::

::

## 2. Les collisions et les deux adressages

Lorsque la fonction de hachage affecte **plusieurs clés à la même case** du tableau, on parle de **collision**. Par exemple, si en plus `hash("Samedi") = 3`, Samedi et Lundi se retrouvent à la même position :

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| Contenu | Mercredi | | | Lundi, Samedi | | Vendredi | |

Une fonction de hachage associe un nombre limité de cases à un nombre bien plus grand de clés possibles : les collisions sont **inévitables**, il faut savoir les gérer. Il existe principalement deux façons de le faire :

- l'adressage dit **fermé** (*closed addressing*) : on enregistre les données dans une **structure externe** ;
- l'adressage dit **ouvert** (*open addressing*) : toutes les données sont enregistrées **dans un seul tableau**.

::exemple{id="ha-ex-collisions" titre="Repérer les collisions" pour="Savoir quelles clés vont se gêner"}
Avec la fonction « nombre de lettres modulo 7 » :

| Clé | Lettres | Case |
|---|---|---|
| Rome | 4 | 4 |
| Paris | 5 | 5 |
| Lyon | 4 | 4 |
| Nice | 4 | 4 |

`Rome`, `Lyon` et `Nice` sont en collision : trois clés pour la case 4. Elles seules auront besoin d'une stratégie ; `Paris` est seule dans sa case.
::

:::qcm{titre="Contrôle express — les collisions" icone="i-lucide-circle-check-big" compact}

::qcm-question{label="1." bonne="a" cours="ha-collisions"}
Qu'appelle-t-on une **collision** dans une table de hachage ?

#a
Deux clés différentes auxquelles la fonction de hachage donne la même case.

#b

#c
Une clé dont la case dépasse la taille du tableau.

#d
Une recherche qui ne trouve pas la clé.

#indice

#solution

**Les distracteurs :** **b** : insérer une clé déjà présente met à jour sa valeur ; **c** : le modulo ramène toujours la case dans le tableau ; **d** est une recherche infructueuse.
::
:::

## 3. L'adressage fermé

Lorsque plusieurs données doivent être enregistrées dans la même case, on les accumule dans un **seau** (en anglais : *bucket*). On peut alors choisir différentes structures de données selon le besoin : **liste chaînée, vecteur, arbre**…

```text
case 0 : [Lundi] → [Jeudi] → [Mardi]       liste chaînée
case 3 : [Alice | Bob | Marie]             vecteur
case 6 :       3                           arbre binaire de recherche
              / \
             1   4
```

- **Avantages** : simple à implémenter ; on peut ajouter des éléments sans avoir à modifier la structure interne de la table ; dans le cas d'un seau trop rempli, l'usage d'un **arbre** peut accélérer la recherche ; si l'on utilise une liste chaînée, l'insertion d'un élément dans un seau est en temps **constant**.
- **Désavantages** : enregistrer un pointeur avec chaque élément **augmente la mémoire utilisée** ; les données sont éparpillées dans la mémoire et **difficiles à mettre en cache** ; le dernier point rend aussi **les prédictions difficiles** ; chaque insertion peut demander une allocation, ce qui **augmente le nombre d'appels système**.

Ce sont les défauts de la liste chaînée du premier chapitre : un seau est souvent une petite liste chaînée.

::exemple{id="ha-ex-ferme" titre="Une table à seaux, case par case" pour="Insérer et chercher en adressage fermé"}
Table de 8 cases, fonction `(key[0] - 'a') % 8`, seaux en listes chaînées, insertion **en tête** du seau. On insère `bruno`, `lucas`, `jade`, `tom`, `rachid` :

| Clé | Calcul | Case |
|---|---|---|
| bruno | $1 \% 8$ | 1 |
| lucas | $11 \% 8$ | 3 |
| jade | $9 \% 8$ | 1 |
| tom | $19 \% 8$ | 3 |
| rachid | $17 \% 8$ | 1 |

```text
case 1 : [rachid] → [jade] → [bruno]
case 3 : [tom] → [lucas]
```

Chercher `bruno` : on calcule la case 1, puis on parcourt **son seau seulement** — trois comparaisons, quelle que soit la taille du reste de la table.
::

:::qcm{titre="Contrôle express — l'adressage fermé" icone="i-lucide-circle-check-big" compact}

::
:::

## 4. L'adressage ouvert et le probing

En adressage ouvert, on enregistre **toutes les données dans le tableau** : si une case est déjà utilisée, on range la donnée dans **une autre case**. Par exemple, si les hashs de `"Alice"` et de `"Bob"` renvoient 2 chacun, on pourra enregistrer le premier dans la case 2 et le second dans la case 3.

La méthode utilisée afin de choisir la case où l'on enregistre les données de même hash s'appelle le **probing** (« sondage »). Il en existe trois familles principales :

- le **probing linéaire** ;
- le **probing quadratique** ;
- le **double hashing** (section suivante).

**Linéaire et quadratique.** On peut par exemple insérer la valeur dans la case $\text{hash(key)} + k \times N$, pour un entier $N$ choisi : au premier essai $k = 0$, puis $k = 1, 2, \dots$ jusqu'à trouver une case libre. On parle alors de probing **linéaire** — les cases essayées sont espacées de $N$. On parle de probing **quadratique** lorsque les cases sont calculées par un **polynôme** en $k$ (par exemple $k^2$), qui espace de plus en plus les essais.

::exemple{id="ha-ex-lineaire" titre="L'exemple du cours, pas à pas" pour="Insérer des clés avec un probing linéaire"}
Table de 8 cases, $N = 2$, avec `hash(Alice) = hash(Bob) = 3` et `hash(Lundi) = hash(Mardi) = 1`. On insère Alice, puis Lundi, puis Mardi, puis Bob.

| Clé | Cases essayées | Case retenue |
|---|---|---|
| Alice | 3 | **3** |
| Lundi | 1 | **1** |
| Mardi | 1 (Lundi), $1 + 2 = 3$ (Alice), $1 + 4 = 5$ | **5** |
| Bob | 3 (Alice), $3 + 2 = 5$ (Mardi), $3 + 4 = 7$ | **7** |

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Contenu | | Lundi | | Alice | | Mardi | | Bob |

Les cases essayées se calculent **modulo la taille** : au-delà de la case 7, on repart de 0.
::

:::qcm{titre="Contrôle express — le probing linéaire" icone="i-lucide-circle-check-big" compact}

::qcm-question{label="1." bonne="b" cours="ha-ouvert"}
Table de 8 cases, probing linéaire avec $N = 2$. On insère, dans cet ordre, Ana, Eva et Ida, de hash 2 tous les trois, puis Léo, de hash 4. Dans quelle case va Léo ?

#a
$4$

#b
$0$

#c
$6$

#d
$8$

#indice
Place d'abord Ana, Eva et Ida : cases 2, puis 4, puis 6. Puis essaie 4, 6, 8… sans oublier le modulo.

#solution
Ana va en 2 ; Eva essaie 2 puis $2 + 2 = 4$ ; Ida essaie 2, 4, puis 6. Léo essaie 4 (Eva), 6 (Ida), puis $4 + 4 = 8$, soit $8 \% 8 = 0$ : case **0**. **b** est juste.

**Les distracteurs :** **a** oublie qu'Eva occupe déjà la case 4 ; **c** oublie Ida ; **d** oublie le modulo : il n'y a pas de case 8.
::

::qcm-question{label="2." bonne="c" cours="ha-ouvert"}
Qu'est-ce qui distingue le probing **quadratique** du probing linéaire ?

#a
Il range les collisions dans un seau à part.

#b
Il essaie toujours la case juste après.

#c
Les cases essayées sont calculées par un polynôme, et s'espacent de plus en plus.

#d

#indice
Linéaire : $\text{hash} + k \times N$. Et quadratique ?

#solution
Le probing quadratique calcule la $k$-ième case essayée par **un polynôme** en $k$ (comme $\text{hash} + k^2$) : les essais s'éloignent de plus en plus. **c** est juste.

**Les distracteurs :** **a** est l'adressage fermé ; **b** est le probing linéaire avec $N = 1$ ; **d** est le double hashing.
::
:::

## 5. Le double hashing

On peut aussi calculer la prochaine case en utilisant **une autre fonction de hachage**, ici nommée `hash2`. Cette deuxième fonction accepte en arguments **la clé à insérer** ainsi que **le nombre de tentatives infructueuses** d'insertion. On parle alors de **double hashing**.

L'exemple du cours insère encore Alice, Lundi, Mardi puis Bob dans 8 cases, avec les mêmes hashs, et

$$
\text{hash2(key, count)} = \text{strlen(key)} + \text{count}
$$

La case essayée après `count` échecs est $\text{hash(key)} + \text{hash2(key, count)}$, modulo 8.

| Clé | Cases essayées | Case retenue |
|---|---|---|
| Alice | 3 | **3** |
| Lundi | 1 | **1** |
| Mardi | 1 (Lundi), puis $1 + (5 + 1) = 7$ | **7** |
| Bob | 3 (Alice), puis $3 + (3 + 1) = 7$ (Mardi), puis $(3 + 3 + 2) \% 8 = 0$ | **0** |

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Contenu | Bob | Lundi | | Alice | | | | Mardi |

Deux clés de même hash mais de longueurs différentes ne suivent pas le même chemin : c'est l'intérêt de la seconde fonction, qui **disperse** les clés en collision au lieu de les aligner les unes derrière les autres.

::rappel{titre="Ce que la diapo écrit autrement" icone="i-lucide-triangle-alert"}
Dans la suite de diapos du double hashing, chaque légende est en avance d'une image : « On insère Alice dans la case 3 » est écrit sous un tableau qui ne montre encore que Lundi, « On insère Lundi dans la case 1 » sous le tableau qui montre Alice. Le tableau ci-dessus donne l'état final, qui est bien celui de la dernière diapo.
::

::exemple{id="ha-ex-double" titre="Insérer une cinquième clé par double hashing" pour="Appliquer hash2 avec son compteur d'échecs"}
On ajoute `"Eve"`, de hash 1, à la table finale ci-dessus.

- Essai 0 : case 1, occupée par Lundi.
- Essai 1 : $1 + \text{hash2}(\text{Eve}, 1) = 1 + (3 + 1) = 5$, libre.

`Eve` va en case **5**. Avec un probing linéaire de pas 2, elle aurait essayé 1, 3 (Alice), puis 5 : même case ici, mais par un autre chemin — et une clé de longueur différente, de même hash, aurait suivi encore un autre chemin en double hashing.
::

## 6. Rechercher et supprimer : la pierre tombale

**La recherche.** Lorsqu'on recherche un élément dans la table, on parcourt les cases **en suivant la méthode d'insertion**, jusqu'à trouver l'élément **ou une case vide**. Dans la table du double hashing, pour chercher Bob, on examine les cases 3, 7 et 0. Une case vide arrête la recherche : si Bob était là, il aurait été rangé dans cette case.

**La suppression.** Lorsqu'on supprime un élément, on doit **retenir qu'il était présent**, afin de **ne pas briser les chaînes de recherche**. On parle alors de **pierre tombale** (en anglais *tombstone*).

Par exemple, après avoir supprimé Alice, on doit toujours pouvoir rechercher Bob, qui était passé par la case 3 : on enregistre qu'un élément était présent en case 3.

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Contenu | Bob | Lundi | | † | | | | Mardi |

La recherche de Bob examine la case 3 : **pierre tombale**, elle continue ; puis la 7 (Mardi), puis la 0 : trouvé.

::rappel{titre="Ce que la diapo écrit autrement" icone="i-lucide-triangle-alert"}
La diapo de la pierre tombale montre Mardi en case **6**, alors qu'il était en case **7** sur la diapo précédente. C'est bien en 7 qu'il est : la recherche de Bob passe par lui.
::

- **Avantages** de l'adressage ouvert : l'utilisation d'un seul tableau améliore la **localité**, la **prédictibilité** ainsi que l'**empreinte mémoire**.
- **Désavantages** : si le **taux de remplissage** est élevé, l'insertion et la recherche deviennent très coûteuses ; il faut toujours **réserver plus d'espace que nécessaire** ; dans certains cas, il peut être nécessaire de **nettoyer la table** en supprimant les pierres tombales et en **recalculant la position de tous les éléments**.

::exemple{id="ha-ex-tombale" titre="Ce qui se passe sans pierre tombale" pour="Comprendre pourquoi on ne vide pas la case"}
Même table, mais on supprime Alice en **vidant** la case 3.

On cherche Bob : hash 3, case 3… **vide**. La recherche s'arrête et conclut que Bob est absent — alors qu'il est en case 0. La chaîne de recherche 3 → 7 → 0 a été **brisée**.

Avec la pierre tombale, la case 3 dit « quelqu'un était ici, continue » : la recherche passe, trouve Bob en case 0. Le prix : les pierres tombales s'accumulent et allongent les recherches, d'où le **nettoyage** de temps en temps.
::

:::qcm{titre="Contrôle express — recherche et pierre tombale" icone="i-lucide-circle-check-big" compact}

#a

#b

#c

#d

#solution
Une recherche s'arrête sur une **case vide**. Vider la case d'une clé supprimée couperait le chemin des clés qui l'avaient trouvée occupée et avaient continué plus loin. La pierre tombale dit « continue » : **d**.

::

::

## 7. Temps d'accès et tables modernes

**Le temps d'accès.** Lorsqu'il n'y a **aucune collision** pour les clés enregistrées dans la table, la recherche d'une clé s'effectue en temps **constant**, $O(1)$. Dans le **pire des cas** — toutes les clés dans la même case —, elle s'effectue en temps **linéaire**, $O(n)$.

Il est aussi possible d'**allouer un tableau plus grand** afin de réduire la probabilité de collision ; il faudra alors **recalculer le hash de chaque clé** avant de la réinsérer, puisque la case dépend de la taille du tableau. Le coût de cette opération est donc **linéaire**.

Un utilisateur malicieux qui connaît la fonction de hachage peut envoyer des clés **de même hash** afin d'augmenter le temps de recherche : on parle d'attaque de type **HashDos**. **Il est donc très important de choisir une fonction de hachage qui minimise la probabilité de collisions.**

**Les implémentations modernes.** Les implémentations récentes utilisent plus souvent l'adressage **ouvert**. Afin de préserver un maximum de données en cache, certaines enregistrent les informations sur les pierres tombales, la présence d'un élément ou même une partie du hash **dans un tableau à part** (cas des *swiss tables*). Certains algorithmes tentent de rapprocher les éléments les plus éloignés de leur position idéale en les échangeant avec des éléments plus proches (*Robin Hood hashing*).

**Les exemples réels.** La plupart des langages proposent une classe de « HashMap », et une table de hachage sert parfois à enregistrer les variables, les fonctions, les objets :

| Langage | Structure | Adressage |
|---|---|---|
| JavaScript, PHP | variables, tableaux associatifs | ouvert |
| C++ | `std::unordered_map` | fermé, seaux en listes chaînées |
| Java | `HashMap` | fermé : listes chaînées si moins de 9 éléments dans le seau, arbres binaires de recherche sinon |
| .NET | `Dictionary` | fermé, listes chaînées |
| .NET | `Hashtable` | ouvert, double hashing |
| Python | variables, fonctions, dictionnaires | ouvert, probing pseudo-aléatoire pour mieux distribuer les clés |
| Go | `map` | ouvert, probing quadratique, tableau de métadonnées et de fin de hash séparé |
| Rust | `HashMap` | ouvert, probing quadratique avec une graine aléatoire contre le HashDos, tableau de métadonnées séparé |

::rappel{titre="Ce que la diapo écrit autrement" icone="i-lucide-triangle-alert"}
La diapo cite `std::map` pour C++ : c'est un **arbre** (le cours sur les arbres le range d'ailleurs parmi eux) ; la table de hachage de C++, à seaux en listes chaînées, est **`std::unordered_map`**. Elle écrit aussi `Dictionnary` pour `Dictionary`.
::

::exemple{id="ha-ex-hashdos" titre="Le pire des cas fabriqué exprès" pour="Comprendre l'attaque HashDos"}
Un serveur range les paramètres d'une requête dans une table de 1 024 cases, avec une fonction de hachage connue. Un attaquant envoie 10 000 paramètres choisis pour avoir **tous le même hash**.

- Adressage fermé : un seul seau de 10 000 éléments ; chaque insertion vérifie si la clé existe déjà, soit jusqu'à $1 + 2 + \dots + 10\,000 \approx 5 \times 10^7$ comparaisons pour une seule requête.
- Avec des clés réparties normalement : une dizaine d'éléments par case, quelques dizaines de milliers de comparaisons.

D'où la parade de Rust : une **graine aléatoire** dans la fonction de hachage, différente à chaque lancement, rend les collisions impossibles à prévoir.
::

:::qcm{titre="Contrôle express — le temps d'accès" icone="i-lucide-circle-check-big" compact}

::qcm-question{label="1." bonne="c" cours="ha-acces"}
Quelle est la complexité de la recherche d'une clé dans une table de hachage de $n$ clés, **dans le pire des cas** ?

#a
Constante, $O(1)$

#b
Logarithmique, $O(\log n)$

#c
Linéaire, $O(n)$ : toutes les clés peuvent être en collision.

#d
Quadratique, $O(n^2)$

#indice
Imagine que la fonction de hachage envoie toutes les clés dans la même case.

#solution
Si toutes les clés sont en collision, la recherche parcourt toutes les clés de la case (ou toute la chaîne de probing) : **linéaire**. Le temps constant n'est vrai que **sans collision**. **c** est juste.

**Les distracteurs :** **a** est le cas sans collision ; **b** suppose des seaux en arbres équilibrés, ce qui n'est pas le cas général ; **d** est le coût de $n$ insertions dans ce pire des cas.
::

::qcm-question{label="2." bonne="a" cours="ha-acces"}
On agrandit le tableau d'une table de hachage pour réduire les collisions. Pourquoi faut-il recalculer le hash de toutes les clés ?

#a
Parce que la case d'une clé dépend de la taille du tableau (le modulo) : les anciennes positions ne sont plus les bonnes.

#b
Parce que la fonction de hachage change de résultat à chaque appel.

#c
Parce que `realloc` efface le contenu du tableau.

#d
Ce n'est pas nécessaire : il suffit de recopier les cases.

#indice
Avec 8 cases, une clé de hash 13 est en case 5. Et avec 16 cases ?

#solution
La case est le hash **modulo la taille** : $13 \% 8 = 5$, mais $13 \% 16 = 13$. Recopier les cases telles quelles laisserait les clés là où une recherche ne les cherchera plus. On recalcule et on réinsère tout : une opération **linéaire**. **a** est juste.

**Les distracteurs :** **b** : une fonction de hachage rend toujours la même valeur pour la même clé ; **c** : `realloc` conserve le contenu ; **d** est le piège décrit en **a**.
::
:::

## 8. La récursion et la pile d'appels

Une fonction **récursive** s'appelle elle-même. Le code ci-dessous parcourt une liste chaînée par récursion — le dernier nœud pointe vers lui-même :

```c
void parcours(NoeudListe* n){
  printf("%c\n", n->elem);
  if (n->suivant != n)
    parcours(n->suivant);
}
// affichera A K M
```

La récursion a des **désavantages** :

- **chaque appel de fonction alloue de l'espace dans la pile** pour enregistrer l'état de la mémoire et de l'exécution ;
- à chaque changement de fonction, l'exécution du code est **interrompue et les valeurs copiées** ;
- la mémoire des fonctions est dans la pile (*stack*), qui est de **taille limitée** et très inférieure au tas ;
- par exemple, **avant PHP 7.3**, une expression régulière de quelques kilooctets pouvait faire planter un serveur (attaque DOS).

Pour ces raisons, les applications qui veulent fonctionner sur des **structures profondes** ne peuvent pas toujours utiliser la récursion.

::exemple{id="ha-ex-pile-appels" titre="La profondeur qui fait planter" pour="Estimer quand une récursion déborde"}
Sur un Linux ou un macOS, la pile d'un programme fait le plus souvent **8 Mo**. Le parcours récursif d'une liste chaînée ajoute un appel par nœud ; si chaque appel occupe 48 octets de pile (adresse de retour, ancien `n`, registres sauvegardés), la pile déborde vers

$$
\dfrac{8 \times 1024 \times 1024}{48} \approx 175\,000 \text{ nœuds.}
$$

Une liste de 4 millions de caractères — le dictionnaire du TP 1 — fait donc planter `parcours` (*segmentation fault*), alors que le tas, lui, l'a contenue sans peine. Le TP 3 le montre sur un vérificateur de parenthèses : 200 000 parenthèses ouvrantes suffisent à le faire planter.
::

:::qcm{titre="Contrôle express — la pile d'appels" icone="i-lucide-circle-check-big" compact}

::qcm-question{label="1." bonne="b" cours="ha-recursion"}
Une fonction récursive plante sur une liste chaînée de dix millions de nœuds, alors que la liste elle-même tient en mémoire. Pourquoi ?

#a
Le tas est plein : la liste occupe trop de place.

#b
Chaque appel occupe de la place dans la pile, de taille limitée ; dix millions d'appels imbriqués la font déborder.

#c
Une fonction récursive ne peut pas s'appeler plus de 65 535 fois.

#d
Le compilateur refuse les fonctions récursives sur de grandes listes.

#indice
Où vivent les nœuds de la liste, et où vit la mémoire de chaque appel ?

#solution
Les nœuds sont dans le **tas**, vaste ; chaque appel en cours réserve sa place dans la **pile**, de quelques mégaoctets. Dix millions d'appels imbriqués la font déborder. **b** est juste.

**Les distracteurs :** **a** : la liste est déjà en mémoire ; **c** : aucune limite de ce genre, seule la taille de la pile compte ; **d** : le plantage a lieu à l'exécution.
::
:::

## 9. Retirer une récursion linéaire

Lorsqu'on peut réduire la tâche à effectuer à **une suite linéaire d'étapes**, le retrait de la récursion est trivial : il suffit d'**enregistrer le résultat de l'étape précédente dans une variable**.

```c
int factorial_rec(int x) {
  if (x > 1)
    return factorial_rec(x - 1) * x;
  else return 1;
}

int factorial_no_rec(int x) {
  int resultat = 1;
  while (x > 1)
    resultat *= x--;
  return resultat;
}
```

```c
void parcours_rec(NoeudListe* n){
  printf("%c\n", n->elem);
  if (n->suivant != n)
    parcours_rec(n->suivant);
}

void parcours_no_rec(NoeudListe* n){
  while (n->suivant != n){
    printf("%c\n", n->elem);
    n = n->suivant;
  }
  printf("%c\n", n->elem); // le dernier nœud
}
```

::rappel{titre="Ce que la diapo écrit autrement" icone="i-lucide-triangle-alert"}
La diapo écrit `factorial_rec(x - 1) * x;` **sans `return`** : la fonction calcule le produit et le jette, et ne renvoie rien de défini pour $x > 1$. Sa version de `parcours_no_rec` s'arrête dès que le nœud courant pointe vers lui-même, **sans afficher le dernier** (`M`) : il faut un dernier `printf` après la boucle. Enfin, sa version récursive appelle `parcours` au lieu de `parcours_rec`, et les deux affichent un caractère avec `%d`.
::

::exemple{id="ha-ex-lineaire-rec" titre="La somme des entiers, sans récursion" pour="Remplacer une récursion linéaire par une boucle"}
```c
int somme_rec(int n) {
  if (n == 0) return 0;
  return n + somme_rec(n - 1);
}
```

Chaque appel ne dépend que du résultat de l'appel suivant : c'est une suite linéaire d'étapes. La variable `total` joue le rôle de « résultat de l'étape précédente » :

```c
int somme_no_rec(int n) {
  int total = 0;
  while (n > 0) {
    total += n;
    n--;
  }
  return total;
}
```

`somme_rec(1000000)` empile un million d'appels — de quoi faire déborder la pile, sauf si le compilateur, en `-O2`, transforme lui-même la récursion en boucle — alors que `somme_no_rec` n'utilise que deux variables. (Un million d'additions débordent d'ailleurs l'`int` : il faudrait un `long`.)
::

:::qcm{titre="Contrôle express — la récursion linéaire" icone="i-lucide-circle-check-big" compact}

::qcm-question{label="1." bonne="d" cours="ha-lineaire"}
Comment retire-t-on une récursion **linéaire**, comme celle de la factorielle ?

#a
On la remplace par une table de hachage des résultats.

#b
On ne peut pas : il faut toujours une pile.

#c
On compile avec `-O3`.

#d
Par une boucle qui garde le résultat de l'étape précédente dans une variable.

#indice
Que transmet chaque appel au suivant ?

#solution
Chaque étape n'a besoin que du résultat de la précédente : une **boucle et une variable** suffisent, comme `resultat` dans `factorial_no_rec`. **d** est juste.

**Les distracteurs :** **a** n'enlève pas la récursion ; **b** : la pile n'est nécessaire que quand il reste plusieurs choses à faire après un appel, comme dans un arbre ; **c** peut aider le compilateur dans certains cas, mais ce n'est pas une méthode.
::
:::

## 10. Parcourir un arbre sans récursion

Pour un arbre, la récursion fait plus que répéter une étape : le parcours préfixé **affiche chaque nœud avant ses suivants**, et l'appel récursif **enregistre dans la pile les nœuds que l'on n'a pas encore parcourus, sous forme d'instructions à exécuter** — « il reste à parcourir le fils droit ».

```c
void parcours(Noeud* n){
  printf("%c\n", n->valeur);
  if (n->noeud_gauche)
    parcours(n->noeud_gauche);
  if (n->noeud_droit)
    parcours(n->noeud_droit);
}
```

**Sa propre pile.** Au lieu de laisser ces informations dans la pile du système, on peut les insérer dans **notre propre pile**, rangée dans le tas :

```c
void parcours(Noeud* r){
  Pile* p = creer_pile();
  empiler(p, r);
  while (!est_vide(p)){
    Noeud* n = depiler(p);
    printf("%c\n", n->valeur);
    if (n->noeud_droit)
      empiler(p, n->noeud_droit);
    if (n->noeud_gauche)
      empiler(p, n->noeud_gauche);
  }
}
```

On empile le fils droit **avant** le gauche : la pile rend le dernier entré, donc le gauche est traité d'abord, comme dans la version récursive.

```text
        A
      /   \
     B     K
    /     / \
   E     L   M
```

Sur cet arbre, les deux versions affichent **A B E K L M**.

**Une pile d'instructions.** Pour un parcours **postfixé**, l'approche récursive enregistrait dans la pile non seulement **les prochains nœuds à parcourir**, mais aussi **le nœud à afficher** une fois ceux-ci parcourus. Il faut donc enregistrer aussi le nœud dans la pile, avec un identifiant qui le distingue des nœuds à parcourir :

```c
typedef struct Inst {
  char affiche; // contient 1 si le nœud doit être affiché, 0 sinon
  Noeud* n;     // le nœud concerné
} Inst;

// construit une instruction à insérer dans la pile
Inst instruction(Noeud* n, int affiche) {
  return (Inst){ .affiche = affiche, .n = n };
}

void postfixe(Noeud* r){
  Pile* p = creer_pile();                // on crée une pile d'instructions
  empiler(p, instruction(r, 0));         // 0 car nœud à parcourir
  while (!est_vide(p)){
    Inst i = depiler(p);
    if (i.affiche) {
      printf("%c ", i.n->valeur);
    } else {
      empiler(p, instruction(i.n, 1));   // 1 car nœud à afficher
      if (i.n->noeud_droit)
        empiler(p, instruction(i.n->noeud_droit, 0));
      if (i.n->noeud_gauche)
        empiler(p, instruction(i.n->noeud_gauche, 0));
    }
  }
}
```

Le nœud à afficher est empilé **en premier** : il ne ressortira qu'une fois ses deux sous-arbres entièrement traités. Sur l'arbre ci-dessus, `postfixe` affiche **E B L M K A** — vérifié en compilant.

::rappel{titre="Ce que la diapo écrit autrement" icone="i-lucide-triangle-alert"}
- Sous le code préfixé, la diapo annonce « affichera E B A L K M » : c'est l'ordre **infixé**. Le parcours préfixé affiche **A B E K L M**.
- La dernière diapo est titrée « Parcours Préfixé non récursif » alors que sa fonction s'appelle `postfixe` et fait bien un parcours **postfixé**.
- Les diapos écrivent `n.noeud_gauche` sur un pointeur (c'est `n->noeud_gauche`), `p->depiler()` comme une méthode (on écrit `depiler(p)` en C), et `enpiler(r)` sans la pile.
::

::exemple{id="ha-ex-pile-arbre" titre="La pile pendant un parcours préfixé" pour="Suivre le contenu de sa propre pile"}
Sur l'arbre A, B, K, E, L, M (sommet de la pile à droite) :

| Dépile | Affiche | Empile | Pile après |
|---|---|---|---|
| | | A | A |
| A | A | K, puis B | K B |
| B | B | E | K E |
| E | E | | K |
| K | K | M, puis L | M L |
| L | L | | M |
| M | M | | (vide) |

La pile ne contient jamais plus que les sous-arbres **en attente** : sa taille suit la hauteur de l'arbre, et elle vit dans le tas, où la place ne manque pas.
::

:::qcm{titre="Contrôle express — sa propre pile" icone="i-lucide-circle-check-big" compact}

::qcm-question{label="1." bonne="c" cours="ha-arbre"}

#a
A B E K L M

#b
E B L M K A

#c
A K M L B E

#d
E B A L K M

#indice
La pile rend le dernier empilé : c'est maintenant le fils droit qui est traité en premier, à chaque nœud.

#solution
À chaque nœud, le droit sort avant le gauche : A, puis K, puis M, L, puis B, E. Le programme affiche **A K M L B E** — un préfixé « en miroir ». **c** est juste (vérifié en compilant).

**Les distracteurs :** **a** est le bon ordre, avec le droit empilé d'abord ; **b** est le postfixé ; **d** l'infixé.
::

::qcm-question{label="2." bonne="a" cours="ha-arbre"}
Dans la fonction `postfixe`, pourquoi empile-t-on l'instruction « afficher le nœud » **avant** celles de ses fils ?

#a
Parce que la pile la rendra après eux : le nœud ne sera affiché qu'une fois ses deux sous-arbres parcourus.

#b
Pour que le nœud soit affiché avant ses fils.

#c

#d
Parce que la pile ne peut contenir qu'une instruction par nœud.

#indice

#solution

**Les distracteurs :** **b** décrit le préfixé ; **c** : rien n'est libéré dans ce parcours ; **d** : chaque nœud passe deux fois dans la pile, une fois pour être parcouru, une fois pour être affiché.
::
:::

::extrait-cours{id="ha-table" titre="La table de hachage" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_1-la-table-de-hachage"}
Une **table de hachage** associe des clés à des valeurs. Une **fonction de hachage** donne un nombre à chaque clé ; la valeur est rangée à cette position du tableau, **modulo sa taille**. Exemple : `(key[0] - 'a') % 8` range `"eric"` en case 4 et `"hanna"` en case 7. Pour retrouver une clé, on recalcule son hash et l'on va directement à la case.
::

::extrait-cours{id="ha-collisions" titre="Collisions et adressages" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_2-les-collisions-et-les-deux-adressages"}
Une **collision** : la fonction de hachage envoie deux clés différentes dans la même case. Deux façons de les gérer : l'adressage **fermé** (les données en collision vont dans une structure externe, un seau) et l'adressage **ouvert** (toutes les données restent dans le tableau).
::

::extrait-cours{id="ha-ferme" titre="L'adressage fermé" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_3-ladressage-fermé"}
Chaque case porte un **seau** (*bucket*) — liste chaînée, vecteur, arbre — qui accueille toutes ses clés. Simple, extensible, insertion constante avec une liste chaînée, arbre utile pour un seau trop rempli ; mais un pointeur par élément, des données éparpillées (cache, prédiction) et une allocation par insertion.
::

::extrait-cours{id="ha-ouvert" titre="L'adressage ouvert et le probing" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_4-ladressage-ouvert-et-le-probing"}
Tout est rangé dans le tableau ; une clé dont la case est occupée en essaie d'autres : c'est le **probing**. **Linéaire** : cases $\text{hash} + k \times N$ pour $k = 0, 1, 2, \dots$, modulo la taille. **Quadratique** : cases calculées par un polynôme en $k$. Ou **double hashing**.
::

::extrait-cours{id="ha-double" titre="Le double hashing" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_5-le-double-hashing"}
La case suivante est calculée par une **seconde fonction de hachage**, qui reçoit la clé et le **nombre de tentatives infructueuses**. Dans le cours : $\text{hash(key)} + \text{hash2(key, count)}$ avec $\text{hash2} = \text{strlen(key)} + \text{count}$, modulo la taille. Les clés en collision suivent des chemins différents.
::

::extrait-cours{id="ha-tombale" titre="Recherche et pierre tombale" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_6-rechercher-et-supprimer-la-pierre-tombale"}
On cherche en suivant la méthode d'insertion, jusqu'à la clé **ou une case vide**. Une clé supprimée laisse une **pierre tombale** : la recherche la traverse au lieu de s'arrêter, sans quoi les clés rangées plus loin deviendraient introuvables. Les pierres tombales allongent les recherches : on nettoie parfois la table en recalculant la position de tous les éléments.
::

::extrait-cours{id="ha-acces" titre="Le temps d'accès" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_7-temps-daccès-et-tables-modernes"}
Sans collision, la recherche est **constante** ; dans le pire des cas, **linéaire**. Agrandir le tableau réduit les collisions mais oblige à **recalculer le hash de chaque clé** (la case dépend de la taille) : coût linéaire. Des clés de même hash envoyées exprès ralentissent la table : attaque **HashDos**. D'où l'importance d'une fonction de hachage qui minimise les collisions.
::

::extrait-cours{id="ha-recursion" titre="La récursion et la pile" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_8-la-récursion-et-la-pile-dappels"}
Chaque appel de fonction réserve de la place dans **la pile**, de taille limitée (souvent 8 Mo) et bien plus petite que le tas ; chaque appel interrompt l'exécution et copie des valeurs. Une récursion trop profonde **fait déborder la pile** : une application qui traite des structures profondes ne peut pas toujours être récursive.
::

::extrait-cours{id="ha-lineaire" titre="Retirer une récursion linéaire" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_9-retirer-une-récursion-linéaire"}
Quand la tâche est une **suite linéaire d'étapes**, on remplace la récursion par **une boucle** qui garde le résultat de l'étape précédente dans **une variable** : `resultat *= x--;` pour la factorielle, `n = n->suivant;` pour le parcours d'une liste chaînée.
::

::extrait-cours{id="ha-arbre" titre="Parcourir un arbre sans récursion" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_10-parcourir-un-arbre-sans-récursion"}
On remplace la pile du système par **sa propre pile**, dans le tas. Préfixé : on dépile un nœud, on l'affiche, on empile **le fils droit puis le gauche**. Postfixé : on empile des **instructions** (nœud, afficher ou non) ; pour un nœud à parcourir, on empile d'abord « l'afficher », puis ses fils, afin qu'il ressorte après eux.
::
