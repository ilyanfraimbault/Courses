::rappel{titre="Mode d'emploi" icone="i-lucide-compass"}
Le TP met en pratique la seconde partie du cours : **une récursion trop profonde fait déborder la pile**, et l'on s'en débarrasse avec **sa propre pile**, rangée dans le tas.

- Les questions sur **ce qui plante et pourquoi** se corrigent d'un clic.
- Le **code à écrire** se rédige sur ta machine, se compile (`gcc -Wall -g -fsanitize=address`), se teste, puis se compare à la solution.
- Les seuils de plantage donnés ici ont été mesurés sur une machine dont la pile fait 8 Mo (`ulimit -s` affiche `8176`) ; ils varient d'une machine à l'autre, pas le fait de planter.
::

::::exercice{titre="1. Expression" theme="Faire planter un vérificateur de parenthèses récursif, puis le corriger"}
Le code ci-dessous lit un fichier et vérifie que les paires de parenthèses, crochets et accolades — et les guillemets — sont bien agencées.

```c
char fermeture(char c){
  switch (c) {
  case '(': return ')';
  case '[': return ']';
  case '{': return '}';
  case '"': return '"';
  default: return 0;
  }
}

char* match(char* s, char expected){
  while (*s) {
    if (*s == expected)
      return s + 1;
    char c = fermeture(*s);
    if (c) {
      s = match(s + 1, c);
      if (!s){
        return 0;
      }
    } else if (*s == ')' || *s == ']' || *s == '}') {
      return 0;
    } else {
      s++;
    }
  }
  return expected ? 0 : s;
}

int is_balanced_recursif(char* s){
  return match(s, 0) != 0;
}

char* read_file(const char* chemin){
  FILE* f = fopen(chemin, "rb");
  fseek(f, 0, SEEK_END);
  long taille = ftell(f);
  rewind(f);
  char* contenu = malloc(taille + 1);
  fread(contenu, 1, taille, f);
  contenu[taille] = '\0';
  fclose(f);
  return contenu;
}

int main(int argc, char* argv[]){
  char* contenu = read_file(argv[1]);
  if (is_balanced_recursif(contenu))
    printf("Le fichier est équilibré\n");
  else
    printf("Le fichier n'est pas équilibré\n");
  free(contenu);
  return 0;
}
```

`match(s, expected)` avance dans la chaîne jusqu'à trouver le caractère fermant `expected` ; à chaque caractère **ouvrant**, elle **s'appelle elle-même** pour chercher la fermeture correspondante.

:::exo-question{label="1." cours="tha-pile-appels"}
Lesquels de ces fichiers font **planter** le programme (et non simplement répondre « pas équilibré ») ?

::cases-a-cocher
---
propositions:
  - Un fichier de dix millions de parenthèses ouvrantes `(`.
  - Un fichier de dix millions de lettres `a`.
  - Un fichier vide.
  - Un fichier **équilibré** d'un million de `(` suivis d'un million de `)`.
  - Un chemin de fichier qui n'existe pas.
  - 'Le fichier `([)]`.'
bonnes: [1, 4, 5]
---
::

#indice
Compte combien d'appels de `match` sont en cours **en même temps** pour chaque fichier. Et regarde ce que fait `read_file` si `fopen` échoue.

#solution
**1, 4 et 5.**

- **1** : chaque `(` déclenche un appel de `match` qui ne se termine qu'à la fermeture : dix millions d'appels **imbriqués**, la pile déborde (*segmentation fault*, code de sortie 139).
- **4** : le fichier est équilibré, mais la profondeur atteint un million avant la première `)` : la pile déborde aussi. Être juste ne protège pas.
- **5** : `fopen` renvoie `NULL`, et `fseek(NULL, …)` plante. Lancer le programme **sans argument** plante de même (`argv[1]` vaut `NULL`).

**2** : aucun caractère ouvrant, aucune récursion — « équilibré ». **3** : la boucle ne tourne pas — « équilibré ». **6** : `[` attend `]` et trouve `)` : « pas équilibré », sans plantage.

Tout cela a été vérifié en exécutant le code du sujet.
:::

:::exo-question{label="2." cours="tha-pile-appels" code="c"}
Écris `ko.c`, un programme qui génère un fichier faisant planter le code donné.

#indice
Il suffit d'écrire dans un fichier un très grand nombre de caractères ouvrants, avec `fopen` et `fputc`.

#solution
```c
#include <stdio.h>

int main(void){
  FILE* f = fopen("ko.txt", "w");
  for (int i = 0; i < 10000000; i++) {
    fputc('(', f);   // dix millions d'appels récursifs imbriqués
  }
  fclose(f);
  return 0;
}
```

```bash
gcc -O3 -o ko ko.c && ./ko
./equilibre ko.txt     # Segmentation fault
```

Mesuré avec une pile de 8 Mo : 100 000 parenthèses passent encore ; **200 000** font planter le programme compilé en `-O0`, **500 000** le font planter même en `-O3`. Dix millions laissent une marge confortable sur n'importe quelle machine.
:::

:::exo-question{label="3." cours="tha-pile-appels" bonne="b"}
Un fichier de dix millions de parenthèses ouvrantes `(` fait planter le programme. Pourquoi ?

#a
`malloc` ne peut pas allouer dix millions d'octets.

#b
Chaque parenthèse ouvrante ajoute un appel de `match` dans la pile, de taille limitée : elle déborde.

#c
La boucle `while (*s)` ne s'arrête jamais, faute de caractère nul.

#d
`char*` ne peut pas pointer au-delà de 65 535 caractères.

#indice
Où vit la chaîne de dix millions d'octets, et où vit la mémoire de chaque appel de `match` ?

#solution
La chaîne est dans le **tas** (`malloc`), qui l'accueille sans peine. Mais chaque `(` ouvre un appel de `match` qui reste en cours jusqu'à sa fermeture : dix millions d'appels imbriqués, chacun avec sa place dans **la pile**, de quelques mégaoctets. La pile déborde. **b** est juste — c'est le désavantage de la récursion vu en cours, et l'attaque DOS de l'ancien PHP.

**Les distracteurs :** **a** : dix millions d'octets, c'est dix mégaoctets, rien pour le tas ; **c** : `read_file` termine la chaîne par `'\0'` ; **d** : un pointeur désigne n'importe quelle adresse.
:::

:::exo-question{label="4." cours="tha-pile-appels" bonne="d"}
Compilé en `-O0`, le programme plante sur un fichier de 200 000 parenthèses ouvrantes. On le recompile en `-O3`. Que devient le plantage ?

#a
Il disparaît : `-O3` transforme toute récursion en boucle.

#b
Il apparaît plus tôt : `-O3` agrandit les appels.

#c
Rien ne change : l'optimisation n'a aucun effet sur la pile.

#d
Il faut une profondeur un peu plus grande pour planter, mais le programme plante toujours.

#indice
`match` utilise le résultat de l'appel récursif (`s = match(…)`) pour continuer : le compilateur peut-il se passer de la pile ?

#solution
En `-O3`, le compilateur range mieux chaque appel, qui occupe moins de place dans la pile : le seuil recule (mesuré sur une machine dont la pile fait 8 Mo : 200 000 parenthèses plantent en `-O0`, pas en `-O3` ; les seuils exacts dépendent de la machine et du compilateur). Mais `match` **a besoin du résultat** de chaque appel pour poursuivre : la récursion ne peut pas devenir une simple boucle, et 500 000 parenthèses plantent dans les deux cas. **d** est juste.

**Les distracteurs :** **a** n'est vrai que de certaines récursions (celles dont l'appel est la toute dernière opération) ; **b** est l'inverse de ce qu'on mesure ; **c** : la taille des appels dépend bien de l'optimisation.
:::

:::exo-question{label="5." cours="tha-sa-pile" code="c"}
Modifie le programme pour qu'il ne plante plus : une vérification **sans récursion**, et un `main` qui résiste aux fichiers absents.

#indice
Ce que la récursion garde dans la pile, c'est la liste des caractères **fermants attendus**. Range-les dans ta propre pile — un tableau de `char` alloué dans le tas, qui double quand il est plein. Le caractère courant ferme-t-il le dernier attendu ? On dépile. Est-il ouvrant ? On empile sa fermeture.

#solution
```c
int is_balanced(char* s){
  int reserve = 16, taille = 0;
  char* attendus = malloc(reserve);    // la pile des fermetures attendues, dans le tas
  for (; *s; s++) {
    if (taille > 0 && *s == attendus[taille - 1]) {
      taille--;                        // le caractère ferme le dernier ouvert : on dépile
      continue;
    }
    char c = fermeture(*s);
    if (c) {
      if (taille == reserve) {         // la pile est un vecteur : sa réserve double
        reserve *= 2;
        attendus = realloc(attendus, reserve);
      }
      attendus[taille++] = c;          // on empile la fermeture attendue
    } else if (*s == ')' || *s == ']' || *s == '}') {
      free(attendus);
      return 0;                        // une fermeture qu'on n'attendait pas
    }
  }
  free(attendus);
  return taille == 0;                  // tout ce qui a été ouvert a été fermé
}

char* read_file(const char* chemin){
  FILE* f = fopen(chemin, "rb");
  if (f == NULL) {
    return NULL;                       // fichier absent : on le dit au lieu de planter
  }
  fseek(f, 0, SEEK_END);
  long taille = ftell(f);
  rewind(f);
  char* contenu = malloc(taille + 1);
  fread(contenu, 1, taille, f);
  contenu[taille] = '\0';
  fclose(f);
  return contenu;
}

int main(int argc, char* argv[]){
  if (argc < 2) {
    fprintf(stderr, "usage : %s fichier\n", argv[0]);
    return 1;
  }
  char* contenu = read_file(argv[1]);
  if (contenu == NULL) {
    fprintf(stderr, "impossible d'ouvrir %s\n", argv[1]);
    return 1;
  }
  if (is_balanced(contenu))
    printf("Le fichier est équilibré\n");
  else
    printf("Le fichier n'est pas équilibré\n");
  free(contenu);
  return 0;
}
```

Le test « ferme le dernier attendu » passe **avant** `fermeture`, comme le `if (*s == expected)` de `match` : c'est ce qui permet au guillemet `"` de fermer une chaîne ouverte par un guillemet.

Vérifié en compilant avec `-fsanitize=address` : `ko.txt` (dix millions de `(`) répond « pas équilibré » sans planter, le fichier équilibré d'un million de paires répond « équilibré », un fichier absent ou l'absence d'argument donnent un message d'erreur. Sur 400 000 chaînes aléatoires de parenthèses, crochets, accolades et guillemets, la nouvelle fonction rend **exactement** les mêmes réponses que `is_balanced_recursif`.
:::

:::exo-question{label="6." cours="tha-sa-pile" bonne="a"}
Une version sans récursion range les fermetures attendues dans un tableau de `char` alloué dans le tas, qui double quand il est plein : elle garde, elle aussi, une information par caractère ouvrant en attente. Pourquoi ne plante-t-elle pas sur dix millions de `(` ?

#a
Sa pile est un tableau dans le tas, qui peut grandir à la demande ; elle n'occupe qu'un octet par niveau, au lieu d'un appel de fonction entier dans la pile du système.

#b
Parce qu'elle s'arrête au premier caractère ouvrant.

#c
Parce que `realloc` ne réserve jamais plus de 8 Mo.

#d
Parce qu'elle ne lit que la moitié du fichier.

#indice
Compare l'endroit où vit l'information et sa taille, dans les deux versions.

#solution
La récursion gardait chaque niveau dans **la pile du système** (quelques mégaoctets), sous la forme d'un appel complet — adresse de retour, variables, registres. La nouvelle version garde **un octet** par niveau, dans un tableau du **tas**, qui double à la demande : dix millions de niveaux occupent environ 16 Mo de tas au plus, sans difficulté. **a** est juste.

**Les distracteurs :** **b** et **d** : la fonction lit tout le fichier ; **c** : `realloc` n'a pas de telle limite — et une limite ferait justement échouer.
:::

:::exo-question{label="7." cours="tha-sa-pile" bonne="b"}
Le fichier contient `{"a(" }`. Le programme le juge-t-il équilibré ?

#a
Oui

#b
Non

#indice
Une fois le guillemet ouvert, `match` cherche le guillemet fermant… mais regarde ce qu'elle fait des caractères qu'elle rencontre en chemin.

#solution
**Non.** `{` attend `}`, puis `"` ouvre une chaîne qui attend `"`. Mais à l'intérieur, `match` traite encore les caractères ouvrants : la `(` attend une `)`, et la recherche de cette `)` rencontre le second `"` — qui ouvre une **nouvelle** chaîne au lieu de fermer la première —, puis l'espace, puis `}` : une fermeture inattendue. Résultat : « pas équilibré », pour les deux versions (vérifié en exécutant).

Le code ne fait donc pas ce qu'un compilateur ferait, où une parenthèse dans une chaîne ne compte pas. Pour cela, il faudrait ignorer tout caractère tant que le sommet de la pile attend un `"`.
:::

Chaque appel de fonction réserve de la place dans **la pile**, de taille limitée (souvent 8 Mo) et bien plus petite que le tas. Une récursion dont la profondeur dépend des données — ici, une parenthèse ouvrante par appel — **fait déborder la pile** sur une entrée assez profonde : *segmentation fault*. Avant PHP 7.3, une expression régulière de quelques kilooctets suffisait à faire planter un serveur.
::

::extrait-cours{id="tha-sa-pile" titre="Remplacer la récursion par sa propre pile" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_10-parcourir-un-arbre-sans-récursion"}
Ce que la récursion garde dans la pile du système — ce qu'il reste à faire —, on peut le garder dans **sa propre pile**, rangée dans **le tas** et qui grandit à la demande. On empile ce qu'on attend, on dépile quand c'est fait ; la boucle tourne tant que la pile n'est pas vide (ou jusqu'à la fin de l'entrée).
::
