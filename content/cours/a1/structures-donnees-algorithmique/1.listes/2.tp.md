::rappel{titre="Mode d'emploi" icone="i-lucide-compass"}
Le TP fait **mesurer** : il compare le temps et la mémoire d'un vecteur, d'une liste chaînée et d'une liste déroulée sur un dictionnaire de plus de quatre millions de caractères (`dict.txt`). Les temps dépendent de ta machine : ils ne sont pas donnés ici. Ce qui l'est, c'est **ce que les mesures doivent montrer**, et pourquoi — ces questions-là se corrigent d'un clic.

- **Compile avec `-O3`** pour toute comparaison de performance : sans optimisation, on mesure surtout le code inutile que le compilateur aurait retiré.
- Les **fonctions à écrire** se rédigent sur ta machine, se compilent (`gcc -Wall -O3`), se testent, puis se comparent à la solution. Une solution différente peut être tout aussi juste.
- Les tailles sont celles d'un Linux 64 bits : `char` 1 octet, `int` 4, **un pointeur 8**.
- Le sujet appelle le fichier `vector.c` ; celui qui est distribué s'appelle `vecteur.c`.

Pour te tester ce code, compile avec `gcc -Wall -g -fsanitize=address` : le moindre octet lu ou écrit hors d'un bloc alloué arrête le programme et désigne la ligne.

::::exercice{titre="Partie I — 1. Simplement chaînée" theme="Lire vecteur.c, mesurer le vecteur, écrire une liste chaînée à deux sentinelles"}
Le fichier `vecteur.c` charge `dict.txt` dans un vecteur de caractères (`vector_from_buffer`), puis compte, pour chaque lettre, ses occurrences en appelant `vector_rechercher` à partir de la position suivante. Il affiche le temps de chargement, la mémoire utilisée et le temps des recherches.

```c
typedef struct Vector {
  int taille;
  int reserve;
  char* valeurs;
} Vector;

Vector* vector_from_buffer(char* buffer, int size) {
  Vector* v = malloc(sizeof(Vector));
  v->taille = size;
  v->valeurs = buffer;
  v->reserve = size;
  return v;
}

void vector_add_elem(Vector* v, char elem) {
  v->taille++;
  if (v->taille > v->reserve) {
    v->reserve *= 2;
    char* new_tab = malloc(v->reserve);
    memcpy(new_tab, v->valeurs, v->taille);
    free(v->valeurs);
    v->valeurs = new_tab;
  }
  v->valeurs[v->taille - 1] = elem;
}

int vector_used_memory(Vector* v) {
  return sizeof(v) + sizeof(char) * v->reserve;
}

// dans main :
for (char c = 'a'; c < 'z'; c++) {
  for (int pos = 0; (pos = vector_rechercher(v, pos + 1, c)) != -1; total++);
}
```

La liste chaînée à implémenter utilise **deux nœuds sentinelles** :

```c
typedef struct Node {
  struct Node* next;
  char elem;
} Node;

typedef struct LinkedList {
  Node* start;
  Node* end;
} LinkedList;
```

:::exo-question{label="0." cours="tli-vecteur"}
Avant de modifier `vecteur.c`, repère ses défauts. Lesquels sont réels ?

::cases-a-cocher
---
propositions:
  - '`memcpy` dans `vector_add_elem` copie un octet de trop, lu hors de l''ancien tableau.'
  - '`vector_used_memory` compte la taille d''un pointeur au lieu de celle de la structure.'
  - 'La lettre `z` n''est jamais recherchée, alors que le programme annonce 26 parcours.'
  - Le caractère d'indice 0 n'est jamais examiné par la boucle de recherche.
  - '`vector_rechercher` lit au-delà de `taille`.'
  - '`vector_free` libère deux fois le même bloc.'
bonnes: [1, 2, 3, 4]
---
::

#indice
Regarde à quel moment `taille` est incrémentée par rapport au `memcpy`, ce que vaut `sizeof(v)` quand `v` est un `Vector*`, la borne de la boucle sur `c`, et la valeur de `pos` au premier appel.

#solution
**1, 2, 3 et 4.**

1. `taille` est incrémentée **avant** le `memcpy` : on copie `taille` octets, soit un de plus que les éléments présents, lus **après la fin** de l'ancien tableau. Compilé avec `-fsanitize=address`, un vecteur créé par `vector_new()` (réserve de 3) s'arrête dès le quatrième ajout sur un *heap-buffer-overflow*. Il faut copier les éléments **avant** l'ajout :

```c
void vector_add_elem(Vector* v, char elem) {
  if (v->taille == v->reserve) {
    v->reserve *= 2;
    char* new_tab = malloc(v->reserve);
    memcpy(new_tab, v->valeurs, v->taille); // les éléments présents, avant l'ajout
    free(v->valeurs);
    v->valeurs = new_tab;
  }
  v->valeurs[v->taille++] = elem;
}
```

2. `v` est un **pointeur** : `sizeof(v)` vaut 8, alors que la structure `Vector` en occupe 16. Il faut `sizeof(Vector)` (ou `sizeof(*v)`).
3. `c < 'z'` s'arrête à `y` : **25** lettres, pas 26. Il faut `c <= 'z'`.
4. `pos` part de 0 et le premier appel cherche à partir de `pos + 1`, soit 1 : le caractère d'indice 0 n'est jamais regardé. Il faut partir de `pos = -1`.

**5** est faux : la boucle de `vector_rechercher` s'arrête à `i < v->taille`. **6** aussi : `vector_free` libère `valeurs` puis la structure, deux blocs distincts. Il reste enfin un défaut dans `read_file` : si le fichier ne s'ouvre pas, `buffer` est renvoyé **sans avoir été initialisé** (le compilateur le signale avec `-Wall`).
:::

:::exo-question{label="1." cours="tli-amorti" bonne="b"}
Le vecteur est créé par `vector_from_buffer` sur un texte de $n$ caractères, donc avec `reserve` égale à $n$. On lui ajoute **50 caractères** avec `vector_add_elem`. Que devient la mémoire qu'il occupe ?

#a
Elle augmente de 50 octets.

#b
Elle double à peu près : la réserve passe de $n$ à $2n$ dès le premier ajout.

#c
Elle ne change pas : la réserve suffit.

#d
Elle est multipliée par 50.

#indice
La réserve est-elle pleine au moment du premier ajout ? Que fait alors `vector_add_elem` ?

#solution
`vector_from_buffer` crée un vecteur **sans aucune place libre** : `reserve` vaut `taille`. Le premier ajout trouve la réserve pleine, alloue $2n$ octets et recopie les $n$ caractères ; les 49 suivants tombent dans la place libre. La mémoire **double** à peu près : sur un texte de 13 006 caractères, `vector_used_memory` (corrigée) passe de 13 022 à 26 028 octets. **b** est juste.

C'est le prix du coût amorti : la réserve qui double garde l'ajout constant en moyenne, mais peut réserver jusqu'à deux fois la place utile.

**Les distracteurs :** **a** serait vrai d'un vecteur qui réalloue au plus juste à chaque ajout — et recopie tout à chaque fois ; **c** oublie que la réserve est pleine ; **d** confond le nombre d'ajouts et le facteur d'agrandissement.
:::

:::exo-question{label="2." cours="tli-sentinelles"}
Écris les fonctions de la liste chaînée à deux sentinelles :

```c
LinkedList* llist_new();
void llist_add_elem_start(LinkedList* ll, char elem);
LinkedList* llist_from_buffer(char* buffer, int size);
int llist_used_memory(LinkedList* ll);
Node* llist_rechercher(LinkedList* ll, Node* starting_at, char elem);
void llist_free(LinkedList* ll);
```

`llist_rechercher` renvoie le premier nœud contenant `elem` à partir de `starting_at` (compris), ou `NULL` s'il n'y en a pas. Puis modifie `main` pour afficher les mêmes mesures que pour le vecteur.

#indice
Une liste vide, c'est `start->next == end`. Ajouter au début, c'est insérer après `start`. Pour garder l'ordre du texte en n'ajoutant qu'au début, parcours le buffer **à l'envers**. Et la sentinelle de fin sert à la recherche : écris-y la lettre cherchée.

#solution
```c
LinkedList* llist_new() {
  LinkedList* ll = malloc(sizeof(LinkedList));
  ll->start = malloc(sizeof(Node));
  ll->end = malloc(sizeof(Node));
  ll->start->next = ll->end;  // liste vide : les deux sentinelles se suivent
  ll->end->next = NULL;
  return ll;
}

void llist_add_elem_start(LinkedList* ll, char elem) {
  Node* n = malloc(sizeof(Node));
  n->elem = elem;
  n->next = ll->start->next;  // 1. le nouveau nœud pointe vers l'ancien premier
  ll->start->next = n;        // 2. la sentinelle pointe vers le nouveau
}

LinkedList* llist_from_buffer(char* buffer, int size) {
  LinkedList* ll = llist_new();
  for (int i = size - 1; i >= 0; i--) {  // à l'envers : le dernier ajouté au début est buffer[0]
    llist_add_elem_start(ll, buffer[i]);
  }
  return ll;
}

int llist_used_memory(LinkedList* ll) {
  int total = sizeof(LinkedList) + 2 * sizeof(Node);  // la structure et ses deux sentinelles
  for (Node* n = ll->start->next; n != ll->end; n = n->next) {
    total += sizeof(Node);
  }
  return total;
}

Node* llist_rechercher(LinkedList* ll, Node* starting_at, char elem) {
  ll->end->elem = elem;  // la sentinelle de fin arrête forcément la boucle
  Node* n = starting_at;
  while (n->elem != elem) {
    n = n->next;
  }
  return n == ll->end ? NULL : n;
}

void llist_free(LinkedList* ll) {
  Node* n = ll->start;
  while (n != NULL) {           // la sentinelle de fin a next == NULL
    Node* suivant = n->next;    // lire le suivant AVANT de libérer
    free(n);
    n = suivant;
  }
  free(ll);
}
```

Dans `main`, la boucle de recherche devient :

```c
for (char c = 'a'; c <= 'z'; c++) {
  for (Node* p = ll->start; (p = llist_rechercher(ll, p->next, c)) != NULL; total++);
}
```

On part de `start` et l'on cherche toujours à partir du nœud **suivant** celui trouvé, comme `pos + 1` pour le vecteur. Testée sur un petit texte avec `-fsanitize=address`, cette version trouve exactement autant d'occurrences que le vecteur corrigé.
:::

:::exo-question{label="3." cours="tli-memoire" bonne="c"}
Que vaut `sizeof(Node)` sur un Linux 64 bits ?

```c
typedef struct Node {
  struct Node* next;
  char elem;
} Node;
```

#a
$9$

#b
$2$

#c
$16$

#d
$8$

#indice
Un pointeur occupe 8 octets, un `char` 1. Mais la taille d'une structure est un multiple de l'alignement de son plus gros champ.

#solution
`next` occupe 8 octets, `elem` 1 octet, soit 9 ; mais la structure doit pouvoir être rangée dans un tableau avec chaque `next` aligné sur 8 octets : le compilateur ajoute **7 octets de compensation**. `sizeof(Node)` vaut **16** — vérifié en compilant. **c** est juste.

**Les distracteurs :** **a** oublie la compensation ; **b** prend un pointeur sur 1 octet ; **d** oublie le caractère.
:::

:::exo-question{label="4." cours="tli-memoire" bonne="a"}
Le dictionnaire compte 4 058 504 caractères. Le vecteur occupe à peu près 4,06 Mo. Que renvoie à peu près `llist_used_memory` pour la liste chaînée du même texte ?

#a
$65$ Mo

#b
$4{,}06$ Mo

#c
$36{,}5$ Mo

#d
$8{,}1$ Mo

#indice
Un nœud par caractère, et `sizeof(Node)` vaut 16.

#solution
Un nœud de **16 octets** par caractère : $16 \times 4\,058\,504 = 64\,936\,064$ octets, plus la structure et ses deux sentinelles, soit **environ 65 Mo** — seize fois le vecteur, pour stocker le même octet par caractère. **a** est juste.

Et c'est une borne basse : `malloc` ajoute ses propres informations à chaque bloc, si bien qu'un nœud occupe en réalité plus de 16 octets dans le tas.

**Les distracteurs :** **b** compte un octet par caractère, comme le vecteur ; **c** compte 9 octets par nœud, sans compensation ; **d** compte un pointeur de… 2 octets.
:::

:::exo-question{label="5." cours="tli-localite" bonne="d"}
Les deux programmes font le même nombre d'appels à la fonction de recherche, et les deux recherches sont linéaires. Que doit montrer la mesure, compilée en `-O3` ?

#a
La liste est plus rapide, grâce à sa sentinelle de fin.

#b
Les deux temps sont égaux, puisque les deux parcours sont linéaires.

#c
La liste est plus rapide, car elle n'a jamais à recopier ses éléments.

#d
Le vecteur est nettement plus rapide : ses caractères se suivent dans la mémoire, la liste saute d'un nœud à l'autre.

#indice
La complexité ne dit rien du cache ni de la prédiction. Où sont rangés les caractères dans chacune des deux structures ?

#solution
Les deux recherches lisent les caractères un à un, mais le vecteur les lit **à la suite** : chaque ligne de cache apporte 64 caractères d'un coup, et le processeur anticipe la suite. La liste suit un pointeur vers une adresse imprévisible à chaque pas, et ses nœuds de 16 octets ne logent que 4 caractères par ligne de cache. Le vecteur gagne nettement — le cours parle d'un facteur pouvant aller jusqu'à plusieurs milliers. **d** est juste.

**Les distracteurs :** **a** : le vecteur peut aussi avoir sa sentinelle, et ce n'est pas elle qui fait la différence ; **b** confond complexité et temps réel ; **c** : la recherche ne recopie rien, ni dans l'un ni dans l'autre.
:::

::::exercice{titre="Partie I — 2. Doublement chaînée" theme="Ajouter le pointeur vers le précédent, et ce qu'il coûte"}
On reprend la liste précédente en ajoutant à chaque nœud un pointeur vers le **précédent** :

```c
typedef struct DNode {
  struct DNode* prev;
  struct DNode* next;
  char elem;
} DNode;
```

:::exo-question{label="1." cours="tli-double"}
Quelles fonctions de la partie précédente faut-il modifier ? Écris leur nouvelle version.

#indice
Toute fonction qui **raccorde** des nœuds doit maintenant tenir à jour deux pointeurs au lieu d'un. Une fonction qui se contente de lire `next` ne change pas.

#solution
Seules les fonctions qui **raccordent** des nœuds changent : `llist_new` et `llist_add_elem_start`. La recherche, le calcul de mémoire (à `sizeof(DNode)` près) et la libération ne font que suivre `next`.

```c
LinkedList* llist_new() {
  LinkedList* ll = malloc(sizeof(LinkedList));
  ll->start = malloc(sizeof(DNode));
  ll->end = malloc(sizeof(DNode));
  ll->start->prev = NULL;
  ll->start->next = ll->end;
  ll->end->prev = ll->start;
  ll->end->next = NULL;
  return ll;
}

void llist_add_elem_start(LinkedList* ll, char elem) {
  DNode* n = malloc(sizeof(DNode));
  DNode* premier = ll->start->next;
  n->elem = elem;
  n->prev = ll->start;
  n->next = premier;
  premier->prev = n;     // l'ancien premier (ou la sentinelle de fin) pointe en arrière vers n
  ll->start->next = n;
}
```

(`LinkedList` contient désormais des `DNode*`.) La sentinelle de fin rend maintenant l'**insertion à la fin** constante : `ll->end->prev` est le dernier nœud.
:::

#b

#d

**Les distracteurs :** **a** oublie la compensation ; **c** oublie le second pointeur ; **d** suppose que tout double, alors que seul un pointeur s'ajoute.

::::exercice{titre="Partie II — 3. Insertion dans le vecteur" theme="Insérer un caractère, puis une chaîne, au milieu du vecteur"}
On veut insérer du texte **au milieu** du vecteur : `vec_insere_char(v, 5, 'k')` insère le caractère `k` à la position 5 (la taille augmente de 1), et `vec_insere_chaine(v, 5, "coucou")` insère la chaîne `coucou` à la position 5. On s'en sert ensuite pour insérer la chaîne `"onjour"` **après toutes les occurrences de la lettre `b`** du texte, en mesurant le temps de l'opération et la mémoire après modification.

:::exo-question{label="1." cours="tli-insertion"}
Écris `vec_insere_char` et `vec_insere_chaine`, cette dernière en réutilisant la première.

#indice
Ajoute d'abord un caractère à la fin (c'est `vector_add_elem` qui agrandit si besoin), puis décale d'une case vers la droite tout ce qui suit la position. `memmove` sait copier entre deux zones qui se chevauchent, pas `memcpy`.

#solution
```c
void vec_insere_char(Vector* v, int pos, char c) {
  vector_add_elem(v, c);  // une case de plus, réallouée si la réserve est pleine
  // décaler les caractères de pos à la fin d'une case vers la droite
  memmove(v->valeurs + pos + 1, v->valeurs + pos, v->taille - 1 - pos);
  v->valeurs[pos] = c;
}

void vec_insere_chaine(Vector* v, int pos, char* s) {
  for (int i = 0; s[i] != '\0'; i++) {
    vec_insere_char(v, pos + i, s[i]);
  }
}
```

Avec une boucle à la place de `memmove`, il faut décaler **en partant de la fin** (`for (int i = v->taille - 1; i > pos; i--) v->valeurs[i] = v->valeurs[i - 1];`), sinon on écrase ce qu'on va copier.
:::

:::exo-question{label="2." cours="tli-insertion"}
Modifie le programme pour qu'il insère `"onjour"` après chaque `b` du texte, et affiche le temps de l'opération et la mémoire utilisée après modification.

#indice
Cherche le `b` suivant avec `vector_rechercher`, insère juste après, puis reprends la recherche **après le mot inséré** — sinon tu retrouves le `b` de `bonjour`… qui n'en a pas, mais tu perds du temps à relire `onjour`.

#solution
```c
start = clock();
for (int pos = 0; (pos = vector_rechercher(v, pos, 'b')) != -1; pos += 7) {
  vec_insere_chaine(v, pos + 1, "onjour");  // juste après le b
}
end = clock();
print_time("Insertion effectuée en %.3lf %s\n", ((double)(end - start)) / CLOCKS_PER_SEC);
printf("Mémoire utilisée pour %d éléments : %.3f Mo\n", v->taille, vector_used_memory(v) / 1000000.0);
```

`pos += 7` saute le `b` et les six lettres insérées. Sur `"abracadabra bob baobab"`, le résultat est `abonjourracadabonjourra bonjourobonjour bonjouraobonjourabonjour` — vérifié en compilant.
:::

:::exo-question{label="3." cours="tli-insertion" bonne="c"}
Le texte compte $n$ caractères, dont $k$ lettres `b`. Quelle est la complexité de l'insertion de `"onjour"` après chaque `b` avec `vec_insere_chaine` ?

#a
$O(k)$ : une insertion par `b`.

#b
$O(n)$ : un seul parcours du texte.

#c
$O(k \times n)$ : chaque insertion décale toute la suite du texte.

#d
$O(\log n)$

#indice
Combien de caractères `memmove` déplace-t-il pour une insertion au milieu, et combien d'insertions fait-on ?

#solution
Chaque caractère inséré décale **toute la suite du texte**, jusqu'à $n$ caractères ; on en insère $6k$. Le total est de l'ordre de $k \times n$ : **c**. Sur le dictionnaire, avec des dizaines de milliers de `b`, cela fait des dizaines de milliards de copies : la mesure le montre.

Pour rester linéaire avec un vecteur, il faudrait **construire un nouveau vecteur** en un seul parcours, en recopiant chaque caractère et en ajoutant `onjour` après chaque `b`.

**Les distracteurs :** **a** ne compte que les insertions, pas leur coût ; **b** ne compte que la recherche ; **d** n'a aucun rapport.
:::

::::exercice{titre="Partie II — 4. Insertion dans la liste chaînée" theme="Les mêmes fonctions pour la liste chaînée, et la comparaison"}
On écrit les mêmes fonctions pour la liste chaînée, et l'on compare les deux structures sur l'insertion de `"onjour"` après chaque `b`.

:::exo-question{label="1." cours="tli-insertion"}
Écris l'insertion d'un caractère et d'une chaîne **après un nœud** de la liste chaînée, puis la boucle qui insère `"onjour"` après chaque `b`.

#indice
Dans une liste chaînée, on n'insère pas « à la position 5 » — il faudrait suivre 5 liens — mais **après un nœud** qu'on tient déjà. Fais renvoyer à l'insertion de chaîne le dernier nœud inséré, pour reprendre le parcours après lui.

#solution
```c
void llist_insere_char(Node* apres, char c) {
  Node* n = malloc(sizeof(Node));
  n->elem = c;
  n->next = apres->next;
  apres->next = n;
}

// renvoie le dernier nœud inséré
Node* llist_insere_chaine(Node* apres, char* s) {
  for (int i = 0; s[i] != '\0'; i++) {
    llist_insere_char(apres, s[i]);
    apres = apres->next;
  }
  return apres;
}

// dans main
for (Node* n = ll->start->next; n != ll->end; n = n->next) {
  if (n->elem == 'b') {
    n = llist_insere_chaine(n, "onjour");  // on reprend après le r
  }
}
```

Sur `"abracadabra bob baobab"`, la liste obtenue se lit exactement comme le vecteur de la question précédente — vérifié en compilant.
:::

:::exo-question{label="2." cours="tli-insertion" bonne="a"}
Avec la liste chaînée, quelle est la complexité de la même opération (texte de $n$ caractères, $k$ lettres `b`) ?

#a
$O(n + k)$ : un parcours, et chaque insertion est constante.

#b
$O(k \times n)$, comme pour le vecteur.

#c
$O(k)$ : on n'a pas à parcourir le texte.

#d
$O(n^2)$

#indice
On tient le nœud du `b` au moment où on le trouve. Que coûte l'insertion de six nœuds après lui ?

#solution
On parcourt la liste **une fois** ($n$ pas) et chaque insertion change deux pointeurs : $6k$ insertions constantes. Total $O(n + k)$ : **a**. C'est là que la liste chaînée prend sa revanche sur le vecteur — quitte à occuper seize fois plus de mémoire et à chercher plus lentement.

**Les distracteurs :** **b** est le coût du vecteur, qui décale la suite à chaque insertion ; **c** oublie qu'il faut trouver les `b` ; **d** n'a pas de raison d'être.
:::

::::exercice{titre="Partie III — 5. La liste déroulée" theme="Compléter llv.c : une liste chaînée de petits vecteurs"}
Pour concilier les avantages de la liste chaînée et du vecteur, on utilise une **liste chaînée de petits vecteurs** (*unrolled list*). Le fichier `llv.c` donne les structures et les déclarations ; chaque nœud contient un vecteur dont la taille reste **entre 50 et 100** caractères (`MAX_SIZE` vaut 100).

```c
#define MAX_SIZE 100

typedef struct LLVNode {
  Vector* elem;
  struct LLVNode* next;
} LLVNode;

typedef struct LinkedListVector {
  LLVNode* start;
  LLVNode* end;
} LinkedListVector;

// la position d'un caractère : le nœud, et l'indice dans son vecteur
typedef struct LLVPos {
  LLVNode* node;
  int position;
} LLVPos;

LinkedListVector* llv_new() {
  LinkedListVector* llv = malloc(sizeof(LinkedListVector));
  llv->start = malloc(sizeof(LLVNode));
  llv->end = malloc(sizeof(LLVNode));
  llv->start->next = llv->end;
  llv->start->elem = vector_new(MAX_SIZE / 2);
  llv->end->next = llv->end;
  llv->end->elem = vector_new(MAX_SIZE / 2);
  return l;
}

LinkedListVector* llv_from_buffer(char* buffer, int size) {
  LinkedListVector* llv = llv_new();
  LLVNode* n = llv->start;
  for (int i = 0; i < size; i++) {
    int splitted = llv_add_elem_after(n, buffer[i]);
    if (splitted) {
      n = n->next;
    }
  }
  return llv;
}
```

Les fonctions à écrire : `llv_split_node` (sépare un nœud de 100 caractères en deux nœuds de 50), `llv_add_elem_after` (ajoute un caractère à la fin du vecteur d'un nœud, renvoie 1 si le nœud a dû être séparé), `llv_rechercher`, `llv_add_elem_at`, `llv_add_word_after`, `llv_count`, `llv_used_memory` et `llv_print_all`. Puis on compare les trois structures quand on remplace chaque `b` par `"bonjour"`.

:::exo-question{label="1." cours="tli-deroulee"}
Que faut-il corriger dans le code fourni avant même qu'il compile ?

::cases-a-cocher
---
propositions:
  - '`llv_new` renvoie `l`, une variable qui n''existe pas.'
  - '`vector_new` est appelée avec une taille, alors que celle de `vecteur.c` ne prend aucun argument.'
  - '`llv->end->next = llv->end;` crée une boucle infinie dans tout parcours.'
  - '`MAX_SIZE` devrait valoir 50.'
bonnes: [1, 2]
---
::

#indice
Lis `llv_new` ligne à ligne en te demandant ce que le compilateur en pense. Et pour la fin de liste : comment un parcours sait-il qu'il est arrivé ?

#solution
**1 et 2.** `llv_new` doit renvoyer `llv` ; et `vector_new(MAX_SIZE / 2)` suppose une version de `vector_new` qui prend la **réserve initiale** en argument — à écrire, par exemple :

```c
Vector* vector_new(int reserve) {
  Vector* v = malloc(sizeof(Vector));
  v->taille = 0;
  v->reserve = reserve;
  v->valeurs = malloc(reserve);
  return v;
}
```

**3** est faux : la sentinelle de fin qui pointe vers elle-même est un **choix** ; les parcours s'arrêtent quand ils atteignent `llv->end` (`while (n != llv->end)`), et ne suivent jamais son `next`. **4** est faux : 100 est la taille à laquelle on sépare, 50 celle des deux moitiés.

Remarque : ici, la sentinelle de **début** porte des données — `llv_from_buffer` remplit d'abord le vecteur de `start`. Seule `end` est une vraie sentinelle.
:::

:::exo-question{label="2." cours="tli-deroulee"}
Écris `llv_split_node`, `llv_add_elem_after`, `llv_rechercher`, `llv_add_elem_at`, `llv_add_word_after` et `llv_count`.

#indice
Pour séparer : crée un nœud, recopie-lui la seconde moitié du vecteur, raccourcis le premier (il suffit de changer sa `taille`), et insère le nouveau nœud **après** l'ancien. Pour chercher : `vector_rechercher` dans chaque vecteur, à partir de la position donnée dans le premier nœud, de 0 dans les suivants. Pour insérer un mot : attention, une séparation peut faire passer la suite du texte dans le nœud suivant.

#solution
```c
void llv_split_node(LLVNode* node) {
  LLVNode* nouveau = malloc(sizeof(LLVNode));
  nouveau->elem = vector_new(MAX_SIZE);
  int moitie = node->elem->taille / 2;
  for (int i = moitie; i < node->elem->taille; i++) {
    vector_add_elem(nouveau->elem, node->elem->valeurs[i]);
  }
  node->elem->taille = moitie;   // la seconde moitié est désormais dans nouveau
  nouveau->next = node->next;    // insertion après node, comme dans une liste chaînée
  node->next = nouveau;
}

int llv_add_elem_after(LLVNode* node, char elem) {
  vector_add_elem(node->elem, elem);
  if (node->elem->taille >= MAX_SIZE) {
    llv_split_node(node);
    return 1;
  }
  return 0;
}

LLVPos llv_rechercher(LinkedListVector* llv, LLVPos starting_at, char elem) {
  LLVNode* n = starting_at.node;
  int depart = starting_at.position;
  while (n != llv->end) {
    int i = vector_rechercher(n->elem, depart, elem);
    if (i != -1) {
      return (LLVPos){ n, i };
    }
    n = n->next;
    depart = 0;
  }
  return (LLVPos){ llv->end, -1 };  // pas trouvé
}

void llv_add_elem_at(LLVPos pos, char elem) {
  vec_insere_char(pos.node->elem, pos.position, elem);  // la fonction de la partie II
  if (pos.node->elem->taille >= MAX_SIZE) {
    llv_split_node(pos.node);
  }
}

void llv_add_word_after(LLVPos pos, char* word) {
  for (int i = 0; word[i] != '\0'; i++) {
    pos.position++;  // juste après le caractère précédent
    // si le nœud vient d'être séparé, cette position est passée dans le nœud suivant
    if (pos.position > pos.node->elem->taille) {
      pos.position -= pos.node->elem->taille;
      pos.node = pos.node->next;
    }
    llv_add_elem_at(pos, word[i]);
  }
}

int llv_count(LinkedListVector* l) {
  int total = 0;
  for (LLVNode* n = l->start; n != l->end; n = n->next) {
    total += n->elem->taille;
  }
  return total;
}
```

Testée sur 5 000 caractères pseudo-aléatoires avec `-fsanitize=address` : après l'insertion de `onjour` derrière chacun des 283 `b`, la liste déroulée se lit **octet pour octet** comme le vecteur, et tous ses nœuds (sauf le dernier) contiennent entre 50 et 98 caractères.
:::

:::exo-question{label="3." cours="tli-deroulee" bonne="b"}
`llv_from_buffer` charge les 4 058 504 caractères du dictionnaire. Combien de nœuds contiennent des données ?

#a
$40\,585$

#b
$81\,170$

#c
$4\,058\,504$

#d
$162\,340$

#indice
`llv_from_buffer` ajoute toujours dans le dernier nœud ; à 100 caractères, il le sépare en deux nœuds de 50 et continue dans le second. Que contiennent alors tous les nœuds sauf le dernier ?

#solution
Chaque séparation laisse derrière elle un nœud de **50** caractères, et l'on continue à remplir le second. À la fin, tous les nœuds sauf le dernier contiennent 50 caractères, et le dernier entre 50 et 99. Avec $4\,058\,504 = 50 \times 81\,169 + 54$ : **81 169 nœuds de 50**, plus un dernier de 54, soit **81 170** — vérifié en exécutant le code. **b** est juste.

**Les distracteurs :** **a** suppose des nœuds pleins (100 caractères) ; **c** compte un nœud par caractère, comme la liste chaînée ; **d** suppose des nœuds de 25.
:::

:::exo-question{label="4." cours="tli-deroulee" bonne="d"}
La liste déroulée du dictionnaire compte 81 170 nœuds de données. Chaque nœud coûte un `LLVNode` (16 octets), un `Vector` (16 octets) et une réserve de 100 caractères. Quelle mémoire occupe à peu près la liste déroulée du dictionnaire, à comparer aux 4,06 Mo du vecteur et aux 65 Mo de la liste chaînée ?

#a
$4{,}06$ Mo

#b
$65$ Mo

#c
$130$ Mo

#d
$10{,}7$ Mo

#indice
$81\,170$ nœuds de $16 + 16 + 100$ octets.

#solution
$81\,170 \times 132 \approx 10{,}7$ millions d'octets : **environ 10,7 Mo** (10 714 538 octets mesurés avec la solution ci-dessus). Plus que le vecteur — chaque petit vecteur est à moitié vide —, mais six fois moins que la liste chaînée. **d** est juste.

C'est le compromis du cours : une localité proche du vecteur, des insertions qui ne recopient qu'un petit vecteur, pour une mémoire intermédiaire.

**Les distracteurs :** **a** est le vecteur ; **b** la liste chaînée ; **c** compte un nœud par caractère avec un vecteur chacun.
:::

::extrait-cours{id="tli-vecteur" titre="Le vecteur et sa réserve" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_2-le-vecteur"}
Un **vecteur** range ses éléments à la suite dans un bloc de `reserve` cases, dont `taille` sont occupées. Quand la réserve est pleine, on alloue un bloc deux fois plus grand, on y recopie les `taille` éléments **présents**, on libère l'ancien, puis on écrit le nouvel élément. La mémoire d'un vecteur est `sizeof(Vector)` plus la réserve.
::

::extrait-cours{id="tli-amorti" titre="Le coût amorti" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_5-le-coût-amorti"}
Avec une réserve qui **double** quand elle est pleine, un ajout isolé peut recopier tout le vecteur (pire des cas linéaire), mais le total des copies reste sous $2n$ : le coût amorti est **constant**. En contrepartie, la réserve peut atteindre deux fois la place utile.
::

::extrait-cours{id="tli-sentinelles" titre="Les nœuds sentinelles" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_7-les-nœuds-sentinelles"}
Deux nœuds sentinelles, en début et en fin : liste vide quand `start->next == end`, et insérer en tête, c'est insérer **après `start`** (`n->next = start->next; start->next = n;`). Pour chercher, on écrit la valeur dans la sentinelle de fin : la boucle s'arrête forcément ; si c'est sur `end`, la valeur est absente.
::

::extrait-cours{id="tli-memoire" titre="Ce que coûte un nœud" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_8-les-limites-de-la-liste-chaînée"}
Chaque élément d'une liste chaînée traîne un pointeur (8 octets sur un Linux 64 bits). La taille d'une structure est arrondie au multiple de l'alignement de son plus gros champ : `{ Node* next; char elem; }` occupe **16** octets, pas 9. Pour des caractères, la liste chaînée occupe donc seize fois la mémoire d'un vecteur.
::

::extrait-cours{id="tli-localite" titre="Localité et cache" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_8-les-limites-de-la-liste-chaînée"}
Deux parcours linéaires ne durent pas le même temps : le vecteur lit des cases **qui se suivent** (cache rempli d'un coup, accès prévisible), la liste chaînée saute de nœud en nœud (**manque de localité**, indirection, prédiction difficile). Le cours parle d'un ralentissement allant jusqu'à plusieurs milliers.
::

::extrait-cours{id="tli-double" titre="La liste doublement chaînée" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_9-la-liste-doublement-chaînée"}
Chaque nœud a un `prev` et un `next` ; on garde deux sentinelles. Toute insertion ou suppression raccorde **deux** pointeurs de chaque côté. On gagne les parcours dans les deux sens et les opérations en fin de liste en temps constant ; on perd de la mémoire (deux pointeurs par élément).
::

::extrait-cours{id="tli-insertion" titre="Insérer au milieu : vecteur contre liste" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_10-vecteur-ou-liste-chaînée-le-comparatif"}
Insérer au milieu d'un vecteur décale toute la suite : **linéaire** par insertion. Dans une liste chaînée, insérer **après un nœud qu'on tient** change deux pointeurs : **constant** — c'est trouver la position qui est linéaire. Pour $k$ insertions trouvées en un parcours : $O(k \times n)$ avec un vecteur, $O(n + k)$ avec une liste chaînée.
::

::extrait-cours{id="tli-deroulee" titre="La liste déroulée" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_11-la-liste-déroulée"}
Une liste chaînée de **petits vecteurs** (ici de 50 à 100 caractères) : un vecteur qui atteint 100 est **séparé en deux** nœuds de 50. Un pointeur par vecteur au lieu d'un par caractère, une bonne localité à l'intérieur de chaque vecteur, et une insertion qui ne recopie qu'un petit vecteur ; mais l'accès n'est pas constant et la mémoire dépasse celle d'un vecteur.
::
