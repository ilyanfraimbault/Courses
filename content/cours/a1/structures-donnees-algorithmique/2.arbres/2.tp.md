::rappel{titre="Mode d'emploi" icone="i-lucide-compass"}
Le TP fait **mesurer** les recherches dans une liste de mots triée, puis dans un arbre binaire de recherche, sur le dictionnaire `dict.txt` et l'échantillon `echantillon.txt`. Les temps dépendent de ta machine : ils ne sont pas donnés ici. Ce qui l'est, c'est **ce que les mesures doivent montrer**, et pourquoi.

- **Compile avec `-O3`** pour toute comparaison de performance.
- Les **fonctions à écrire** se rédigent sur ta machine (`gcc -Wall -O3`), se testent, puis se comparent à la solution. Pour traquer les erreurs mémoire : `gcc -Wall -g -fsanitize=address`.
- Les tailles sont celles d'un Linux 64 bits : **un pointeur occupe 8 octets**.
- Les solutions ont été testées sur un dictionnaire synthétique de 16 580 mots triés et un échantillon de 492 mots absents du dictionnaire : mêmes résultats que la recherche naïve, liste toujours triée, arbre toujours ordonné.
::

::::exercice{titre="Partie I — 1. Mots triés" theme="Une liste de char*, l'insertion qui garde l'ordre, la recherche dichotomique"}
Le fichier `mots.c` charge les mots de `dict.txt` dans une liste de mots, **triée**, puis y insère les mots de `echantillon.txt`, les recherche, et les supprime, en mesurant chaque opération :

```c
// Insertion dans la liste triée : on part de la fin et on décale vers la droite
// tous les mots plus grands que le nouveau.
void mots_inserer(Vector* v, char* mot) {
  if (v->taille == v->reserve) {
    mots_agrandir(v);
  }
  int i = v->taille;
  for (; i > 0 && strcmp(v->valeurs[i - 1], mot) > 0; i--) {
    v->valeurs[i] = v->valeurs[i - 1];
  }
  v->valeurs[i] = copier_mot(mot);
  v->taille++;
}

// Recherche naïve : on compare avec chaque mot, du début à la fin.
int mots_rechercher(Vector* v, char* mot) {
  for (int i = 0; i < v->taille; i++) {
    if (strcmp(v->valeurs[i], mot) == 0) {
      return i;
    }
  }
  return -1;
}

// dans main, pour chaque mot de l'échantillon :
mots_supprimer(v, mots_rechercher(v, inserer->valeurs[i]));
```

Il faut d'abord adapter le vecteur du TP précédent pour qu'il contienne des `char*` au lieu de `char`.

:::exo-question{label="0." cours="tar-vecteur-mots"}
Le fichier `mots.c` ne compile ni ne fonctionne tel quel. Quels défauts sont réels ?

::cases-a-cocher
---
propositions:
  - Il inclut `vector.h`, qui n'est pas fourni.
  - '`mots_new` est déclarée mais jamais définie, et `mots_memoire` est appelée sans être définie.'
  - '`mots_lire_fichier` crée la liste avec le `vector_new()` du TP précédent, qui réserve 3 octets : le premier pointeur (8 octets) est écrit hors du bloc.'
  - '`mots_supprimer` recevrait l''indice `-1` pour un mot absent, et libérerait `valeurs[-1]`.'
  - '`mots_inserer` perd l''ordre alphabétique quand le nouveau mot est le plus petit.'
  - '`copier_mot` oublie la place du zéro final.'
bonnes: [1, 2, 3, 4]
---
::

#indice
Compile le fichier, puis lis chaque fonction : combien d'octets réserve `vector_new()`, et combien en faut-il pour ranger un `char*` ? Que renvoie la recherche pour un mot absent ?

#solution
**1, 2, 3 et 4.**

1. Le compilateur s'arrête dès la ligne 5 : `'vector.h' file not found`.
2. `Vector* mots_new();` n'a pas de corps, et `mots_memoire` n'existe nulle part : l'édition de liens échoue.
3. `vector_new()` fait `malloc(3)` : c'était 3 caractères, mais un `char*` occupe **8** octets. `valeurs[0] = copier_mot(…)` écrit hors du bloc dès le premier mot. Il faut réserver `reserve * sizeof(char*)` octets.
4. Dans `main`, tous les mots supprimés ont été insérés, donc trouvés ; mais pour un mot absent, `mots_rechercher` renvoie `-1` et `mots_supprimer` ferait `free(v->valeurs[-1])`. Il faut tester l'indice.

**5** est faux : si le nouveau mot est le plus petit, la boucle décale tous les mots et s'arrête à `i = 0`, où il est rangé. **6** est faux : `malloc(strlen(mot) + 1)` compte le zéro final. Enfin, `vector_free` ne libère pas chaque mot copié par `copier_mot` : une fuite.
:::

:::exo-question{label="1." cours="tar-vecteur-mots"}
Modifie le vecteur pour qu'il contienne des `char*` : la structure, `mots_new`, `mots_agrandir`, `mots_memoire` (pointeurs **et** chaînes) et la libération. Vérifie que `mots.c` compile et s'exécute.

#indice
Seul le type des cases change : `char** valeurs`, et chaque `malloc`/`realloc` multiplie par `sizeof(char*)`. Mais chaque case pointe vers une chaîne allouée à part : il faut la compter, et la libérer.

#solution
```c
typedef struct Vector {
  int taille;
  int reserve;
  char** valeurs;  // chaque case contient l'adresse d'un mot
} Vector;

Vector* mots_new() {
  Vector* v = malloc(sizeof(Vector));
  v->taille = 0;
  v->reserve = 16;
  v->valeurs = malloc(v->reserve * sizeof(char*));
  return v;
}

void mots_agrandir(Vector* v) {
  v->reserve *= 2;
  v->valeurs = realloc(v->valeurs, v->reserve * sizeof(char*));
}

int mots_memoire(Vector* v) {
  int total = sizeof(Vector) + v->reserve * sizeof(char*);
  for (int i = 0; i < v->taille; i++) {
    total += strlen(v->valeurs[i]) + 1;  // la chaîne et son zéro final
  }
  return total;
}

void mots_free(Vector* v) {
  for (int i = 0; i < v->taille; i++) {
    free(v->valeurs[i]);  // chaque mot a été alloué par copier_mot
  }
  free(v->valeurs);
  free(v);
}
```

Et `mots_lire_fichier` appelle `mots_new()` au lieu de `vector_new()`.

:::exo-question{label="2." cours="tar-insertion-triee" bonne="c"}
`mots_inserer` maintient l'ordre des mots. Quelle est sa complexité pour une liste de $n$ mots ?

#a
Constante : on écrit le mot dans une case.

#b
Logarithmique : la liste est triée.

#c
Linéaire : il faut décaler tous les mots plus grands d'une case.

#d
Quadratique : chaque décalage appelle `strcmp`.

#indice
Dans le pire des cas, le nouveau mot est le plus petit. Combien de mots faut-il décaler ?

#solution
Le nouveau mot doit trouver sa place **et** lui faire de la place : tous les mots plus grands glissent d'une case. Pour le plus petit mot, c'est toute la liste : **linéaire**. **c** est juste.

**Les distracteurs :** **a** oublie le décalage ; **b** : chercher la place pourrait être logarithmique (question suivante), mais **décaler** reste linéaire ; **d** : un `strcmp` par mot décalé, c'est un coût constant par mot (pour des mots de longueur bornée), donc toujours linéaire.
:::

:::exo-question{label="3." cours="tar-dichotomie"}
La liste est triée : réécris `mots_rechercher` pour qu'elle trouve un mot sans parcourir tous les mots, et compare les performances.

#indice
Compare le mot cherché à celui du **milieu** : s'il est plus petit, il ne peut être que dans la première moitié ; sinon dans la seconde. Recommence sur la moitié restante.

#solution
C'est la **recherche dichotomique** :

```c
int mots_rechercher(Vector* v, char* mot) {
  int debut = 0;
  int fin = v->taille - 1;
  while (debut <= fin) {
    int milieu = debut + (fin - debut) / 2;
    int c = strcmp(v->valeurs[milieu], mot);
    if (c == 0) {
      return milieu;
    }
    if (c < 0) {
      debut = milieu + 1;  // le mot du milieu est plus petit : chercher à droite
    } else {
      fin = milieu - 1;    // il est plus grand : chercher à gauche
    }
  }
  return -1;
}
```

Testée sur 17 072 mots : elle trouve exactement les mêmes indices que la recherche naïve, en **13,1 comparaisons en moyenne** au lieu de plusieurs milliers. Le gain mesuré sur le vrai dictionnaire doit être spectaculaire.
:::

::::exercice{titre="Partie II — 1. L'arbre binaire de recherche" theme="Couper la liste récursivement en deux : charger, chercher, insérer, supprimer, libérer"}
Plutôt que de couper la liste en deux une seule fois par comparaison, on la coupe **récursivement** en deux une fois pour toutes, en un arbre binaire de recherche :

```c
struct ArbreMots {
  ArbreMots* mot_gauche;
  char* mot;
  ArbreMots* mot_droit;
}
```

Les fonctions à créer :

- `ArbreMots* arbre_mots_charger(Vector*)` : crée l'arbre en coupant récursivement la liste triée en deux ;
- `int arbre_mots_mémoire(ArbreMots*)` : la mémoire totale des nœuds et des chaînes ;
- `int arbre_mots_rechercher(ArbreMots*, char*)` : 1 si le mot existe, 0 sinon ;
- `int arbre_mots_insérer(ArbreMots*, char*)` : insère le mot en préservant l'ordre, **sans préserver l'équilibre** ;
- `int arbre_mots_supprimer(ArbreMots*, char*)` : supprime le mot en préservant l'ordre, sans préserver l'équilibre ;
- `int arbre_mots_free(ArbreMots*, char*)` : libère la mémoire.

:::exo-question{label="1." cours="tar-charger"}
Écris `arbre_mots_charger`. Corrige au passage la déclaration de la structure.

#indice
Le mot du **milieu** de la liste devient la racine ; la moitié gauche de la liste donne le sous-arbre gauche, la moitié droite le sous-arbre droit. Écris une fonction auxiliaire qui travaille sur un intervalle `[debut, fin]`.

#solution
La structure telle qu'écrite ne compile pas : `ArbreMots` n'est pas encore un type à l'intérieur de sa propre définition, et il manque le `;` final.

```c
typedef struct ArbreMots {
  struct ArbreMots* mot_gauche;
  char* mot;
  struct ArbreMots* mot_droit;
} ArbreMots;

ArbreMots* creer_noeud(char* mot) {
  ArbreMots* a = malloc(sizeof(ArbreMots));
  a->mot = copier_mot(mot);  // l'arbre possède ses propres chaînes
  a->mot_gauche = NULL;
  a->mot_droit = NULL;
  return a;
}

ArbreMots* charger_entre(Vector* v, int debut, int fin) {
  if (debut > fin) {
    return NULL;  // intervalle vide : pas de nœud
  }
  int milieu = debut + (fin - debut) / 2;
  ArbreMots* a = creer_noeud(v->valeurs[milieu]);
  a->mot_gauche = charger_entre(v, debut, milieu - 1);
  a->mot_droit = charger_entre(v, milieu + 1, fin);
  return a;
}

ArbreMots* arbre_mots_charger(Vector* v) {
  return charger_entre(v, 0, v->taille - 1);
}
```

Testé sur 17 072 mots : le parcours infixé de l'arbre rend la liste dans l'ordre, et la hauteur vaut 14.
:::

:::exo-question{label="2." cours="tar-charger" bonne="b"}
On charge ainsi une liste triée de **1 000 000** de mots. Quelle est la hauteur de l'arbre obtenu ?

#a
$20$

#b
$19$

#c
$500\,000$

#d
$999\,999$

#indice
Chaque niveau coupe la liste restante en deux : l'arbre est aussi équilibré que possible. Sa hauteur est le plus grand $h$ tel que $2^h \le n$.

#solution
Couper au milieu à chaque fois donne un arbre aussi bas que possible : $2^{19} = 524\,288 \le 1\,000\,000 < 2^{20}$, donc la hauteur est **19** (vérifié en simulant la construction). **b** est juste. Une recherche visite au plus $19 + 1 = 20$ nœuds — autant de comparaisons que la recherche dichotomique, ce qui n'a rien d'étonnant : l'arbre **enregistre** les coupures que la dichotomie refait à chaque recherche.

**Les distracteurs :** **a** compte les nœuds visités au lieu des arêtes ; **c** et **d** décrivent un arbre dégénéré en liste.
:::

:::exo-question{label="3." cours="tar-recherche"}
Écris `arbre_mots_mémoire` et `arbre_mots_rechercher`.

#indice
La mémoire d'un arbre vide est 0 ; sinon, c'est le nœud, sa chaîne, et la mémoire de ses deux sous-arbres. Pour chercher, descends à gauche ou à droite selon `strcmp`, jusqu'à trouver le mot ou tomber sur `NULL`.

#solution
```c
int arbre_mots_memoire(ArbreMots* a) {
  if (a == NULL) {
    return 0;
  }
  return sizeof(ArbreMots) + strlen(a->mot) + 1
       + arbre_mots_memoire(a->mot_gauche)
       + arbre_mots_memoire(a->mot_droit);
}

int arbre_mots_rechercher(ArbreMots* a, char* mot) {
  while (a != NULL) {
    int c = strcmp(mot, a->mot);
    if (c == 0) {
      return 1;
    }
    a = c < 0 ? a->mot_gauche : a->mot_droit;
  }
  return 0;
}
```

La recherche est écrite avec une boucle : elle ne descend que d'un côté à chaque nœud, pas besoin de récursion. Testée sur l'échantillon : 492 mots trouvés sur 492, en 13,1 comparaisons en moyenne — comme la dichotomie.
:::

:::exo-question{label="5." cours="tar-insertion"}
Écris `arbre_mots_insérer`, `arbre_mots_supprimer` et `arbre_mots_free`, sans chercher à garder l'arbre équilibré.

#indice
Insérer : descends comme pour une recherche, et accroche le nouveau nœud au premier fils `NULL`. Supprimer : trois cas — une feuille, un nœud à un fils, un nœud à deux fils. Pour pouvoir modifier le pointeur qui mène au nœud supprimé (y compris la racine), manipule l'**adresse** de ce pointeur.

#solution
```c
int arbre_mots_inserer(ArbreMots* a, char* mot) {
  while (1) {
    int c = strcmp(mot, a->mot);
    if (c == 0) {
      return 0;  // déjà présent
    }
    ArbreMots** fils = c < 0 ? &a->mot_gauche : &a->mot_droit;
    if (*fils == NULL) {
      *fils = creer_noeud(mot);
      return 1;
    }
    a = *fils;
  }
}

int arbre_mots_supprimer(ArbreMots** racine, char* mot) {
  ArbreMots** p = racine;  // l'adresse du pointeur qui mène au nœud
  while (*p != NULL) {
    int c = strcmp(mot, (*p)->mot);
    if (c == 0) break;
    p = c < 0 ? &(*p)->mot_gauche : &(*p)->mot_droit;
  }
  ArbreMots* n = *p;
  if (n == NULL) {
    return 0;  // absent
  }
  if (n->mot_gauche && n->mot_droit) {
    // deux fils : on remplace le mot par le plus petit du sous-arbre droit
    ArbreMots** s = &n->mot_droit;
    while ((*s)->mot_gauche) {
      s = &(*s)->mot_gauche;
    }
    ArbreMots* successeur = *s;
    free(n->mot);
    n->mot = successeur->mot;
    *s = successeur->mot_droit;  // le successeur n'a pas de fils gauche
    free(successeur);
  } else {
    // zéro ou un fils : le fils (ou NULL) prend la place du nœud
    *p = n->mot_gauche ? n->mot_gauche : n->mot_droit;
    free(n->mot);
    free(n);
  }
  return 1;
}

void arbre_mots_free(ArbreMots* a) {
  if (a == NULL) return;
  arbre_mots_free(a->mot_gauche);  // postfixé : les fils avant le nœud
  arbre_mots_free(a->mot_droit);
  free(a->mot);
  free(a);
}
```

Deux écarts avec les signatures du sujet : `arbre_mots_supprimer` reçoit `ArbreMots**`, sans quoi elle ne pourrait pas supprimer la racine quand c'est une feuille ou qu'elle n'a qu'un fils ; et `arbre_mots_free` n'a pas besoin du `char*` que lui donne le sujet. Testées sur l'échantillon : après suppression des 492 mots, aucun n'est retrouvé et l'arbre reste ordonné ; après leur réinsertion, il est encore ordonné, mais sa hauteur est passée de 14 à 15.
:::

:::exo-question{label="6." cours="tar-insertion" bonne="c"}
Pour supprimer un mot dont le nœud a **deux fils**, par quoi le remplace-t-on pour que l'arbre reste un arbre de recherche ?

#a
Par son fils gauche, en raccrochant le fils droit à la racine.

#b
Par n'importe quelle feuille de l'arbre.

#c
Par le plus petit mot de son sous-arbre droit.

#d
Par le plus grand mot de son sous-arbre droit.

#indice
Le remplaçant doit être plus grand que tout le sous-arbre gauche et plus petit que tout le reste du sous-arbre droit.

Et il n'a pas de fils gauche, ce qui le rend facile à retirer. **c** est juste — le plus grand du sous-arbre **gauche** conviendrait aussi.

**Les distracteurs :** **a** casse l'ordre ou perd des nœuds ; **b** : une feuille quelconque n'a aucune raison d'être bien placée ; **d** est plus grand que les autres mots du sous-arbre droit, qui se retrouveraient à sa droite alors qu'ils lui sont inférieurs.

::::exercice{titre="Partie II — 2. Préfixes" theme="Comparer un nombre au lieu d'appeler strcmp, et ce qu'un uint16_t peut contenir"}
Pour chaque mot, on compare tous les caractères un par un afin de savoir s'ils sont identiques ou supérieurs ; il est possible d'accélérer cette opération. On crée une fonction `uint16_t prefixe(char*)` qui renvoie

$$
\ell_1 \times 126^3 + \ell_2 \times 126^2 + \ell_3 \times 126 + \ell_4
$$

où $\ell_1, \ell_2, \ell_3, \ell_4$ sont les codes des quatre premières lettres, on enregistre ce nombre dans chaque nœud, et l'on n'utilise `strcmp` que si les préfixes sont identiques. Puis on recommence avec un `uint64_t` et davantage de lettres. Rappel : un `uint16_t` contient les entiers de $0$ à $65\,535$, un `uint64_t` ceux de $0$ à $2^{64} - 1 \approx 1{,}8 \times 10^{19}$.

:::exo-question{label="1." cours="tar-prefixe" bonne="b"}
Pour le mot `abri` (codes 97, 98, 114, 105), la formule vaut $195\,606\,789$. Que contient le `uint16_t` renvoyé par `prefixe` ?

#a
$65\,535$, la plus grande valeur possible.

#b
$47\,365$, le reste de la division de $195\,606\,789$ par $65\,536$.

#c
$195\,606\,789$

#d
$0$, car le calcul déborde.

#indice
Un calcul sur des entiers non signés trop grand pour leur type ne s'arrête pas à la valeur maximale : il « fait le tour ».

#solution
Un entier non signé de 16 bits calcule **modulo $2^{16} = 65\,536$** : il ne garde que le reste. $195\,606\,789 = 2\,984 \times 65\,536 + 47\,365$ : le `uint16_t` contient **47 365** (vérifié en compilant). **b** est juste.

Et ce n'est pas un accident de ce mot : $126^3 = 2\,000\,376$ dépasse déjà $65\,535$ — la première lettre seule ne tient pas.

**Les distracteurs :** **a** suppose que le calcul sature, ce que ne font pas les entiers non signés en C ; **c** ne tient pas dans 16 bits ; **d** : le débordement donne un reste, pas zéro.
:::

:::exo-question{label="2." cours="tar-prefixe" bonne="b"}
Avec un `uint16_t`, si `prefixe(m1) < prefixe(m2)`, alors `m1` est avant `m2` dans l'ordre alphabétique.

#a
Vraie

#b
Fausse

#indice
Calcule (ou fais calculer) `prefixe("zinc")` et compare-le à `prefixe("abri")`.

#solution
**Fausse.** Le reste modulo $65\,536$ mélange l'ordre : `prefixe("zinc")` vaut $32\,347$ et `prefixe("abri")` vaut $47\,365$, alors que `zinc` est bien après `abri`. Sur le dictionnaire de test (17 072 mots triés), **195 couples de mots voisins** ont des préfixes 16 bits dans le mauvais ordre ; avec un `uint64_t`, aucun.

Conséquence : se fier au préfixe 16 bits pour choisir la gauche ou la droite fait descendre du mauvais côté, et la recherche **rate** des mots présents. Le préfixe ne peut servir qu'à tester l'**égalité** — et alors il n'apprend rien sur le côté où descendre. Aucun gain à attendre de cette version, et c'est la réponse à la question « Observez-vous un gain de performance ? ».
:::

:::exo-question{label="3." cours="tar-prefixe" bonne="a"}
Avec un préfixe **correct** (qui tient dans son type), pourquoi l'enregistrer dans chaque nœud peut-il accélérer la recherche ?

#a
On compare un entier rangé dans le nœud, sans aller lire la chaîne, rangée ailleurs dans la mémoire, tant que les préfixes diffèrent.

#b
Parce qu'un préfixe permet de sauter des niveaux de l'arbre.

#c
Parce que `strcmp` ne sait pas comparer des mots de plus de quatre lettres.

#d
Parce que l'arbre devient équilibré.

#indice
Où se trouve la chaîne d'un nœud par rapport au nœud lui-même ? Que coûte d'aller la lire ?

#solution
Le nœud ne contient qu'un **pointeur** vers son mot : `strcmp` doit aller lire la chaîne ailleurs dans la mémoire — un accès de plus, souvent hors du cache. Un préfixe **dans le nœud** se compare en une instruction ; on ne lit la chaîne que si les préfixes sont égaux (les mots commencent pareil). **a** est juste : c'est encore la localité du chapitre précédent.

**Les distracteurs :** **b** : on visite toujours un nœud par niveau ; **c** : `strcmp` compare des chaînes de toute longueur ; **d** : le préfixe ne change pas la forme de l'arbre.
:::

:::exo-question{label="4." cours="tar-prefixe" bonne="d"}
On passe à un `uint64_t`, en gardant la base 126 et en ajoutant des lettres. Combien de lettres au plus peut-on prendre en compte sans débordement ?

#a
$4$

#b
$8$

#c
$64$

#d
$9$

#indice
Avec $k$ lettres, le préfixe peut approcher $126^k$. Cherche le plus grand $k$ tel que $126^k < 2^{64} \approx 1{,}8 \times 10^{19}$.

#solution
$126^9 \approx 8{,}0 \times 10^{18} < 2^{64} \approx 1{,}8 \times 10^{19}$, mais $126^{10} \approx 1{,}0 \times 10^{21}$ dépasse : **9 lettres** au plus (vérifié par calcul exact). **d** est juste.

**Les distracteurs :** **a** est le nombre de lettres du sujet ; **b** compte 8 octets d'un `uint64_t` comme 8 lettres ; **c** confond les bits et les lettres.
:::

:::exo-question{label="5." cours="tar-prefixe"}
Écris `prefixe` sur un `uint64_t`, avec 9 lettres, en traitant les mots plus courts.

#indice
Calcule à la manière de Horner : `p = p * 126 + lettre`. Si le mot s'arrête avant 9 lettres, continue à multiplier par 126 pour que tous les préfixes aient le même nombre de « chiffres » — sans lire au-delà du zéro final.

#solution
```c
#include <stdint.h>

uint64_t prefixe(char* mot) {
  uint64_t p = 0;
  int i = 0;
  for (; i < 9 && mot[i] != '\0'; i++) {
    p = p * 126 + (unsigned char)mot[i];
  }
  for (; i < 9; i++) {
    p = p * 126;  // un mot court se complète par des « lettres » de code 0
  }
  return p;
}
```

Compléter par des zéros garde l'ordre : `abri` passe avant `abris`, comme dans le dictionnaire. Sur le dictionnaire de test, aucun couple de mots voisins n'est mal ordonné.

Une réserve : la base 126 suppose que chaque code de lettre est inférieur à 126. Les lettres accentuées d'un dictionnaire français, codées en UTF-8 sur plusieurs octets de code supérieur à 127 (et négatifs dans un `char` signé, d'où le `unsigned char`), sortent de ce cadre : elles peuvent fausser l'ordre comparé à celui de `strcmp`.
:::

::extrait-cours{id="tar-vecteur-mots" titre="Un vecteur de pointeurs" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_2-le-vecteur"}
Un vecteur de mots range dans ses cases des **adresses** de chaînes (`char**`) : chaque case occupe la taille d'un pointeur, 8 octets, et chaque `malloc` se calcule en `reserve * sizeof(char*)`. Les chaînes, elles, sont allouées à part : il faut les compter dans la mémoire et les libérer une à une.
::

::extrait-cours{id="tar-insertion-triee" titre="Insérer dans un vecteur trié" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_4-la-complexité-dune-opération"}
Insérer au milieu d'un vecteur décale tous les éléments suivants d'une case : dans le pire des cas (le plus petit mot), toute la liste, d'où une insertion **linéaire** — même si l'on trouve la place rapidement.
::

::extrait-cours{id="tar-dichotomie" titre="La recherche dichotomique" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_7-larbre-binaire-de-recherche"}
Dans une liste triée, on compare au mot du **milieu** et l'on ne garde que la moitié où il peut se trouver. Chaque comparaison divise par deux ce qui reste : au plus $\lceil \log_2(n+1) \rceil$ comparaisons, 20 pour un million de mots. C'est la complexité **logarithmique** de la recherche dans un ABR.
::

::extrait-cours{id="tar-charger" titre="Construire l'ABR d'une liste triée" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_7-larbre-binaire-de-recherche"}
L'élément du milieu devient la racine ; la moitié gauche de la liste forme le sous-arbre gauche, la moitié droite le sous-arbre droit, récursivement. L'arbre respecte l'ordre (plus petits à gauche, plus grands à droite) et sa hauteur est le plus grand $h$ tel que $2^h \le n$.
::

::extrait-cours{id="tar-recherche" titre="Chercher dans un ABR" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_7-larbre-binaire-de-recherche"}
À chaque nœud, on compare et l'on descend d'un seul côté, jusqu'à trouver la clé ou un fils absent : au plus la hauteur de l'arbre plus un nœuds visités, $\log_2(n)$ pour un arbre équilibré. Chaque nœud coûte ses pointeurs vers ses fils en plus de sa valeur.
::

::extrait-cours{id="tar-insertion" titre="Insérer et supprimer dans un ABR" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_8-insérer-supprimer-rééquilibrer"}
**Insérer** : descendre comme pour une recherche et accrocher la nouvelle feuille au premier fils absent. **Supprimer** : une feuille disparaît ; un nœud à un fils est remplacé par ce fils ; un nœud à deux fils prend la valeur du **plus petit de son sous-arbre droit**, qu'on retire à sa place. Sans rééquilibrage, l'arbre reste ordonné mais peut grandir en hauteur.
::

::extrait-cours{id="tar-prefixe" titre="Un préfixe numérique, et sa taille" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_9-les-limites-des-pointeurs-larbre-dans-un-tableau"}
Comparer un entier rangé dans le nœud évite d'aller lire la chaîne, rangée ailleurs : moins d'indirections, meilleure localité. Mais l'entier doit **tenir dans son type** : un `uint16_t` calcule modulo 65 536 et ne garde pas l'ordre ($126^3$ dépasse déjà 65 535) ; un `uint64_t` contient 9 lettres en base 126.
::
