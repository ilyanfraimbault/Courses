::rappel{titre="Ce que dit ce contrôle de ce qu'il faut savoir" icone="i-lucide-compass"}
Le sujet est donné **à but d'entraînement** ; il montre surtout ce qui est attendu :

- **les complexités** du comparatif vecteur / liste chaînée / arbre binaire de recherche, et ce qu'elles veulent dire (« varie selon $k$ », « varie selon $n$ ») ;
- **pile et file** : dérouler un programme qui empile et dépile ;
- **les arbres** : dessiner l'arbre construit par un code, écrire un parcours (infixé, en largeur), la hauteur d'un arbre complet ;
- **les tables de hachage** : adressage ouvert ou fermé, placer des clés avec un probing linéaire, supprimer avec des pierres tombales ;
- **choisir une structure** pour un problème de performance, et le justifier ;
- **retirer une récursion** avec sa propre pile.

Pour le code, on peut considérer que les structures vues en cours (vecteur, pile, file, liste chaînée, arbre, table de hachage) et leurs fonctions sont déjà écrites.

**Mode d'emploi.** Le QCM se coche (plusieurs réponses possibles, comme le jour du contrôle ; une question qui n'a qu'une bonne réponse se pose ici en choix simple) ; les sorties, les cases et les étapes s'écrivent dans des champs ; le code se rédige sur une feuille avant d'ouvrir la solution.
::

:::exo-question{label="1." cours="ctl-double"}
Une liste doublement chaînée est :

::cases-a-cocher
---
propositions:
  - Un type particulier de table de hachage.
  - Une liste de caractères.
  - Une structure contenant deux listes.
  - Une liste dans laquelle chaque élément contient deux liens vers le suivant.
  - Aucune de ces réponses.
bonnes: [5]
---
::

#indice
Que contient chaque nœud d'une liste doublement chaînée, en plus du lien vers le suivant ?

#solution
**Aucune** des quatre propositions du sujet n'est juste, et le corrigé du professeur n'en coche d'ailleurs aucune : chaque élément d'une liste doublement chaînée contient un lien vers le **suivant** et un lien vers le **précédent**. La cinquième case, « Aucune de ces réponses », n'est pas dans le sujet : elle est ajoutée ici parce qu'une question à cocher doit avoir au moins une bonne réponse.

- **1** : rien à voir avec une table de hachage ;
- **2** : une liste doublement chaînée peut contenir n'importe quel type de valeur ;
- **3** : c'est une seule liste, parcourable dans les deux sens ;
- **4** : le piège — deux liens, oui, mais l'un vers le suivant, l'autre vers le **précédent**.
:::

:::exo-question{label="2." cours="ctl-abr"}
Dans un arbre binaire de recherche :

::cases-a-cocher
---
propositions:
  - La valeur d'un nœud est inférieure à celle du nœud parent.
  - La valeur du nœud parent est comprise entre celle du nœud gauche et celle du nœud droit.
  - Chaque nœud a deux fils.
  - L'arbre est complet.
bonnes: [2, 4]
---
::

#indice
Rappelle-toi les deux conditions de la définition du cours : une relation d'ordre, et une forme d'arbre.

#solution
**2 et 4**, d'après la définition du cours : un ABR est un arbre **complet** dont chaque nœud est **plus grand que tout son sous-arbre gauche et plus petit que tout son sous-arbre droit** — en particulier, sa valeur est comprise entre celles de ses deux fils.

- **1** est faux : le fils **droit** est plus grand que son parent ;
- **3** est faux : les feuilles n'ont aucun fils, et un arbre complet peut avoir au dernier niveau un nœud avec un seul fils (à gauche).

Attention : exiger que l'arbre soit **complet** est la définition **du professeur**, qui garantit la recherche en $\log_2(n)$. Ailleurs, on appelle souvent « arbre binaire de recherche » tout arbre qui respecte l'ordre, équilibré ou non — c'est d'ailleurs ce que construit le TP quand il insère « sans préserver l'équilibre ». Pour ce contrôle, suis la définition du cours.
:::

:::exo-question{label="3." cours="ctl-file"}
Si on insère les éléments 3, 2 puis 1 dans une file `f` :

::cases-a-cocher
---
propositions:
  - '`defiler(f)` renverra l''élément 3.'
  - Enfiler un élément ne changera pas le résultat du prochain appel à la fonction défiler.
  - Je peux défiler trois fois sans causer d'erreurs dans mon programme.
bonnes: [1, 2, 3]
---
::

#indice
Premier entré, premier sorti. Et un élément enfilé maintenant passe derrière les trois autres.

#solution
**Les trois.**

1. Le premier entré, **3**, sort le premier.
2. Un élément enfilé se place **à la fin** de la file : le prochain `defiler` rend toujours 3.
3. La file contient trois éléments : on peut défiler trois fois (3, puis 2, puis 1) ; c'est la quatrième fois qui poserait problème.
:::

:::exo-question{label="4." cours="ctl-acces-k" bonne="c"}
Le nombre d'opérations requises pour accéder à l'élément en position $k$ d'une liste simplement chaînée :

#a
Varie selon la taille de la liste

#b
Est constant

#c
Varie selon $k$

#indice
On part du début et l'on suit les liens. Jusqu'où ?

#solution
On part du premier nœud et l'on suit $k$ liens : le coût **varie selon $k$**. **c** est juste.

**Les distracteurs :** **a** : les nœuds situés après la position $k$ ne sont jamais visités, la taille de la liste n'intervient pas ; **b** décrit l'accès dans un vecteur, où l'adresse se calcule.
:::

:::exo-question{label="5." cours="ctl-acces-k" bonne="c"}
Le nombre d'opérations requises pour retirer l'élément en position $k$ d'une liste chaînée de taille $n$ :

#a
Varie selon $n$

#b
Est constant

#c
Varie selon $k$

#indice
Le retrait lui-même change deux pointeurs. Mais il faut d'abord atteindre le nœud qui précède la position $k$.

#solution
Il faut **atteindre** la position $k$ en suivant $k$ liens, puis changer un pointeur et libérer le nœud : le coût **varie selon $k$**, comme dans le corrigé. **c** est juste.

**Les distracteurs :** **a** : contrairement au vecteur, rien n'est décalé après la position $k$, la suite de la liste n'est pas parcourue ; **b** n'est vrai que si l'on tient déjà le nœud précédent.
:::

:::exo-question{label="6." cours="ctl-vecteur" bonne="a"}
Le nombre d'opérations requises pour accéder au dernier élément d'un tableau de taille $n$ :

#a
Est constant

#b
Varie selon $n$

#indice
Comment calcule-t-on l'adresse de la case $n - 1$ ?

#solution
L'adresse de la dernière case se calcule en **une addition** (`t + n - 1`), quelle que soit la taille : **constant**. **a** est juste.

**Le distracteur :** **b** confond le tableau avec une liste simplement chaînée, où il faut parcourir toute la liste pour atteindre la fin.
:::

:::exo-question{label="7." cours="ctl-vecteur" bonne="b"}
Dans le pire des cas, le nombre d'opérations requises pour insérer un élément dans un tableau de taille $n$ :

#a
Est constant

#b
Varie selon $n$

#indice
Pense au pire des cas : une insertion au début, ou une réserve pleine.

#solution
Dans le pire des cas, il faut **décaler** tous les éléments (insertion au début) ou **recopier** tout le tableau dans un emplacement plus grand (réserve pleine) : jusqu'à $n$ opérations. **b** est juste.

**Le distracteur :** **a** est le coût **amorti** d'un ajout à la fin d'un vecteur, pas le coût dans le pire des cas.
:::

:::exo-question{label="8." cours="ctl-abr" bonne="b"}
Le nombre d'opérations requises pour rechercher un élément dans un arbre binaire de recherche contenant $n$ nœuds :

#a
Est constant en moyenne

#b
Augmente proportionnellement au logarithme du nombre d'éléments

#c
Augmente proportionnellement au nombre d'éléments ajoutés

#d
Augmente proportionnellement au carré du nombre d'éléments ajoutés

#indice
À chaque comparaison, on descend d'un niveau. Combien de niveaux compte un arbre complet de $n$ nœuds ?

#solution
Chaque comparaison descend d'un niveau, et un arbre complet de $n$ nœuds a au plus $\log_2(n)$ niveaux sous la racine : la recherche est **logarithmique**. **b** est juste — dix milliards de nœuds, une trentaine de comparaisons.

**Les distracteurs :** **a** est la promesse d'une table de hachage sans collisions ; **c** est la recherche dans une liste ou un arbre dégénéré ; **d** ne correspond à aucune structure du cours.
:::

:::exo-question{label="9." cours="ctl-complet" bonne="a"}
Un arbre binaire complet contenant 57 nœuds sera de hauteur :

#a
$5$

#b
$6$

#c
$7$

#d
$8$

#indice
La hauteur est le niveau maximal, la racine étant au niveau 0. Combien de nœuds tiennent sur les niveaux 0 à $h$ ?

#solution
Les niveaux 0 à 4 remplis contiennent $1 + 2 + 4 + 8 + 16 = 31$ nœuds, les niveaux 0 à 5 en contiennent $63$. Avec 57 nœuds, le niveau 5 est commencé mais pas le niveau 6 : la hauteur est $\boxed{5}$, car $2^5 \le 57 < 2^6$. **a** est juste.

**Les distracteurs :** **b** compte les niveaux (6 : de 0 à 5) au lieu du niveau maximal ; **c** et **d** surestiment.
:::

:::exo-question{label="10." cours="ctl-adressage" bonne="b"}
La table de hachage suivante range les clés d'après la position de leur première lettre dans l'alphabet, `(key[0] - 'a') % 8` :

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Contenu | alice → ahmed → asha | bob | | | eric → elise | | | |

#a
La table utilise un adressage ouvert.

#b
La table utilise un adressage fermé.

#indice
Les clés en collision sont-elles rangées dans d'autres cases du tableau, ou ailleurs ?

#solution
`ahmed` et `asha` ont le même hachage qu'`alice` (case 0), `elise` le même qu'`eric` (case 4) : les collisions sont **accumulées dans une structure à part** — ici une liste chaînée accrochée à la case. C'est l'**adressage fermé**. **b** est juste.

**Le distracteur :** **a** : en adressage ouvert, `ahmed` aurait été rangé dans une **autre case** du tableau.
:::

:::exo-question{label="11." cours="ctl-hachage" bonne="a"}
Dans la même table, qui range les clés en case `(key[0] - 'a') % 8` :

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Contenu | alice → ahmed → asha | bob | | | eric → elise | | | |

dans quelle case sera inséré le prénom « hanna » ?

#a
$7$

#b
$0$

#c
$3$

#d
$5$

#indice
Calcule `'h' - 'a'`. Vérifie ta méthode sur `alice` et `eric`.

#solution
`'a' - 'a'` vaut 0 (alice en case 0), `'e' - 'a'` vaut 4 (eric en case 4) : la position commence à **0**. `h` est la huitième lettre, donc `'h' - 'a'` vaut **7**, et $7 \% 8 = 7$ : hanna va en case $\boxed{7}$. **a** est juste.

**Le corrigé du professeur se trompe ici** : il donne la case 0, « h est la huitième lettre de l'alphabet » — c'est vrai, mais la huitième lettre est à la position 7 en partant de 0 ; il aurait fallu `('h' - 'a' + 1) % 8` pour tomber en 0, et alice serait alors en case 1. Le corrigé remplace aussi la proposition a) du sujet (7) par 6.

**Les distracteurs :** **b** est l'erreur du corrigé (compter `h` comme 8) ; **c** et **d** ne correspondent à aucun calcul sur la lettre `h`.
:::

::::exercice{titre="Exercice 1 — La pile" theme="Dérouler une boucle qui dépile et rempile"}
Le code suivant utilise une pile `p` dans laquelle ont été empilés les nombres 1, 2, 2, 6, 6, 3, 2, **dans cet ordre** (en commençant par empiler le nombre 1 et en terminant par empiler le nombre 2).

```c
int a = 0;
while (a != 6){
  a = depiler(p);
  if (a == 6){
    empiler(p, 2);
  }
  printf("%d\n", a);
}
```

:::exo-question{label="a)" cours="ctl-pile"}
Qu'affichera le programme dans la console à l'exécution ?

::champs-reponse
---
champs:
  - libelle: Les nombres affichés, dans l'ordre
    attendu: '2 3 6'
    aide: un nombre par ligne, séparés par des espaces
---
::

#indice
Le sommet est le dernier nombre empilé. Dépile un par un, et arrête-toi dès que `a` vaut 6 — après l'affichage.

#solution
La pile vaut, sommet à droite, `1 2 2 6 6 3 2`.

| Tour | `depiler` | `a == 6` ? | Pile après | Affiche |
|---|---|---|---|---|
| 1 | 2 | non | 1 2 2 6 6 3 | 2 |
| 2 | 3 | non | 1 2 2 6 6 | 3 |
| 3 | 6 | oui : `empiler(p, 2)` | 1 2 2 6 2 | 6 |

Après le troisième tour, `a` vaut 6 et la boucle s'arrête. Le programme affiche $\boxed{2,\ 3,\ 6}$, un nombre par ligne.
:::

:::exo-question{label="b)" cours="ctl-pile"}
Que reste-t-il dans la pile après exécution du programme ?

::champs-reponse
---
champs:
  - libelle: La pile, du fond au sommet
    attendu: ['1 2 2 6 2', '1, 2, 2, 6, 2']
---
::

#indice
Reprends le tableau de la question précédente : qu'a-t-on empilé au dernier tour ?

#solution
On a retiré 2, 3 et 6, puis empilé 2 au dernier tour : il reste, du fond au sommet, $\boxed{1,\ 2,\ 2,\ 6,\ 2}$ — le deuxième 6, que la boucle n'a pas atteint, se retrouve sous le 2 rempilé.
:::

::::exercice{titre="Exercice 2 — L'arbre d'une expression" theme="Construire un arbre, parcours infixé, parcours en largeur"}
Soit le code suivant :

```c
arbre* g = creer_arbre('+');
g->fils_gauche = creer_arbre('4');
g->fils_droit = creer_arbre('6');
arbre* d = creer_arbre('-');
d->fils_gauche = creer_arbre('7');
d->fils_droit = creer_arbre('1');
arbre* a = creer_arbre('*');
a->fils_gauche = g;
a->fils_droit = d;
```

:::exo-question{label="a)" cours="ctl-arbre"}
Dessine un schéma de l'arbre produit par ce code, puis complète :

::champs-reponse
---
champs:
  - libelle: Racine
    attendu: '*'
  - libelle: Fils gauche de la racine
    attendu: '+'
  - libelle: Fils droit de la racine
    attendu: ['-', '−']
  - libelle: Fils de « + », gauche puis droit
    attendu: '4 6'
  - libelle: Fils de « − », gauche puis droit
    attendu: '7 1'
---
::

#indice
Le dernier arbre créé, `a`, reçoit `g` et `d` comme fils : c'est lui la racine.

#solution
`g` est le sous-arbre `+` (fils 4 et 6), `d` le sous-arbre `−` (fils 7 et 1), et `a`, créé en dernier, les prend pour fils gauche et droit :

```text
          *
        /   \
       +     -
      / \   / \
     4   6 7   1
```

C'est l'arbre de l'expression $(4 + 6) \times (7 - 1)$.
:::

:::exo-question{label="b)" cours="ctl-parcours"}
Qu'afficherait dans la console un programme qui effectuerait un **parcours en profondeur infixé** de l'arbre pour afficher la valeur des nœuds ?

::champs-reponse
---
champs:
  - libelle: Affichage
    attendu: '4+6*7-1'
---
::

#indice
Infixé : le sous-arbre gauche, puis le nœud, puis le sous-arbre droit — à chaque niveau.

#solution
Infixé à la racine : tout le sous-arbre gauche (`4 + 6`, lui-même en infixé), puis `*`, puis tout le sous-arbre droit (`7 - 1`). L'affichage est $\boxed{4+6*7-1}$.

Les parenthèses ont disparu : lu ainsi, $4 + 6 \times 7 - 1$ vaudrait $45$, alors que l'arbre calcule $(4+6) \times (7-1) = 60$. Pour afficher une expression fidèle, un parcours infixé doit écrire une parenthèse ouvrante avant chaque sous-arbre et une fermante après.
:::

:::exo-question{label="c)" cours="ctl-largeur"}
Écris le code d'un **parcours en largeur** qui affichera les nœuds de cet arbre.

#indice
Le parcours en profondeur utilise une pile ; le parcours en largeur la remplace par une **file**. Enfile la racine, puis, tant que la file n'est pas vide : défile un nœud, affiche-le, enfile ses fils.

#solution
La correction du professeur :

```c
void parcours_largeur(Noeud* n){
  File* f = creer_file();
  enfiler(f, n);
  while (taille(f)){
    Noeud* suivant = defiler(f);
    if (suivant != 0){
      enfiler(f, suivant->noeud_gauche);
      enfiler(f, suivant->noeud_droit);
      printf("%c\n", suivant->valeur);
    }
  }
  free_file(f);
}
```

Les fils absents des feuilles (des pointeurs nuls) sont enfilés aussi, puis ignorés au défilement grâce au test `suivant != 0`. La file rend les nœuds **niveau par niveau** : le programme affiche `*`, `+`, `-`, `4`, `6`, `7`, `1`.
:::

::::exercice{titre="Exercice 3 — Table de hachage à probing linéaire" theme="Insertion par probing linéaire, pierres tombales, recherche"}
Ci-dessous le schéma d'une table de hachage de 9 cases utilisant :

- **le nombre de lettres modulo 9** comme fonction de hachage ;
- un **probing linéaire ($N = 2$)** pour résoudre les collisions : si la case $h$ est occupée, on essaie $h + 2$, puis $h + 4$, etc., modulo 9.

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| Contenu | | | | | Ales | Jeudi | | Lundi | |

:::exo-question{label="a)" cours="ctl-probing"}
On insère, dans cet ordre, `Mercredi`, `Mardi`, `Dimanche`, puis `Nimes`. Dans quelle case va chacune ?

::champs-reponse
---
champs:
  - libelle: Case de Mercredi
    attendu: '8'
  - libelle: Case de Mardi
    attendu: '0'
  - libelle: Case de Dimanche
    attendu: '1'
  - libelle: Case de Nimes
    attendu: '2'
---
::

#indice
Compte les lettres, prends le reste par 9, et si la case est prise, avance de 2 en 2 — en revenant à 0 après 8.

#solution
- `Mercredi` : 8 lettres → case **8**, libre.
- `Mardi` : 5 lettres → 5 (Jeudi), 7 (Lundi), $9 \% 9 = 0$ → case **0**.
- `Dimanche` : 8 lettres → 8 (Mercredi), $10 \% 9 = 1$ → case **1**.
- `Nimes` : 5 lettres → 5, 7, 0 (Mardi), $11 \% 9 = 2$ → case **2**.

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| Contenu | Mardi | Dimanche | Nimes | | Ales | Jeudi | | Lundi | Mercredi |
:::

:::exo-question{label="b)" cours="ctl-tombale"}
On supprime ensuite les clés `Lundi` puis `Jeudi`. Quelles cases portent alors une **pierre tombale** ?

::cases-a-cocher
---
propositions:
  - Case 0
  - Case 1
  - Case 2
  - Case 3
  - Case 4
  - Case 5
  - Case 6
  - Case 7
  - Case 8
bonnes: [6, 8]
---
::

#indice
On ne vide pas une case supprimée : on y laisse une marque, pour ne pas briser les chaînes de recherche des clés rangées plus loin.

#solution
`Jeudi` était en case **5**, `Lundi` en case **7** : on y laisse une **pierre tombale**, qui dit « une clé était là, continue à chercher ».

| Case | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| Contenu | Mardi | Dimanche | Nimes | | Ales | † | | † | Mercredi |

Si l'on vidait simplement ces cases, la recherche de `Mardi` (5 lettres) tomberait sur une case 5 vide et conclurait, à tort, que `Mardi` n'est pas dans la table.
:::

:::exo-question{label="c)" cours="ctl-tombale" bonne="d"}
Combien de cases faut-il examiner afin de trouver l'élément `Mardi` ?

#a
$1$

#b
$2$

#c
$5$

#d
$3$

#indice
`Mardi` a 5 lettres. Suis la même séquence de cases qu'à l'insertion, sans t'arrêter sur une pierre tombale.

#solution
La recherche suit les cases 5, 7, 0 : la **première pierre tombale** (case 5), la **seconde** (case 7), puis `Mardi` (case 0). Il faut examiner $\boxed{3}$ cases. **d** est juste.

**Les distracteurs :** **a** suppose que `Mardi` est dans sa case idéale ; **b** oublie une des pierres tombales ; **c** compte toutes les cases jusqu'à la case 0 dans l'ordre 4, 5, 6, 7, 8… au lieu de sauter de 2 en 2.
:::

:::exo-question{label="d)" cours="ctl-tombale" bonne="a"}
Quelle opération pourrait-on alors effectuer afin d'améliorer les performances de la table pour les prochaines recherches ?

#a
Retirer les pierres tombales en recalculant le hachage de tous les éléments et en les réinsérant (ou agrandir la table).

#b
Remplacer les pierres tombales par des cases vides, sans rien déplacer.

#c
Trier les éléments de la table par ordre alphabétique.

#d
Passer le pas du probing de 2 à 1, sans réinsérer les éléments.

#indice
Les pierres tombales allongent les chaînes de recherche. Comment s'en débarrasser sans perdre de clé ?

#solution
On **nettoie** la table : on retire les pierres tombales et l'on **recalcule la position de tous les éléments** en les réinsérant — ou l'on agrandit la table, ce qui oblige aussi à tout réinsérer. Après réinsertion, `Mardi` irait en case 5 et serait trouvé en une seule case. **a** est juste.

Le professeur note qu'ici on pourrait aussi simplement **déplacer `Mardi` dans la première pierre tombale** rencontrée sur son chemin, la case 5.

**Les distracteurs :** **b** rend `Mardi` et `Nimes` introuvables : leur chaîne de recherche passe par la case 5, qui serait vide ; **c** : une table de hachage ne range pas ses clés dans l'ordre ; **d** change le chemin de recherche sans déplacer les clés : on ne les retrouverait plus.
:::

::::exercice{titre="Exercice 4 — Les commandes des utilisateurs" theme="Choisir une structure de données pour accélérer un parcours"}
Un site de vente en ligne enregistre une liste d'utilisateurs dans une **liste chaînée**. La fonction ci-dessous parcourt les utilisateurs et compte le nombre total de commandes effectuées :

```c
int total_commandes(LinkedList* liste_users) {
  int total = 0;
  for (Node* n = liste_users->start; n != liste_users->end; n = n->next){
    total += n->user->commandes->taille;
  }
  return total;
}
```

Cette fonction prend trop de temps à s'exécuter.

:::exo-question{label="a)" cours="ctl-localite" bonne="c"}
Quelle structure de données proposer à la place de la liste chaînée ?

#a
Une liste doublement chaînée

#b
Un arbre binaire de recherche

#c
Un tableau (vecteur)

#d
Une table de hachage

#indice
La fonction fait un parcours complet, du premier au dernier utilisateur. Qu'est-ce qui ralentit un tel parcours dans une liste chaînée ?

#solution
Le parcours est **linéaire quoi qu'on fasse** : il faut visiter tous les utilisateurs. Ce qui coûte, c'est de sauter d'un nœud à l'autre dans la mémoire. Un **tableau / vecteur** range les utilisateurs **à la suite** : **c** est juste. Une liste déroulée fonctionnerait aussi, note le professeur.

**Les distracteurs :** **a** ajoute un pointeur sans rien changer à la dispersion des nœuds ; **b** et **d** accélèrent la **recherche** d'un élément, pas le parcours de tous.
:::

:::exo-question{label="a bis)" cours="ctl-localite"}
Quels sont les avantages de ce choix pour cette fonction ?

::cases-a-cocher
---
propositions:
  - Les éléments sont à la suite dans la mémoire, donc plus faciles à mettre en cache.
  - Le prochain élément à lire est facile à prévoir et à précharger.
  - On n'enregistre plus un pointeur avec chaque élément.
  - Le parcours devient logarithmique.
  - Le total des commandes est calculé sans lire chaque utilisateur.
bonnes: [1, 2, 3]
---
::

#indice
Les avantages sont ceux des limites de la liste chaînée, retournées. La complexité, elle, ne change pas.

#solution
**1, 2 et 3**, la réponse du professeur : localité (le cache se remplit d'utilisateurs voisins), prédiction (le processeur précharge la suite), et plus de pointeur `next` par élément — même si, note le professeur, ce pointeur est négligeable devant la taille d'un utilisateur.

**4** et **5** sont faux : il faut toujours lire les $n$ utilisateurs, le parcours reste **linéaire** ; on gagne sur la constante, pas sur la complexité.

Le professeur ajoute deux remarques : `commandes->taille` déréférence encore un pointeur par utilisateur, ce qui réduit le gain ; et pour parcourir très vite, on pourrait garder à part **un tableau des nombres de commandes**, sans aucun pointeur dans la boucle.
:::

:::exo-question{label="b)" cours="ctl-localite"}
Écris le code mis à jour de cette fonction.

#indice
Le vecteur a une longueur et un tableau d'utilisateurs : une boucle `for` sur les indices remplace la boucle sur les nœuds.

#solution
La correction du professeur, avec un vecteur d'utilisateurs (`len` éléments rangés dans `tab`) :

```c
int total_commandes(Vector liste_users) {
  int total = 0;
  for (int i = 0; i < liste_users.len; i++){
    total += liste_users.tab[i].commandes->taille;
  }
  return total;
}
```

Les utilisateurs sont lus dans l'ordre de la mémoire : plus de saut d'un nœud à l'autre.
:::

::::exercice{titre="Exercice 5 — Les tours de Hanoï" theme="Dérouler une récursion, puis la retirer avec sa propre pile"}
Ci-dessous le code d'une fonction qui affiche les étapes à réaliser afin de résoudre un problème de logique, les tours de Hanoï :

```c
void tours_de_hanoi(int n, char depart, char fin, char milieu) {
  if (n == 1) { // s'il n'y a qu'un disque on le déplace directement
    printf("Déplacer un disque de la pile %c à la pile %c\n", depart, fin);
  } else { // sinon on effectue la stratégie suivante
    // on déplace n-1 disques du départ vers le milieu
    tours_de_hanoi(n - 1, depart, milieu, fin);
    // on déplace un disque du départ vers la fin
    tours_de_hanoi(1, depart, fin, milieu);
    // on déplace n-1 disques du milieu vers la fin
    tours_de_hanoi(n - 1, milieu, fin, depart);
  }
}
```

:::exo-question{label="a)" cours="ctl-recursion"}
Que va afficher cette fonction si elle est appelée avec les paramètres `3 A C B` ? Pour chaque étape, écris la pile de départ puis la pile d'arrivée (par exemple `A C`).

::champs-reponse
---
champs:
  - libelle: Étape 1
    attendu: ['A C', 'A→C', 'A->C', 'A à C']
    aide: A C
  - libelle: Étape 2
    attendu: ['A B', 'A→B', 'A->B', 'A à B']
  - libelle: Étape 3
    attendu: ['C B', 'C→B', 'C->B', 'C à B']
  - libelle: Étape 4
    attendu: ['A C', 'A→C', 'A->C', 'A à C']
  - libelle: Étape 5
    attendu: ['B A', 'B→A', 'B->A', 'B à A']
  - libelle: Étape 6
    attendu: ['B C', 'B→C', 'B->C', 'B à C']
  - libelle: Étape 7
    attendu: ['A C', 'A→C', 'A->C', 'A à C']
---
::

#indice
Écris sur un brouillon l'arbre des appels : `(3, A, C, B)` appelle `(2, A, B, C)`, puis `(1, A, C, B)`, puis `(2, B, C, A)`. Développe chaque appel à 2 disques de la même façon : seuls les appels à 1 disque affichent.

#solution
L'arbre des appels, en ne gardant que les paramètres (`n`, départ, fin, milieu) :

```text
(3, A, C, B)
├── (2, A, B, C)
│   ├── (1, A, C, B)   → A vers C
│   ├── (1, A, B, C)   → A vers B
│   └── (1, C, B, A)   → C vers B
├── (1, A, C, B)       → A vers C
└── (2, B, C, A)
    ├── (1, B, A, C)   → B vers A
    ├── (1, B, C, A)   → B vers C
    └── (1, A, C, B)   → A vers C
```

La fonction affiche, dans l'ordre :

```text
Déplacer un disque de la pile A à la pile C
Déplacer un disque de la pile A à la pile B
Déplacer un disque de la pile C à la pile B
Déplacer un disque de la pile A à la pile C
Déplacer un disque de la pile B à la pile A
Déplacer un disque de la pile B à la pile C
Déplacer un disque de la pile A à la pile C
```

Sept étapes, $2^3 - 1$ — résultat vérifié en exécutant le code, et identique à la correction du professeur.
:::

:::exo-question{label="b)" cours="ctl-recursion"}
Écris le code d'une fonction affichant les mêmes étapes **sans utiliser de récursion**. Tu peux considérer que les structures de données vues en cours et leurs fonctions sont déjà implémentées.

#indice
Remplace la pile d'appels par **ta propre pile**, sur le tas, qui contient des **sous-objectifs** : « déplacer $n$ disques de tel départ vers telle fin ». Les sous-objectifs sont réalisés dans l'ordre **inverse** de celui où on les empile : empile donc la troisième étape en premier.

#solution
La correction du professeur. On empile des **objectifs**, réalisés dans l'ordre inverse de leur empilement :

```c
typedef struct Objectif {
  int n;
  char depart;
  char fin;
  char milieu;
} Objectif;

Objectif cree_objectif(int n, char depart, char fin, char milieu) {
  Objectif o = {
    .n = n,
    .depart = depart,
    .fin = fin,
    .milieu = milieu,
  };
  return o;
}

void tours_de_hanoi(Objectif depart) {
  Pile* p = creer_pile();
  empiler(p, depart);
  while (taille(p) > 0){
    Objectif courant = depiler(p);
    if (courant.n == 1) {
      printf("Déplacer un disque de la pile %c à la pile %c\n", courant.depart, courant.fin);
    } else {
      // 3. on déplace n-1 disques du milieu vers la fin
      empiler(p, cree_objectif(courant.n - 1, courant.milieu, courant.fin, courant.depart));
      // 2. on déplace un disque du départ vers la fin
      empiler(p, cree_objectif(1, courant.depart, courant.fin, 0));
      // 1. on déplace d'abord n-1 disques du départ vers le milieu
      empiler(p, cree_objectif(courant.n - 1, courant.depart, courant.milieu, courant.fin));
    }
  }
}
```

L'appel `tours_de_hanoi(cree_objectif(3, 'A', 'C', 'B'))` affiche les sept mêmes étapes, dans le même ordre — vérifié en compilant avec une pile d'objectifs. La pile est sur le **tas** : elle peut contenir bien plus d'objectifs que la pile d'appels, de taille limitée. Il manque seulement, à la fin, la libération de la pile.
:::

::extrait-cours{id="ctl-double" titre="La liste doublement chaînée" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_9-la-liste-doublement-chaînée"}
Chaque élément contient un lien vers le **suivant** et un lien vers le **précédent** ; on garde deux sentinelles. On parcourt dans les deux sens, et l'on insère et supprime à la fin en temps constant, au prix de deux fois plus de pointeurs.
::

::extrait-cours{id="ctl-abr" titre="L'arbre binaire de recherche" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_7-larbre-binaire-de-recherche"}
Dans la définition du cours, un **arbre binaire de recherche** est un arbre **complet** dont les valeurs respectent l'ordre : tout le sous-arbre gauche est plus petit que le père, tout le sous-arbre droit plus grand. La recherche d'une clé demande au plus $\log_2(n)$ comparaisons : **complexité logarithmique**. L'affichage trié (parcours infixé) est linéaire.
::

::extrait-cours{id="ctl-file" titre="La file" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_13-la-file"}
`enfiler` ajoute **à la fin**, `defiler` retire **au début** : le premier entré sort le premier (FIFO). Enfiler ne change donc pas le résultat du prochain `defiler`.
::

::extrait-cours{id="ctl-acces-k" titre="La position k d'une liste chaînée" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_10-vecteur-ou-liste-chaînée-le-comparatif"}
Dans une liste chaînée, on ne calcule pas l'adresse du nœud $k$ : on la trouve en suivant $k$ liens depuis le début. Accéder à la position $k$, ou y retirer un élément, **varie selon $k$** ; la suite de la liste n'est pas parcourue. Retirer un nœud qu'on tient déjà est constant.
::

::extrait-cours{id="ctl-vecteur" titre="Accès et insertion dans un tableau" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_4-la-complexité-dune-opération"}
L'accès à n'importe quelle case d'un tableau est **constant** : une addition sur l'adresse. L'insertion est **linéaire dans le pire des cas** : décaler tous les éléments, ou tout recopier quand la réserve est pleine.
::

::extrait-cours{id="ctl-complet" titre="L'arbre complet et sa hauteur" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_6-larbre-complet"}
Un arbre binaire est **complet** quand tous ses niveaux sont remplis sauf le dernier, dont les nœuds sont à gauche. La **hauteur** est le niveau maximal (la racine est au niveau 0). Les niveaux 0 à $h$ contiennent au plus $2^{h+1} - 1$ nœuds : un arbre complet de $n$ nœuds a pour hauteur $h$ tel que $2^h \le n < 2^{h+1}$.
::

::extrait-cours{id="ctl-adressage" titre="Adressage ouvert et adressage fermé" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_2-les-collisions-et-les-deux-adressages"}
Deux façons de gérer les collisions : l'**adressage fermé** range les clés en collision dans une **structure à part** accrochée à la case (un seau : liste chaînée, vecteur, arbre) ; l'**adressage ouvert** range toutes les clés **dans le tableau**, en cherchant une autre case quand la sienne est prise.
::

::extrait-cours{id="ctl-hachage" titre="La fonction de hachage" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_1-la-table-de-hachage"}
Une table de hachage range chaque clé dans la case du tableau donnée par la **fonction de hachage**. Avec `(key[0] - 'a') % 8`, la lettre `a` donne 0, `b` donne 1… : la position d'une lettre se compte **à partir de 0**.
::

::extrait-cours{id="ctl-pile" titre="La pile" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_12-la-pile"}
`empiler` pose un élément au sommet, `depiler` retire le sommet : le dernier entré sort le premier (LIFO). Pour dérouler un programme, écris la pile de gauche à droite, sommet à droite.
::

::extrait-cours{id="ctl-arbre" titre="L'arbre binaire et ses fils" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_3-implémenter-un-arbre-larbre-binaire"}
Un nœud d'arbre binaire porte une valeur et deux pointeurs, vers son fils **gauche** et son fils **droit**. Le nœud qui n'a pas de parent est la **racine** ; ceux qui n'ont pas de fils sont les **feuilles**.
::

::extrait-cours{id="ctl-parcours" titre="Les parcours en profondeur" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_4-les-parcours-récursifs"}
**Préfixé** : le nœud, puis le sous-arbre gauche, puis le droit. **Infixé** : le gauche, le nœud, le droit. **Postfixé** : le gauche, le droit, puis le nœud. On applique la règle à chaque sous-arbre.
::

::extrait-cours{id="ctl-largeur" titre="Le parcours en largeur" source="/cours/a1/structures-donnees-algorithmique/arbres/cours#_5-en-profondeur-en-largeur"}
On parcourt tous les nœuds d'un niveau avant ceux du niveau suivant : on remplace la pile du parcours en profondeur par une **file**. On enfile la racine ; tant que la file n'est pas vide, on défile un nœud, on le traite et on enfile ses fils.
::

::extrait-cours{id="ctl-probing" titre="Le probing linéaire" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_4-ladressage-ouvert-et-le-probing"}
En adressage ouvert, si la case `hash(key)` est prise, on essaie `hash(key) + N`, puis `hash(key) + 2N`, etc., **modulo la taille du tableau** : c'est le probing **linéaire** de pas $N$.
::

::extrait-cours{id="ctl-tombale" titre="Recherche et pierre tombale" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_6-rechercher-et-supprimer-la-pierre-tombale"}
Pour chercher, on suit les mêmes cases qu'à l'insertion, jusqu'à trouver la clé ou une case **vide**. Pour supprimer, on laisse une **pierre tombale** (*tombstone*), qui ne brise pas les chaînes de recherche. Quand elles s'accumulent, on **nettoie** la table : on retire les pierres tombales et l'on réinsère tous les éléments (ou l'on agrandit la table).
::

::extrait-cours{id="ctl-localite" titre="Les limites de la liste chaînée" source="/cours/a1/structures-donnees-algorithmique/listes/cours#_8-les-limites-de-la-liste-chaînée"}
Parcourir une liste chaînée est linéaire, comme parcourir un vecteur, mais bien plus lent : nœuds dispersés (**localité** et cache), **prédiction** difficile, un **pointeur** de plus par élément, une indirection à chaque pas. Pour un parcours complet, un vecteur ou une liste déroulée fait mieux.
::

::extrait-cours{id="ctl-recursion" titre="Retirer une récursion avec sa propre pile" source="/cours/a1/structures-donnees-algorithmique/tables-de-hachage-et-recursion/cours#_10-parcourir-un-arbre-sans-récursion"}
Chaque appel récursif occupe de la place dans la **pile d'appels**, de taille limitée. Pour s'en passer, on empile soi-même, dans une pile sur le **tas**, ce qu'il reste à faire, et l'on boucle tant que la pile n'est pas vide. Les tâches empilées sortent dans l'ordre **inverse** : on empile la dernière étape en premier.
::
