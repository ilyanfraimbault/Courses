| Instruction | Ce qu'elle fait |
|---|---|
| `RUN commande` | exécute une commande pendant la construction — **une couche** de plus |
| `CMD ["./cmatrix"]` | la commande lancée au démarrage du conteneur, ou les arguments par défaut d'`ENTRYPOINT` |
| `WORKDIR /cmatrix` | le répertoire de travail des instructions suivantes, créé s'il n'existe pas |
| `FROM alpine AS cmatrixbuilder` | ouvre une étape de construction et lui donne un nom |
| `COPY --from=cmatrixbuilder /cmatrix/cmatrix /cmatrix` | copie un fichier **depuis une autre étape** |
| `USER thomas` | l'utilisateur sous lequel tourne le conteneur |
| `ENTRYPOINT ["./cmatrix"]` | l'exécutable lancé au démarrage, auquel s'ajoutent les arguments |

Et au terminal : `docker build -t kikinovak/cmatrix .` pour construire, `docker run --rm -it kikinovak/cmatrix` pour lancer.

## 1. Du shell au Dockerfile : RUN et CMD

L'atelier précédent s'est terminé sur l'historique du shell collé tel quel dans le `Dockerfile`. On supprime les numéros de ligne, puis on **commente** toutes les étapes où l'on a avancé à tâtons — les essais ratés, les `ls`, les `echo $?`, le `history` :

```text
# git clone https://github.com/abishekvashok/cmatrix
apk update
apk add git
git clone https://github.com/abishekvashok/cmatrix
cd cmatrix/
# ls -l
# autoreconf -i
apk add autoconf
…
```

Reste à en faire des instructions :

- chaque étape utile devient une instruction **`RUN`**, qui exécute la commande pendant la construction et **ajoute une couche** à l'image ;
- la dernière, `./cmatrix`, devient une instruction **`CMD`**, qui dit quoi lancer au démarrage du conteneur — sous forme de tableau JSON.

```dockerfile
RUN apk update
RUN apk add git
RUN git clone https://github.com/abishekvashok/cmatrix
RUN cd cmatrix/
…
RUN make
CMD ["./cmatrix"]
```

Premier essai de construction :

```text
$ docker build -t kikinovak/cmatrix .
…
 => ERROR [ 8/14] RUN autoreconf -i        1.2s
```

L'échec est voulu : la démarche est itérative, et chaque erreur se corrige à son tour.

## 2. L'instruction WORKDIR

Pourquoi `autoreconf -i` échoue-t-il ? À cause de la ligne qui le précède :

```dockerfile
RUN cd cmatrix/
```

Chaque `RUN` s'exécute dans **son propre shell** : le changement de répertoire ne survit pas à l'instruction, et le `RUN` suivant repart de la racine, où il n'y a pas de code source.

L'instruction **`WORKDIR`** règle le problème : elle fixe le répertoire de travail de toutes les instructions `RUN`, `COPY`, `ADD`, `CMD` et `ENTRYPOINT` qui suivent, et **crée** ce répertoire s'il n'existe pas. On clone alors le code source **dans le répertoire courant**, grâce au point final :

```dockerfile
WORKDIR /cmatrix

RUN apk update
RUN apk add git
RUN git clone https://github.com/abishekvashok/cmatrix .
…
```

Cette fois, la construction va au bout, et l'image fonctionne :

```text
$ docker images
REPOSITORY          TAG       IMAGE ID       CREATED          SIZE
kikinovak/cmatrix   latest    316c1d277496   34 seconds ago   327MB
alpine              latest    706db57fb206   7 days ago       8.32MB
$ docker run --rm -it kikinovak/cmatrix
```

Elle fonctionne, mais pèse **327 Mo** pour un simple binaire, et compte bien trop de couches.

## 3. Moins de couches

Chaque `RUN` ajoute une couche. On commence par retirer toutes les lignes commentées, puis on regroupe.

**Les installations d'abord.** `apk add` est appelée cinq fois de suite ; une seule fois suffit, avec tous les paquets :

```dockerfile
RUN apk update
RUN apk add git autoconf automake alpine-sdk ncurses-dev ncurses-static
RUN git clone https://github.com/abishekvashok/cmatrix .
…
```

On passe à une dizaine de couches.

**Puis toutes les commandes.** L'opérateur `&&` enchaîne deux commandes, la seconde ne s'exécutant que si la première a réussi ; la barre oblique inversée `\` en fin de ligne poursuit l'instruction sur la ligne suivante, pour la lisibilité. Les deux `LABEL` fusionnent de la même façon :

```dockerfile
FROM alpine

LABEL org.opencontainers.image.authors="Nicolas Kovacs" \
      org.opencontainers.image.description="Container image for CMatrix"

WORKDIR /cmatrix

RUN apk update && \
    apk add git autoconf automake alpine-sdk ncurses-dev ncurses-static && \
    git clone https://github.com/abishekvashok/cmatrix . && \
    autoreconf -i && \
    mkdir -pv /usr/lib/kbd/consolefonts && \
    mkdir -pv /usr/share/consolefonts && \
    ./configure LDFLAGS="-static" && \
    make

CMD ["./cmatrix"]
```

Plus que trois couches, et le conteneur tourne toujours. Mais l'image reste **énorme** : elle contient tous les outils de compilation.

## 4. Le multi-stage build

Comment ne garder que le binaire, sans les outils qui ont servi à le compiler ? Avec un **multi-stage build** : un `Dockerfile` en plusieurs étapes, chacune ouverte par un `FROM`.

```dockerfile
# Build Container Image
FROM alpine AS cmatrixbuilder

WORKDIR /cmatrix

RUN apk update --no-cache && \
    apk add git autoconf automake alpine-sdk ncurses-dev ncurses-static && \
    …
    make

# CMatrix Container Image
FROM alpine

LABEL org.opencontainers.image.authors="Nicolas Kovacs" \
      org.opencontainers.image.description="Container image for CMatrix"

RUN apk update --no-cache && apk add ncurses-terminfo-base

COPY --from=cmatrixbuilder /cmatrix/cmatrix /cmatrix

CMD ["./cmatrix"]
```

- La première étape, **nommée** `cmatrixbuilder` par `AS`, compile le binaire, avec tous ses outils.
- La seconde repart d'une Alpine vierge et n'y **copie que le binaire**, avec `COPY --from=cmatrixbuilder`. C'est elle qui devient l'image ; la première est jetée.

Sans la ligne `RUN … ncurses-terminfo-base`, l'image ne pèse que 9,13 Mo, mais le conteneur refuse de démarrer :

```text
$ docker run --rm -it kikinovak/cmatrix
ncurses: cannot initialize terminal type ($TERM="xterm"); exiting
```

Il lui manque une **dépendance d'exécution**, le paquet `ncurses-terminfo-base`, repéré pendant la compilation. Une fois ajouté, l'image pèse **11,8 Mo** — contre 327 Mo — et fonctionne. L'option `--no-cache` de `apk update` évite de garder les index des paquets dans l'image.

::exemple{id="ms-ex-multistage" titre="Ce que chaque étape garde" pour="Savoir quoi mettre dans quelle étape d'un multi-stage build"}
| | Étape `cmatrixbuilder` | Étape finale |
|---|---|---|
| Base | `alpine` | `alpine` |
| Paquets | git, autoconf, automake, alpine-sdk, ncurses-dev, ncurses-static | ncurses-terminfo-base |
| Contenu | le code source et le binaire compilé | le seul binaire `/cmatrix` |
| Devient l'image ? | non, jetée après la construction | **oui** |

La règle : ce qui sert à **construire** reste dans la première étape ; ce qui sert à **exécuter** va dans la dernière.
::

## 5. Un utilisateur non privilégié

Le conteneur tourne pour l'instant en tant que `root` :

```text
$ docker run --rm -it kikinovak/cmatrix whoami
root
```

On ajoute un utilisateur « commun des mortels », dans la même instruction `RUN` que l'installation de la dépendance, puis on bascule dessus avec **`USER`** :

```dockerfile
RUN apk update --no-cache && \
    apk add ncurses-terminfo-base && \
    adduser -g "Thomas Anderson" -s /usr/sbin/nologin -D -H thomas

COPY --from=cmatrixbuilder /cmatrix/cmatrix /cmatrix

USER thomas

CMD ["./cmatrix"]
```

Les options d'`adduser` sous Alpine :

- `-g` : le nom complet de l'utilisateur ;
- `-s` : son shell — ici `/usr/sbin/nologin`, aucun ;
- `-D` : pas de mot de passe ;
- `-H` : pas de répertoire personnel.

```text
$ docker run --rm -it kikinovak/cmatrix whoami
thomas
```

## 6. ENTRYPOINT et CMD : les options de CMatrix

CMatrix accepte toute une série d'options :

```text
/ $ ./cmatrix --help
 Usage: cmatrix -[abBcfhlsmVxk] [-u delay] [-C color] [-t tty] [-M message]
 -a: Asynchronous scroll
 -b: Bold characters on
 -k: Characters change while scrolling. (Works without -o opt.)
 -r: rainbow mode
 -u delay (0 - 10, default 4): Screen update delay
 -C [color]: Use this color for matrix (default green)
 …
```

Avec `CMD ["./cmatrix"]`, tout argument passé à `docker run` **remplace** `./cmatrix` au lieu de s'y ajouter. On sépare donc les rôles :

```dockerfile
ENTRYPOINT ["./cmatrix"]
CMD ["-b"]
```

- **`ENTRYPOINT`** fixe l'exécutable, lancé à chaque démarrage ;
- **`CMD`** ne fournit plus que les **arguments par défaut** — ici `-b`, les caractères gras.

Les arguments donnés à `docker run` remplacent ceux de `CMD` et sont passés à `./cmatrix` :

```text
$ docker run --rm -it kikinovak/cmatrix                     # ./cmatrix -b
$ docker run --rm -it kikinovak/cmatrix -a                  # ./cmatrix -a
$ docker run --rm -it kikinovak/cmatrix -ab -u 2 -C magenta # ./cmatrix -ab -u 2 -C magenta
```

::extrait-cours{id="ms-run-cmd" titre="Du shell au Dockerfile : RUN et CMD" source="/cours/a1/virtualisation-conteneurisation/cmatrix-multi-stage/atelier#_1-du-shell-au-dockerfile-run-et-cmd"}
- On garde de l'historique les étapes utiles, on commente les essais ratés.
- Chaque étape devient `RUN commande` : exécutée **pendant la construction**, elle ajoute une **couche**.
- La commande lancée **au démarrage** devient `CMD ["./cmatrix"]`, en tableau JSON (guillemets doubles).
- `docker build -t kikinovak/cmatrix .` construit l'image depuis le `Dockerfile` du répertoire courant.

::extrait-cours{id="ms-workdir" titre="L'instruction WORKDIR" source="/cours/a1/virtualisation-conteneurisation/cmatrix-multi-stage/atelier#_2-linstruction-workdir"}
Chaque `RUN` a son propre shell : `RUN cd cmatrix/` ne vaut pas pour les instructions suivantes.

```dockerfile
WORKDIR /cmatrix
RUN git clone https://github.com/abishekvashok/cmatrix .
```

`WORKDIR` fixe le répertoire de travail des `RUN`, `COPY`, `ADD`, `CMD` et `ENTRYPOINT` suivants, et le crée au besoin. Le point final de `git clone` clone dans le répertoire courant.
::

::extrait-cours{id="ms-couches" titre="Moins de couches" source="/cours/a1/virtualisation-conteneurisation/cmatrix-multi-stage/atelier#_3-moins-de-couches"}
- Un seul `apk add` pour tous les paquets.
- `&&` enchaîne les commandes dans un seul `RUN` — la suivante seulement si la précédente a réussi.
- `\` en fin de ligne poursuit l'instruction sur la ligne suivante.
- `LABEL cle1="…" cle2="…"` : plusieurs métadonnées dans une seule instruction.

Moins d'instructions `RUN`, moins de couches — mais les outils de compilation restent dans l'image.
::

::extrait-cours{id="ms-multistage" titre="Le multi-stage build" source="/cours/a1/virtualisation-conteneurisation/cmatrix-multi-stage/atelier#_4-le-multi-stage-build"}
```dockerfile
FROM alpine AS cmatrixbuilder
# … compilation …

FROM alpine
RUN apk update --no-cache && apk add ncurses-terminfo-base
COPY --from=cmatrixbuilder /cmatrix/cmatrix /cmatrix
CMD ["./cmatrix"]
```

- Chaque `FROM` ouvre une étape ; `AS` la nomme.
- La **dernière** étape devient l'image ; `COPY --from=<étape>` y apporte le seul binaire.
- Ne pas oublier les **dépendances d'exécution** (`ncurses-terminfo-base`). `--no-cache` évite de garder les index d'`apk`.
- 327 Mo → 11,8 Mo.
::

::extrait-cours{id="ms-utilisateur" titre="Un utilisateur non privilégié" source="/cours/a1/virtualisation-conteneurisation/cmatrix-multi-stage/atelier#_5-un-utilisateur-non-privilégié"}
```dockerfile
RUN apk update --no-cache && \
    apk add ncurses-terminfo-base && \
    adduser -g "Thomas Anderson" -s /usr/sbin/nologin -D -H thomas
USER thomas
```

`adduser` : `-g` nom complet, `-s` shell, `-D` sans mot de passe, `-H` sans répertoire personnel. `USER` fait tourner le conteneur sous cet utilisateur : `docker run --rm -it kikinovak/cmatrix whoami` répond `thomas`.
::

::extrait-cours{id="ms-entrypoint" titre="ENTRYPOINT et CMD" source="/cours/a1/virtualisation-conteneurisation/cmatrix-multi-stage/atelier#_6-entrypoint-et-cmd-les-options-de-cmatrix"}
```dockerfile
ENTRYPOINT ["./cmatrix"]
CMD ["-b"]
```

- `ENTRYPOINT` : l'exécutable, toujours lancé.
- `CMD` : ses arguments **par défaut**.
- `docker run --rm -it kikinovak/cmatrix -ab -u 2` : les arguments placés **après l'image** remplacent ceux de `CMD` et vont à `./cmatrix`.
