## 1. Pourquoi des volumes

Les images sont construites pour que leurs conteneurs soient **compacts, portables et jetables**. Elles ne contiennent que les paquets indispensables au service, et les petits fichiers de configuration qui changent rarement.

On doit donc pouvoir se débarrasser d'un conteneur **sans perdre de données importantes**. Les données d'un conteneur ne doivent pas vivre uniquement dans le conteneur : pour les rendre **persistantes** — ou les sauvegarder —, on utilise un **volume**. C'est aussi le meilleur moyen de **partager** des données entre plusieurs conteneurs.

Il y a deux façons de monter un volume au lancement d'un conteneur. L'option `-v`, déjà vue à l'atelier « Exposer un conteneur », et sa forme longue `--volume` :

```text
$ docker run --name autre_nginx -d -p 8080:80 \
  -v ~/pagesweb:/usr/share/nginx/html:ro nginx
```

Et l'option **`--mount`**, que Docker recommande désormais. Les deux fonctionnent ; c'est `--mount` que l'atelier détaille.

## 2. Créer, lister, inspecter et supprimer un volume

La sous-commande `docker volume` gère les volumes :

```text
$ docker volume --help
Commands:
  create      Create a volume
  inspect     Display detailed information on one or more volumes
  ls          List volumes
  prune       Remove all unused local volumes
  rm          Remove one or more volumes
```

```text
$ docker volume create testdata
testdata
$ docker volume ls
DRIVER    VOLUME NAME
local     testdata
$ docker volume rm testdata
testdata
```

Si `docker volume ls` affiche une liste de volumes aux noms à coucher dehors, `docker volume prune` fait le ménage : il supprime tous les volumes locaux **qui ne sont pas utilisés**.

`docker volume inspect` révèle l'**emplacement réel** du volume sur l'hôte :

```text
$ docker volume inspect mesdata1
[
  {
    "CreatedAt": "2023-07-07T07:20:35+02:00",
    "Driver": "local",
    "Mountpoint": "/var/lib/docker/volumes/mesdata1/_data",
    "Name": "mesdata1",
    "Scope": "local"
  }
]
```

Les données du volume `mesdata1` sont rangées dans `/var/lib/docker/volumes/mesdata1/_data` sur l'hôte.

## 3. Attacher un volume avec --mount

Au lancement, l'option `--mount` attache un volume au conteneur, qui accède alors à ses données :

```text
$ docker run -d --name avecvolume --mount \
  source=mesdata1,destination=/root/volume nginx
```

- `source=` : le volume ;
- `destination=` : le répertoire **dans le conteneur** où il apparaît.

Les formes brèves `src=` et `dst=` font la même chose, et `target=` remplace aussi `destination=` :

```text
$ docker run -d --name avecvolume --mount src=mesdata1,dst=/root/volume nginx
```

**Pas d'espace** dans les arguments de `--mount`.

On vérifie le montage dans la section `Mounts` de `docker inspect`, que `grep -A 10` extrait avec les dix lignes qui la suivent :

```text
$ docker inspect avecvolume | grep -A 10 Mounts
  "Mounts": [
    {
      "Type": "volume",
      "Name": "mesdata1",
      "Source": "/var/lib/docker/volumes/mesdata1/_data",
      "Destination": "/root/volume",
      "Driver": "local",
      "Mode": "z",
      "RW": true,
      "Propagation": ""
    }
```

`Source` est le chemin sur l'hôte, `Destination` le chemin dans le conteneur, et `"RW": true` dit qu'on y lit et écrit.

Le volume vit **indépendamment** du conteneur : arrêter le conteneur le laisse intact, et il faut le supprimer à part, avec `docker volume rm`.

Un fichier ajouté depuis l'hôte apparaît dans le conteneur :

```text
$ echo 'Coucou depuis le volume mesdata1 !' |
> sudo tee /var/lib/docker/volumes/mesdata1/_data/index.html
$ docker exec -it avecvolume bash
root@480fadc6bbb2:/# cat /root/volume/index.html
Coucou depuis le volume mesdata1 !
```

Et le **même volume** peut se monter dans **plusieurs conteneurs** :

```text
$ docker run -d --name avecvolume2 --mount \
  src=mesdata1,dst=/root/volume nginx
$ docker exec -it avecvolume2 bash
root@046c17291d10:/# cat /root/volume/index.html
Coucou depuis le volume mesdata1 !
```

## 4. Un volume en lecture seule

Pour que le conteneur **ne puisse pas modifier** le contenu d'un volume, on ajoute `ro` (*read only*) aux paires de `--mount` :

```text
$ docker run -d --name conteneurenlecture --mount \
  src=nouveauvolume,dst=/usr/share/nginx/html,ro nginx
```

Si le volume n'existe pas au lancement, **Docker le crée** :

```text
$ docker volume ls
DRIVER    VOLUME NAME
local     mesdata1
local     nouveauvolume
```

Dans la section `Mounts` du conteneur, la ligne `"RW": false` confirme la lecture seule, et une écriture échoue :

```text
$ docker exec -it conteneurenlecture bash
root@8b5210c998c4:/# touch /usr/share/nginx/html/test
touch: cannot touch '/usr/share/nginx/html/test': Read-only file system
```

C'est une bonne pratique de sécurité quand l'écriture n'est pas nécessaire : si le conteneur est compromis, les données du volume restent intactes. Le droit d'écrire se règle **conteneur par conteneur**, pas au niveau du volume : un même volume peut être en lecture et écriture pour l'un, en lecture seule pour l'autre.

## 5. Les volumes éphémères tmpfs

Pour des données censées disparaître après usage, on utilise un volume **éphémère**, de type `tmpfs` :

```text
$ docker run -dit --name ephemere --mount \
  type=tmpfs,dst=/root/volume nginx
```

La section `Mounts` affiche alors `"Type": "tmpfs"`, sans `Source` : rien n'est écrit sur le disque de l'hôte.

On peut lui fixer une **taille**, pour garder la main sur l'espace utilisé :

```text
$ docker run -dit --name ephemere2 --mount \
  type=tmpfs,tmpfs-size=256M,dst=/root/volume nginx
$ docker exec -it ephemere2 df -h
Filesystem      Size  Used Avail Use% Mounted on
overlay         1.8T  457G  1.3T  27% /
…
tmpfs           256M     0  256M   0% /root/volume
```

Le conteneur ne pourra pas mettre plus de 256 Mo dans `/root/volume`. Un volume éphémère est une bonne pratique quand un conteneur a besoin d'un espace temporaire qu'on veut voir nettoyé à son arrêt.

## 6. L'approche classique : -v

`--mount` est la méthode recommandée, mais `-v` reste valide et revient souvent dans la documentation :

```text
$ docker run -dit -p 8080:80 --name nginx-avec-vol \
  -v ~/pagesweb:/usr/share/nginx/html:ro nginx
```

La syntaxe : le répertoire **de l'hôte**, deux-points, le répertoire **du conteneur**, et au besoin deux-points et des options (`ro`). Dans la section `Mounts` :

```text
      "Type": "bind",
      "Source": "/home/kikinovak/pagesweb",
      "Destination": "/usr/share/nginx/html",
      "Mode": "ro",
      "RW": false,
```

Le type **`bind`** correspond à l'ancienne méthode d'accès aux répertoires de l'hôte ; elle offre moins de fonctionnalités que `--mount`.

## 7. Un brin de ménage

`docker stop` et `docker rm` acceptent plusieurs conteneurs, `docker volume rm` plusieurs volumes :

```text
$ docker stop nginx-avec-vol ephemere ephemere2 \
  conteneurenlecture avecvolume avecvolume2
$ docker rm nginx-avec-vol ephemere ephemere2 \
  conteneurenlecture avecvolume avecvolume2
$ docker volume ls
DRIVER    VOLUME NAME
local     mesdata1
local     nouveauvolume
$ docker volume rm mesdata1 nouveauvolume
```

Supprimer les conteneurs n'a pas supprimé les volumes : il faut le faire à part.

::extrait-cours{id="vo-pourquoi" titre="Pourquoi des volumes" source="/cours/a1/virtualisation-conteneurisation/volumes/atelier#_1-pourquoi-des-volumes"}
Les conteneurs sont **compacts, portables et jetables** : leurs données importantes ne doivent pas vivre seulement en eux. Un **volume** les rend persistantes — elles survivent au conteneur — et permet de les partager entre conteneurs.

Deux syntaxes au lancement : `-v` (ou `--volume`), et `--mount`, recommandée.
::

::extrait-cours{id="vo-gerer" titre="docker volume" source="/cours/a1/virtualisation-conteneurisation/volumes/atelier#_2-créer-lister-inspecter-et-supprimer-un-volume"}
```bash
docker volume create mesdata1
docker volume ls
docker volume inspect mesdata1    # Mountpoint : /var/lib/docker/volumes/mesdata1/_data
docker volume rm mesdata1
docker volume prune               # les volumes locaux inutilisés
```
::

::extrait-cours{id="vo-mount" titre="Monter un volume avec --mount" source="/cours/a1/virtualisation-conteneurisation/volumes/atelier#_3-attacher-un-volume-avec-mount"}
```bash
docker run -d --name avecvolume --mount source=mesdata1,destination=/root/volume nginx
docker run -d --name avecvolume --mount src=mesdata1,dst=/root/volume nginx
docker inspect avecvolume | grep -A 10 Mounts
```

- `source`/`src` : le volume ; `destination`/`dst`/`target` : le répertoire dans le conteneur. Pas d'espace.
- Le volume survit au conteneur : on le supprime à part.
- Un même volume se monte dans plusieurs conteneurs.
- Ses données sont dans le `Mountpoint` sur l'hôte (`sudo` pour y écrire).
::

::extrait-cours{id="vo-lecture" titre="Un volume en lecture seule" source="/cours/a1/virtualisation-conteneurisation/volumes/atelier#_4-un-volume-en-lecture-seule"}
```bash
docker run -d --name conteneurenlecture --mount src=nouveauvolume,dst=/usr/share/nginx/html,ro nginx
```

- `ro` : lecture seule — `"RW": false` dans `Mounts`.
- Un volume absent est créé par Docker au lancement.
- La lecture seule se décide **par conteneur**, pas pour le volume.
::

::extrait-cours{id="vo-tmpfs" titre="Les volumes éphémères tmpfs" source="/cours/a1/virtualisation-conteneurisation/volumes/atelier#_5-les-volumes-éphémères-tmpfs"}
```bash
docker run -dit --name ephemere --mount type=tmpfs,dst=/root/volume nginx
docker run -dit --name ephemere2 --mount type=tmpfs,tmpfs-size=256M,dst=/root/volume nginx
docker exec -it ephemere2 df -h
```

Un `tmpfs` n'a pas de source et disparaît avec le conteneur ; `tmpfs-size` en limite la taille.
::

::extrait-cours{id="vo-classique" titre="L'option -v" source="/cours/a1/virtualisation-conteneurisation/volumes/atelier#_6-lapproche-classique-v"}
```bash
docker run -dit -p 8080:80 --name nginx-avec-vol -v ~/pagesweb:/usr/share/nginx/html:ro nginx
```

`-v hôte:conteneur[:options]` monte un répertoire de l'hôte — type `bind` dans `Mounts`. Toujours valide, moins riche que `--mount`.
::
