::rappel{titre="Les commandes de l'atelier" icone="i-lucide-file-cog"}
| Commande | Ce qu'elle fait |
|---|---|
| `yamllint compose.yaml` | vérifie la syntaxe du fichier |
| `docker compose up -d` | crée le réseau, les volumes et les conteneurs décrits dans `compose.yaml`, et les démarre en arrière-plan |
| `docker compose down` | arrête et supprime les conteneurs et le réseau — **pas** les volumes |
| `docker compose down --volumes` | supprime aussi les volumes |

| Clé de `compose.yaml` | Équivaut à |
|---|---|
| `services:` | la liste des conteneurs, un par service |
| `image: mariadb:latest` | l'image de `docker run` |
| `volumes:` (dans un service) | `-v volume:/chemin` |
| `environment:` | les `-e CLE=valeur` |
| `ports:` | les `-p 8080:80` |
| `restart: always` | `--restart always` |
| `volumes:` (au premier niveau) | les volumes nommés à créer |

Indentation : **deux espaces** par niveau, jamais de tabulation.

## 1. De docker run à compose.yaml

Combiner des conteneurs avec `docker run` simplifie déjà l'installation d'une application comme WordPress, mais il existe un outil bien plus confortable : `docker compose`. Il lit le fichier **`compose.yaml` du répertoire courant** et configure les conteneurs qu'il décrit. Tout l'apprentissage se résume à la syntaxe de ce fichier.

Autrefois, `docker-compose` — avec un trait d'union — était une commande distincte de `docker`. Les versions actuelles ont intégré `compose` comme une sous-commande officielle : on écrit **`docker compose`**.

L'extension `.yaml` désigne le format **YAML** (*YAML Ain't Markup Language*). Deux règles à ne jamais oublier :

- **deux espaces** pour chaque niveau d'indentation ;
- **aucune tabulation**.

Pour éviter les erreurs bizarres, on vérifie la syntaxe avec un validateur, comme `yamllint`. On commence par un répertoire de travail :

```text
$ mkdir -v wordpress-compose
mkdir: création du répertoire 'wordpress-compose'
$ cd wordpress-compose/
$ vim compose.yaml
$ yamllint compose.yaml
```

## 2. Décrire un service

Voici le blog de l'atelier précédent — MariaDB, PHPMyAdmin, WordPress —, adapté en `compose.yaml` :

```yaml
---  # compose.yaml
services:
  # MariaDB
  mariadb:
    image: mariadb:latest
    volumes:
      - blog-db-volume:/var/lib/mysql
    environment:
      MYSQL_RANDOM_ROOT_PASSWORD: 1
      MYSQL_DATABASE: wp
      MYSQL_USER: wpuser
      MYSQL_PASSWORD: motdepasse
    restart: always
  # PHPMyAdmin
  phpmyadmin:
    image: phpmyadmin:latest
    environment:
      PMA_HOST: mariadb
    ports:
      - "8080:80"
    restart: always
  # WordPress
  wordpress:
    image: wordpress:latest
    volumes:
      - blog-wp-volume:/var/www/html/wp-content
    ports:
      - "80:80"
    environment:
      WORDPRESS_DB_HOST: mariadb
      WORDPRESS_DB_USER: wpuser
      WORDPRESS_DB_NAME: wp
      WORDPRESS_DB_PASSWORD: motdepasse
    restart: always
volumes:
  blog-db-volume:
  blog-wp-volume:
...
```

- Le fichier commence par l'élément **`services`**, suivi de la liste indentée des services — ici `mariadb`, `phpmyadmin` et `wordpress`.
- Les propriétés de chaque service sont indentées d'un niveau de plus et définies par des mots-clés : `image` pour l'image Docker, `volumes`, `environment`, `ports`…
- Ce que `docker run` disait en options se lit ici en clés : `volumes` remplace `-v`, `environment` les `-e` (une ligne `CLE: valeur` par variable), `ports` les `-p`.
- **`restart: always`** relance les conteneurs, même après un redémarrage de l'hôte.
- Après `services`, d'autres sections de premier niveau peuvent suivre, comme **`volumes`** ou `networks`. Ici, `volumes` déclare les deux volumes nommés utilisés par les services.
- Plus de `--network` ni de `-h` : Compose crée lui-même un réseau commun, sur lequel chaque service se joint **par son nom** — d'où `PMA_HOST: mariadb`.

La référence complète est la documentation officielle : `https://docs.docker.com/compose/compose-file`.

::exemple{id="cp-ex-traduire" titre="Traduire un docker run en service" pour="Passer d'une commande de l'atelier précédent à son bloc de compose.yaml"}
La commande de PHPMyAdmin :

```text
docker run -d --name phpmyadmin -h phpmyadmin --network blog-wordpress \
  -p 8080:80 -e PMA_HOST=mariadb phpmyadmin
```

devient, option par option :

```yaml
phpmyadmin:              # --name : le nom du service
  image: phpmyadmin:latest   # l'image, en dernier dans docker run
  environment:
    PMA_HOST: mariadb    # -e PMA_HOST=mariadb
  ports:
    - "8080:80"          # -p 8080:80
  restart: always        # en plus : relancer toujours
```

`-d`, `--network` et `-h` disparaissent : c'est `docker compose up -d` qui détache, et Compose qui fournit le réseau.
::

## 3. Démarrer la configuration

Dans le répertoire du fichier, une commande démarre tout :

```text
$ docker compose up -d
[+] Running 6/6
 ✔ Network wordpress-compose_default          Created    0.2s
 ✔ Volume "wordpress-compose_blog-db-volume"  Created    0.0s
 ✔ Volume "wordpress-compose_blog-wp-volume"  Created    0.0s
 ✔ Container wordpress-compose-mariadb-1      Started    0.0s
 ✔ Container wordpress-compose-phpmyadmin-1   Started    0.0s
 ✔ Container wordpress-compose-wordpress-1    Started    0.0s
```

En moins d'une seconde, la configuration est prête : PHPMyAdmin à `http://localhost:8080`, WordPress à `http://localhost`. `-d` détache les conteneurs, comme pour `docker run`.

Le **nom du répertoire de travail** sert à nommer tout ce que Compose crée :

- `docker ps` montre trois conteneurs : `wordpress-compose-mariadb-1`, `wordpress-compose-phpmyadmin-1`, `wordpress-compose-wordpress-1` ;
- `docker network ls`, un nouveau réseau : `wordpress-compose_default` ;
- `docker volume ls`, deux nouveaux volumes : `wordpress-compose_blog-db-volume` et `wordpress-compose_blog-wp-volume`.

## 4. Arrêter et faire le ménage

Une commande arrête et **supprime** les conteneurs et le réseau de la configuration :

```text
$ docker compose down
[+] Running 4/4
 ✔ Container wordpress-compose-wordpress-1   Removed    1.3s
 ✔ Container wordpress-compose-mariadb-1     Removed    0.4s
 ✔ Container wordpress-compose-phpmyadmin-1  Removed    1.3s
 ✔ Network wordpress-compose_default         Removed    0.2s
```

Les **volumes**, eux, n'ont pas été supprimés — les données survivent :

```text
$ docker volume ls
DRIVER    VOLUME NAME
local     wordpress-compose_blog-db-volume
local     wordpress-compose_blog-wp-volume
```

Pour s'en débarrasser, on les supprime à la main avec `docker volume rm`… ou l'on fait tout d'un coup à l'arrêt : **`docker compose down --volumes`** supprime conteneurs, réseau et volumes.

`docker compose` lit le fichier **`compose.yaml` du répertoire courant** et configure les conteneurs décrits.

- `docker compose` (sous-commande de `docker`) a remplacé l'ancienne commande `docker-compose`.
- YAML : **deux espaces** par niveau d'indentation, **aucune tabulation**.
- `yamllint compose.yaml` vérifie la syntaxe.

```bash
mkdir -v wordpress-compose
cd wordpress-compose/
yamllint compose.yaml
```

::extrait-cours{id="cp-services" titre="Décrire un service" source="/cours/a1/virtualisation-conteneurisation/compose/atelier#_2-décrire-un-service"}
```yaml
services:
  phpmyadmin:
    image: phpmyadmin:latest     # l'image
    environment:                 # les -e
      PMA_HOST: mariadb
    ports:                       # les -p
      - "8080:80"
    volumes:                     # les -v
      - un-volume:/chemin
    restart: always              # relancer toujours
volumes:                         # premier niveau : les volumes nommés
  un-volume:
```

Pas de `--network` ni de `-h` : Compose fournit un réseau commun, où chaque service se joint par son nom.

Le nom du répertoire préfixe tout : conteneurs `repertoire-service-1`, réseau `repertoire_default`, volumes `repertoire_volume`. `docker ps`, `docker network ls` et `docker volume ls` les montrent.
