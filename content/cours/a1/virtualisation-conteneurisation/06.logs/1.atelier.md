::rappel{titre="Les commandes de l'atelier" icone="i-lucide-terminal"}
| Commande | Ce qu'elle fait |
|---|---|
| `docker logs <conteneur>` | affiche la sortie standard et la sortie d'erreur d'un conteneur |
| `docker logs -f <conteneur>` | suit les logs **en direct** (*follow*), comme `tail -f` |
| `docker logs -t <conteneur>` | ajoute l'**horodatage** (*timestamps*) de chaque ligne |
| `grep -i docker /var/log/messages` | les journaux du moteur Docker sous Red Hat et ses clones (`/var/log/syslog` sous Debian et Ubuntu) |
| `journalctl -u docker.service -n 25` | les 25 dernières entrées du service Docker, via `journald` |
::

## 1. Les logs d'un conteneur

Tôt ou tard, on lit les **journaux** d'un conteneur pour comprendre ce qui se passe — surtout quand plusieurs conteneurs travaillent ensemble. Ce qu'un conteneur écrit sur sa **sortie standard** et sa **sortie d'erreur standard** se lit avec `docker logs`.

L'atelier prend pour cobaye l'application **Jenkins** — un outil d'intégration continue, dont le rôle importe peu ici : seuls ses logs nous intéressent.

```text
$ docker run -dit --name pleindelogs -p 8080:8080 -p 50000:50000 \
  jenkins/jenkins:lts
58a30d0285916966e22b3b02e6f39d80dd5119cfb0add02ba...
```

Dans le nom `jenkins/jenkins:lts`, le premier `jenkins`, avant la barre oblique, est l'**identifiant Docker** de l'éditeur ; `lts` est le tag.

Au premier lancement, Jenkins fabrique un mot de passe d'administration. Il ne l'affiche nulle part ailleurs que dans sa sortie — donc dans ses logs :

```text
$ docker logs pleindelogs
...
*************************************************************************
Jenkins initial setup is required. An admin user has been created and a
password generated. Please use the following password to proceed to
installation:

ea952fa0f8534898b52dd03c16b0794e

This may also be found at: /var/jenkins_home/secrets/initialAdminPassword
*************************************************************************
```

Il arrive qu'une application écrive aussi ses journaux dans des fichiers, sous `/var/log`, à l'intérieur du conteneur. Mais les conteneurs préfèrent le plus souvent **rediriger** leurs journaux vers la sortie standard et la sortie d'erreur — justement pour que `docker logs` les montre.

::exemple{id="lg-ex-mot-de-passe" titre="Retrouver un mot de passe dans les logs" pour="Une application lancée en arrière-plan qui affiche une information au démarrage"}
Le conteneur Jenkins tourne en arrière-plan (`-d`) : rien ne s'affiche au lancement, sinon son ID. Le mot de passe a bien été écrit — sur la sortie standard du conteneur, que personne ne regardait. `docker logs pleindelogs` relit tout ce que le conteneur a écrit depuis son démarrage : on y repère le mot de passe, on le copie, et l'on ouvre `http://localhost:8080` dans un navigateur.
::

## 2. Suivre et horodater les logs

Deux options de `docker logs` reviennent sans cesse :

- `-f` (*follow*) **suit** les logs : la commande ne rend pas la main et affiche chaque nouvelle ligne au moment où elle est écrite — le même principe que `tail -f` sous Linux. **Ctrl + C** arrête le suivi, pas le conteneur ;
- `-t` (*timestamps*) ajoute devant chaque ligne l'**horodatage** auquel elle a été écrite — précieux pour un débogage.

```text
$ docker logs -f pleindelogs
$ docker logs -t pleindelogs
2023-06-29T06:52:24.949346103Z Running from: /usr/share/jenkins/jenkins.war
```

Les deux se combinent : `docker logs -tf pleindelogs`.

::exemple{id="lg-ex-suivre" titre="Suivre l'installation de Jenkins" pour="Voir ce que fait une application pendant qu'on agit sur elle"}
Dans le navigateur, on choisit **Sélectionner les plugins à installer**, on garde la configuration par défaut et on clique sur **Installer**. Pendant ce temps, dans le terminal :

```text
$ docker logs -f pleindelogs
```

Chaque plugin installé fait apparaître ses lignes, en direct. Une fois l'installation finie, **Ctrl + C** rend la main — Jenkins, lui, continue de tourner.
::

## 3. Les logs du moteur Docker

À côté des logs de chaque conteneur, le **moteur Docker** tient ses propres journaux. Comme la plupart des services, il les confie au système `syslog` de l'hôte :

- sous **Red Hat Enterprise Linux** et ses clones (AlmaLinux, Rocky Linux), ainsi que sous OpenSUSE, dans `/var/log/messages` ;
- sous **Debian** et **Ubuntu**, dans `/var/log/syslog`.

```text
# grep -i docker /var/log/messages
```

L'option `-i` de `grep` ignore la casse : elle trouve `docker`, `Docker` et `DOCKER`.

Sur un système qui utilise `systemd`, on interroge aussi son outil de journalisation, `journald`, avec `journalctl`. Les 25 dernières entrées du service Docker :

```text
# journalctl -u docker.service -n 25
```

- `-u docker.service` restreint aux entrées de l'**unité** Docker ;
- `-n 25` n'en garde que les 25 dernières.

Pour obtenir la sortie d'un bloc, sans visualiseur qui attend qu'on la fasse défiler, on ajoute `--no-pager` :

```text
# journalctl --no-pager -u docker.service -n 25
```

L'invite `#` dit que ces commandes se lancent en **root** : les journaux du système ne sont pas lisibles par tout le monde.


:::exo-question{label="1." cours="lg-logs"}

::commande

  - docker run -dit --name apache_logs -p 8080:80 httpd:latest

#indice
`-p` publie un port : celui de l'hôte d'abord, celui du conteneur ensuite. Apache écoute sur le port 80 dans son conteneur.


::extrait-cours{id="lg-moteur" titre="Les logs du moteur Docker" source="/cours/a1/virtualisation-conteneurisation/logs/atelier#_3-les-logs-du-moteur-docker"}
Le moteur Docker écrit dans le `syslog` de l'hôte : `/var/log/messages` (Red Hat, AlmaLinux, Rocky, OpenSUSE), `/var/log/syslog` (Debian, Ubuntu).

```bash
grep -i docker /var/log/messages
journalctl -u docker.service -n 25
journalctl --no-pager -u docker.service -n 25
```

`-u` : l'unité ; `-n` : le nombre d'entrées ; `--no-pager` : sans visualiseur.
