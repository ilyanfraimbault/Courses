::rappel{titre="Les commandes de l'atelier" icone="i-lucide-terminal"}
| Commande | Ce qu'elle fait |
|---|---|
| `docker run -it --name apache httpd /bin/bash` | lance un conteneur et ouvre aussitôt son shell Bash |
| `exit` ou **Ctrl + D** | quitte le shell du conteneur |
| `docker exec -it shelltest /bin/bash` | ouvre un shell dans un conteneur **qui tourne déjà** |
| `docker exec -it shelltest sh` | même chose avec le shell rudimentaire `sh` |
| `docker exec -d execution touch /root/coucou.txt` | exécute une commande dans le conteneur, en arrière-plan |
| `docker exec -it execution ls /root` | exécute une commande et affiche son résultat |
| `docker top execution` | liste les processus du conteneur, même sans `ps` à l'intérieur |

Sans `-it`, un shell lancé par `docker run` ou `docker exec` s'exécute et s'arrête aussitôt.
::

## 1. Se connecter au lancement

On ne se connecte pas à un conteneur en SSH, comme à une machine virtuelle. Et plutôt que de modifier un conteneur qui tourne, on préfère adapter son `Dockerfile` et **reconstruire** l'image. Mais il est parfois utile d'entrer dans un conteneur pour voir ce qui s'y passe, de façon interactive, plutôt que de lire ses logs.

Première façon : se connecter **au moment du lancement**, en donnant à `docker run` la commande à exécuter — un shell :

```text
$ docker run -it --name apache httpd /bin/bash
root@d724f090a8cf:/usr/local/apache2#
```

- `-it` est **requis** pour un shell interactif ;
- pas de `-d` : le conteneur s'exécute au premier plan ;
- `/bin/bash`, placé **après** l'image, est la commande que le conteneur exécute.

L'invite change : l'utilisateur `root`, le nom d'hôte du conteneur `d724f090a8cf`, puis le répertoire courant `/usr/local/apache2`. On y tape n'importe quelle commande du shell (`pwd`, `ls`…), et on en sort par `exit` ou **Ctrl + D**.

Mais après `exit`, `docker ps` ne montre plus le conteneur : il a exécuté la commande qu'on lui a donnée, `/bin/bash`, et s'est arrêté dès qu'on a quitté Bash. Avec `-d` en plus, il se détache aussitôt :

```text
$ docker run -dit --name autre_apache httpd /bin/bash
96e278c968a813c01194424236e588cb5e9284fd6d85b1d837cf04ae3e67e5d2
```

Le conteneur tourne, mais on n'y est **pas** connecté : l'argument `/bin/bash` n'a guère de sens ici.

Deux remarques sur les shells :

- beaucoup de conteneurs sont bâtis sur **Alpine Linux**, qui n'a pas de Bash complet : il faut alors demander `/bin/sh`. Dans tous les cas, ne pas s'attendre à toutes ses commandes habituelles, ni à la complétion ou à l'historique ;
- au lieu du chemin complet `/bin/bash`, on peut écrire `bash` ou `sh`, tant que la commande est dans le `PATH` du conteneur — ce qui est généralement le cas.

## 2. Se connecter à un conteneur qui tourne

Pour accéder au shell d'un conteneur **déjà en cours d'exécution** — détaché, donc — on utilise `docker exec` :

```text
$ docker run -dit --name shelltest httpd
373a25810b747e6f8198cedd40974cad11d007aea68dd5f889fedbda869e0d9a
$ docker exec -it shelltest /bin/bash
root@373a25810b74:/usr/local/apache2# exit
```

Le chemin complet n'est pas nécessaire, et le shell rudimentaire `sh` marche aussi :

```text
$ docker exec -it shelltest bash
root@373a25810b74:/usr/local/apache2# exit
$ docker exec -it shelltest sh
# exit
```

L'erreur fréquente : **oublier `-it`**. Le shell s'exécute alors et s'arrête aussitôt.

Contrairement au cas précédent, quitter ce shell n'arrête **pas** le conteneur : son processus principal, le serveur Apache, tourne toujours. `exec` a lancé un processus **de plus**, et c'est lui qu'on termine.

## 3. Exécuter des commandes

`docker exec` ne sert pas qu'à ouvrir un shell : il exécute **n'importe quelle commande** disponible dans le conteneur. Avec `-d`, la commande tourne en arrière-plan ; ici, elle crée un fichier vide :

```text
$ docker run -dit --name execution httpd
c7bf797bd79176fbc6c4dd99b0a0b27bd6aa3175442df0e8819e7e16cdab07e2
$ docker exec -d execution touch /root/coucou.txt
$ docker exec -it execution ls /root
coucou.txt
```

Un conteneur n'est pas une distribution complète : beaucoup de commandes habituelles y **manquent** — `uptime`, `man`, `locate`, `vim`, `vi`, `nano`…

```text
root@c7bf797bd791:/usr/local/apache2# vim
bash: vim: command not found
```

L'image `httpd` étant basée sur Debian, on peut installer ce qui manque avec `apt` :

```text
root@c7bf797bd791:/usr/local/apache2# apt update
root@c7bf797bd791:/usr/local/apache2# apt install vim
```

Mais la modification est **éphémère** : elle change le conteneur en cours d'exécution, **pas l'image**. Un nouveau conteneur lancé depuis `httpd` n'aura pas Vim ; pour cela, il faut reconstruire l'image.

::::exercice{titre="Au terminal — exécuter des commandes" theme="docker exec -d, docker exec -it commande"}

:::exo-question{label="1." cours="cn-commandes"}

::commande

---

#indice
`docker exec`, l'option qui détache, le conteneur, puis la commande Linux qui crée un fichier vide.

#solution
```bash

```

Tout ce qui suit le nom du conteneur est la commande exécutée à l'intérieur.

## 4. Les processus d'un conteneur

La commande `ps` manque elle aussi dans certains conteneurs :

```text
root@c7bf797bd791:/usr/local/apache2# ps
bash: ps: command not found
```

On demande alors à Docker, depuis l'hôte, avec `docker top` :

```text
$ docker top execution
UID   PID  PPID  C  STIME  TTY    TIME      CMD
root  2414 2396  0  09:52  pts/0  00:00:00  httpd -DFOREGROUND
bin   2440 2414  0  09:52  pts/0  00:00:00  httpd -DFOREGROUND
bin   2441 2414  0  09:52  pts/0  00:00:00  httpd -DFOREGROUND
bin   2442 2414  0  09:52  pts/0  00:00:00  httpd -DFOREGROUND
```

Quatre processus `httpd` tournent dans le conteneur `execution`.
