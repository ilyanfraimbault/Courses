## 1. Une architecture en couches

Docker range une image en **couches** (*layers*). Chaque couche ne garde que la **différence** avec la couche du dessous — un peu comme la commande `diff` sous Linux, ou un commit sous Git, qui n'enregistre que ce qui a changé.

- Les couches d'une image sont en **lecture seule**.
- Si toutes tes images partent d'Alpine, chacune n'occupe sur le disque que ce que tu as **ajouté** à l'image Alpine de base.
- Reconstruire une image après une petite modification est **rapide** : seules les couches touchées sont refaites.

## 2. Télécharger une image

`docker pull` télécharge l'image dont on donne le nom, sans lancer de conteneur. Sans tag, Docker prend `latest` :

```text
$ docker pull nginx
Using default tag: latest
latest: Pulling from library/nginx
d107e437f729: Pull complete
cb497a329a81: Pull complete
f1c4d397f477: Pull complete
…
Status: Downloaded newer image for nginx:latest
docker.io/library/nginx:latest
```

Chaque ligne `Pull complete` est **une couche** téléchargée. On vérifie la présence de l'image avec `docker images` (ou `docker image ls`).

`docker history` montre la suite d'instructions qui a construit l'image, une couche par ligne, la plus récente en haut :

```text
$ docker history nginx
IMAGE          CREATED       CREATED BY
41f689c20910   6 weeks ago   CMD ["nginx" "-g" "daemon off;"]
…              6 weeks ago   STOPSIGNAL SIGQUIT
…              6 weeks ago   EXPOSE map[80/tcp:{}]
…              6 weeks ago   ENTRYPOINT ["/docker-entrypoint.sh"]
…              6 weeks ago   ENV NGINX_VERSION=1.29.2
…
```

## 3. Les tags

Un **tag** transmet une information sur l'image — le plus souvent sa **version**. Sans tag, c'est `latest`. La commande `docker tag` en crée un nouveau :

```text
$ docker tag --help
Usage: docker tag SOURCE_IMAGE[:TAG] TARGET_IMAGE[:TAG]
```

Pour héberger un blog, on donne à Nginx le tag `monblog_prod` :

```text
$ docker tag nginx:latest nginx:monblog_prod
$ docker image ls
REPOSITORY    TAG            IMAGE ID       CREATED      SIZE
nginx         latest         07ccdb783875   4 days ago   160MB
nginx         monblog_prod   07ccdb783875   4 days ago   160MB
```

Les deux lignes ont le **même `IMAGE ID`** : Docker n'a pas recopié l'image, il a créé un **alias**. Aucun mégaoctet de plus sur le disque.

## 4. Lire un Dockerfile

Sur la page de l'image officielle de Nginx, sur Docker Hub, la section *Supported tags and respective `Dockerfile` links* mène au `Dockerfile` qui a construit l'image. En voici une version simplifiée :

```dockerfile
FROM debian:trixie-slim
LABEL maintainer="NGINX Docker Maintainers <docker-maint@nginx.com>"

ENV NGINX_VERSION=1.29.2
ENV NJS_VERSION=0.9.3
ENV PKG_RELEASE=1~trixie

RUN apt-get update \
&& apt-get install -y nginx \
&& apt-get clean

RUN ln -sf /dev/stdout /var/log/nginx/access.log \
&& ln -sf /dev/stderr /var/log/nginx/error.log

COPY index.html /var/www/html/
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

| Instruction | Rôle |
|---|---|
| `FROM` | l'**image de base** : la construction ajoute des couches par-dessus |
| `LABEL` | des métadonnées — l'endroit idéal pour ses coordonnées |
| `ENV` | des variables d'environnement, comme celles du shell Bash |
| `RUN` | exécute une commande pendant la construction ; les gestionnaires de paquets y tournent en mode **non interactif** (`-y`) |
| `COPY` | copie un fichier de l'hôte dans l'image — souvent un petit fichier de configuration |
| `EXPOSE` | ouvre (expose) un port au lancement d'un conteneur — ici 80, le port standard du HTTP |
| `CMD` | la commande lancée dans le conteneur, en **tableau JSON** |

Deux détails de ce fichier :

- les `&&` enchaînent plusieurs commandes dans **un seul** `RUN` : tout le travail du gestionnaire de paquets tient en une couche, au lieu d'une couche par commande. `apt-get clean` supprime ensuite les paquets téléchargés, pour une image plus légère ;
- `daemon off;` fait tourner Nginx **au premier plan** du conteneur. Sans lui, Nginx passerait en arrière-plan, le processus principal se terminerait, et le conteneur s'arrêterait net.

Pour reconstruire l'image, on range le `Dockerfile` dans un répertoire `~/Test`, avec la page `index.html` qu'il copie, puis on lance la construction :

```text
$ echo "<h1>Mon serveur Nginx</h1>" > ~/Test/index.html
$ cd ~/Test
$ ls
Dockerfile index.html
$ docker build -t mon_nginx .
```

- `-t` donne un **nom** (et éventuellement un tag) à l'image ;
- le point `.` dit à Docker d'utiliser le `Dockerfile` du **répertoire courant** — ne pas l'oublier.

On lance ensuite un conteneur à partir de cette image, et l'on regarde ses couches avec `docker history mon_nginx`.

::exemple{id="im-ex-dockerfile" titre="Associer une instruction à son rôle" pour="Lire n'importe quel Dockerfile sur Docker Hub"}
Dans le `Dockerfile` de Nginx :

- `FROM debian:trixie-slim` : on part d'une Debian minimale ;
- `RUN apt-get update && apt-get install -y nginx && apt-get clean` : on installe Nginx, en **une** couche ;
- `EXPOSE 80` : le conteneur ouvrira le port 80 ;
- `CMD ["nginx", "-g", "daemon off;"]` : au lancement, on démarre Nginx au premier plan.

Ce qui est construit une fois pour toutes (`RUN`, `COPY`) se distingue de ce qui se passe **à chaque lancement** d'un conteneur (`CMD`).
::

## 5. Supprimer les images

`docker rmi` supprime une image. Sur un tag qui n'est qu'un alias, Docker ne retire que le **tag** :

```text
$ docker rmi nginx:monblog_prod
Untagged: nginx:monblog_prod
```

Sur le dernier nom d'une image, il supprime **les couches** et libère de la place :

```text
$ docker rmi nginx:latest
Untagged: nginx:latest
Deleted: sha256:eb4a57159180767450cb8426e6367f11b999653d8f185b5e3b78a9ca30c2
Deleted: sha256:387c6708d068d261ce5b1fe3e67323cbf64d8a37901f3d9742557f4abb83
…
```

Si l'on supprime par mégarde l'image originale, l'image retaguée reste en place : Docker gère ce cas. Il arrive qu'une suppression doive être **forcée**, avec `-f` — option qu'on découvre dans l'aide en ligne, `docker rmi --help` :

```text
$ docker rmi -f debian:latest
```

## 6. Faire le ménage sur le disque

Les couches qui ne servent plus à aucune image munie d'un tag sont des **images en suspens** (*dangling images*). La sous-commande `prune` (« élaguer ») les supprime :

```text
$ docker image prune
WARNING! This will remove all dangling images.
Are you sure you want to continue? [y/N] y
```

Pour supprimer **aussi** les images inutilisées — celles qui n'ont aucun conteneur — ainsi que les conteneurs arrêtés, les réseaux inutilisés et le cache de construction :

```text
$ docker system prune -a
WARNING! This will remove:
- all stopped containers
- all networks not used by at least one container
- all images without at least one container associated to them
- all build cache
```

Et pour savoir combien de place Docker occupe :

```text
$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          6         1         495MB     495MB (100%)
Containers      1         1         2B        0B (0%)
Local Volumes   0         0         0B        0B
Build Cache     0         0         0B        0B
```

::extrait-cours{id="im-couches" titre="Une architecture en couches" source="/cours/a1/virtualisation-conteneurisation/images/atelier#_1-une-architecture-en-couches"}
Une image est un empilement de **couches** en **lecture seule** ; chacune ne garde que la différence avec celle du dessous, comme un commit Git.

- Des images bâties sur la même base ne paient que ce qu'elles ajoutent.
- Reconstruire après une petite modification est rapide : seules les couches touchées sont refaites.
::

::extrait-cours{id="im-pull" titre="Télécharger une image et lire son historique" source="/cours/a1/virtualisation-conteneurisation/images/atelier#_2-télécharger-une-image"}
```bash
docker pull nginx          # télécharge nginx:latest
docker images              # ou docker image ls
docker history nginx       # les instructions, couche par couche
```

Chaque `Pull complete` est une couche. `docker history` liste les instructions de construction, la plus récente en haut.
::

::extrait-cours{id="im-tags" titre="Les tags" source="/cours/a1/virtualisation-conteneurisation/images/atelier#_3-les-tags"}
Un tag dit, le plus souvent, la **version** d'une image ; sans tag, c'est `latest`. On l'accroche par un deux-points : `httpd:2-alpine`.

```bash
docker tag nginx:latest nginx:monblog_prod   # source, puis cible
```

Le nouveau tag est un **alias** : même `IMAGE ID`, aucun espace disque en plus.
::

::extrait-cours{id="im-dockerfile" titre="Lire un Dockerfile et construire une image" source="/cours/a1/virtualisation-conteneurisation/images/atelier#_4-lire-un-dockerfile"}
`FROM` (image de base), `LABEL` (métadonnées), `ENV` (variables), `RUN` (commande de construction — enchaîner avec `&&` pour une seule couche), `COPY` (fichier de l'hôte vers l'image), `EXPOSE 80` (port ouvert), `CMD ["nginx", "-g", "daemon off;"]` (commande au lancement, en tableau JSON).

```bash
docker build -t mon_nginx .   # -t : le nom ; . : le Dockerfile du répertoire courant
```

::extrait-cours{id="im-rmi" titre="Supprimer les images" source="/cours/a1/virtualisation-conteneurisation/images/atelier#_5-supprimer-les-images"}
```bash
docker rmi nginx:monblog_prod   # un alias : seul le tag part (Untagged)
docker rmi nginx:latest         # le dernier nom : les couches partent (Deleted)
docker rmi -f debian:latest     # forcer
docker rmi --help               # les options
```

Sans tag, `docker rmi httpd` vise `httpd:latest`.
::

::extrait-cours{id="im-menage" titre="Faire le ménage sur le disque" source="/cours/a1/virtualisation-conteneurisation/images/atelier#_6-faire-le-ménage-sur-le-disque"}
```bash
docker image prune        # les images en suspens (dangling)
docker system prune -a    # + images inutilisées, conteneurs arrêtés, réseaux, cache
docker system df          # l'espace occupé par Docker
```
