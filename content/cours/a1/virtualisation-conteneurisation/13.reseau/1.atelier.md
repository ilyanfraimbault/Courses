Sur un réseau personnalisé, un conteneur en joint un autre **par son nom** : Docker y fait office de serveur DNS. Ce n'est pas le cas sur le réseau `bridge` par défaut.

## 1. Docker et le pare-feu

Docker confie le filtrage et le routage au pare-feu du noyau Linux, **Netfilter**, qu'on manipule couramment avec `iptables` (progressivement remplacé par `nftables`). Publions un port pour voir ce qu'il y écrit :

```text
$ docker run -dit -p 8080:80 php:apache
71c2e5a3ab89984a1eca0fdf9496650b9fc9b45c1e498170356f4ff35c1c28a3
$ docker ps
... PORTS
... 0.0.0.0:8080->80/tcp
$ sudo iptables -nL "DOCKER"
Chain DOCKER (1 references)
target     prot opt source       destination
ACCEPT     tcp  --  0.0.0.0/0    172.17.0.2       tcp dpt:80
```

L'image `php:apache` contient le serveur web Apache avec le module `mod_php` : un bon point de départ pour une application écrite en PHP. Dans la chaîne `DOCKER`, `tcp dpt:80` dit que le **port de destination** est le port TCP 80, et `172.17.0.2` est l'adresse que Docker a donnée au conteneur — une adresse **locale**, non routable sur Internet.

Le serveur répond aussi bien à cette adresse qu'au port publié sur l'hôte :

```text
$ curl http://172.17.0.2
<title>403 Forbidden</title>
...
<address>Apache/2.4.57 (Debian) Server at 172.17.0.2 Port 80</address>
$ curl http://127.0.0.1:8080
<title>403 Forbidden</title>
...
<address>Apache/2.4.57 (Debian) Server at 127.0.0.1 Port 8080</address>
```

Le routage interne de Docker fait passer le trafic de façon transparente du port 8080 de l'hôte au port 80 du conteneur. (Le `403 Forbidden` est normal : Apache n'a encore aucune page à servir.)

## 2. Le réseau de l'hôte

On peut désactiver la mise en réseau de Docker : avec `--network host`, le conteneur **partage la pile réseau de l'hôte**. Il n'a pas d'adresse IP à lui, et Docker n'écrit aucune règle de routage :

```text
$ docker run -dit --network host php:apache
e68ad367f3e986af0c754c1c9445135a1558bf7c54578edfb17f50199ffb5e59
$ sudo iptables -nL "DOCKER"
Chain DOCKER (1 references)
target     prot opt source       destination
$ curl http://127.0.0.1
<address>Apache/2.4.57 (Debian) Server at 127.0.0.1 Port 80</address>
```

Apache écoute directement sur le port 80 de l'hôte, sans `-p`. C'est une manière de faire **peu commune** et **pas du tout sécurisée** : conteneur et hôte ne sont plus isolés. Il faut seulement savoir qu'elle existe.

## 3. Le réseau bridge par défaut

`docker network ls` liste les réseaux de Docker :

```text
$ docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
8c5e2a8c9201   bridge    bridge    local
a12b2a39c25b   host      host      local
40756a45b4dd   none      null      local
```

- `bridge` est le réseau **par défaut** : un conteneur lancé sans préciser de réseau y est branché. Un *bridge* (pont) relie deux réseaux ; deux conteneurs branchés sur `bridge` peuvent se parler.
- `host` et `none` relient les piles réseau du conteneur et de l'hôte ; on peut en faire abstraction.

`docker network inspect bridge` détaille le réseau, et sa section `Containers` liste les conteneurs branchés, avec leur adresse MAC et leur adresse IP :

```text
$ docker run -dit --name webserver1 php:apache
$ docker run -dit --name webserver2 php:apache
$ docker network inspect bridge
...
  "Containers": {
      "09d1724677fd99f8bdf984336b4a88d638e58...": {
      "Name": "webserver1",
      "MacAddress": "02:42:ac:11:00:02",
      "IPv4Address": "172.17.0.2/16",
    }
      "99a76a5bb45422031f274b194b6d966545f0a8...": {
      "Name": "webserver2",
      "MacAddress": "02:42:ac:11:00:03",
      "IPv4Address": "172.17.0.3/16",
    }
  },
```

Pour vérifier que les deux conteneurs se parlent, on ouvre un shell dans `webserver1` et on contacte `webserver2`. L'image n'a pas la commande `ip` : on l'installe (paquet `iproute2`) — ou on se contente de `hostname -I`.

```text
$ docker exec -it webserver1 bash
root@09d1724677fd:/var/www/html# apt update
root@09d1724677fd:/var/www/html# apt install -y iproute2
root@09d1724677fd:/var/www/html# ip addr
    inet 172.17.0.2/16 brd 172.17.255.255 scope global eth0
root@09d1724677fd:/var/www/html# curl http://172.17.0.3
<address>Apache/2.4.57 (Debian) Server at 172.17.0.3 Port 80</address>
root@09d1724677fd:/var/www/html# exit
$ docker logs webserver2
172.17.0.2 - - [08/Jul/2023:05:35:45 +0000] "GET / HTTP/1.1" 403 436 "-" "curl/7.88.1"
```

Le journal de `webserver2` montre la requête, venue de `172.17.0.2` : celle de `webserver1`.

## 4. Un réseau isolé pour une application

Un blog demande deux conteneurs : un **serveur web** et un **serveur de bases de données**. Le serveur web doit joindre la base, mais aucun autre conteneur, ni aucune machine extérieure, ne doit pouvoir y accéder. On crée donc un **réseau personnalisé** pour ces deux-là :

```text
$ docker network create blog
52288618e976b3566f2e84b208944def99267537f470bd7c437d551f4edb36b4
$ docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
3cc5986cb45e   blog      bridge    local
97bab690e648   bridge    bridge    local
...
```

Le réseau `blog` est lui aussi de type `bridge`. On y branche le serveur web avec `--network`, après avoir créé un volume pour ses pages :

```text
$ docker volume create blog_web_data
$ docker run -dit --name web --network blog -p 80:80 \
  --mount src=blog_web_data,dst=/var/www/html php:apache
$ docker network inspect blog
...
      "Name": "web",
      "IPv4Address": "172.18.0.2/16",
```

Le conteneur `web` a une adresse dans un autre sous-réseau, `172.18.0.0/16`. Depuis `webserver1`, resté sur le réseau `bridge`, il est injoignable :

```text
$ docker exec -it webserver1 bash
root@8f891d85f3fb:/var/www/html# curl -m 5 http://172.18.0.2
curl: (28) Connection timed out after 5001 milliseconds
```

L'option `-m 5` limite l'attente de `curl` à cinq secondes. Les conteneurs d'un réseau ne parlent pas à ceux d'un autre : `web` est isolé.

## 5. Une base de données sur le réseau

Le second conteneur du blog est un serveur **MariaDB**, fork libre de MySQL. Son `Dockerfile` contient `VOLUME /var/lib/mysql` : les données vivent dans un volume. Docker en créerait un tout seul ; on préfère en créer un au nom parlant :

```text
$ docker volume create blog_db_data
```

La documentation de l'image, section *Environment Variables*, demande au moins une **variable d'environnement** au lancement. On les passe avec l'option `-e` :

- `MYSQL_ROOT_PASSWORD` fixe le mot de passe de `root` ;
- `MYSQL_DATABASE` crée une base de ce nom au premier lancement.

```text
$ docker run -dit --name database --network blog \
  -e MYSQL_ROOT_PASSWORD=password123 -e MYSQL_DATABASE=wordpress \
  --mount src=blog_db_data,dst=/var/lib/mysql mariadb
```

**Pas de `-p`** : le port MySQL 3306 n'a pas à être public. Seul le serveur web doit y accéder, et il est sur le même réseau. `docker network inspect blog` montre maintenant `web` en `172.18.0.2` et `database` en `172.18.0.3`.

Les données de la base sont dans le volume, sur l'hôte :

```text
$ docker volume inspect blog_db_data | grep Mountpoint
"Mountpoint": "/var/lib/docker/volumes/blog_db_data/_data",
$ sudo ls -1F /var/lib/docker/volumes/blog_db_data/_data
...
mysql/
wordpress/
```

Si le conteneur `database` disparaissait, les données resteraient dans le volume, et un nouveau conteneur monté au même endroit les retrouverait. Et si le volume contient déjà une base, `MYSQL_ROOT_PASSWORD` et `MYSQL_DATABASE` n'ont **aucun effet** : la base existante est gardée telle quelle.

Pour tester la connexion depuis le serveur web, on y installe un client MySQL et on se connecte à l'adresse de `database` :

```text
$ docker exec -it web bash
root@3bc4c3eb1bc8:/var/www/html# apt update
root@3bc4c3eb1bc8:/var/www/html# apt install -y default-mysql-client
root@3bc4c3eb1bc8:/var/www/html# mysql -h 172.18.0.3 -p
Enter password: ***********
MariaDB [(none)]> show databases;
...
| wordpress          |
```

## 6. Le DNS des réseaux personnalisés

Sur un réseau personnalisé, Docker fournit un **serveur DNS embarqué** : un conteneur en joint un autre **par son nom**. Plus besoin de chercher l'adresse de `database` :

```text
$ docker exec -it web bash
root@c7efa289fa0c:/var/www/html# mysql -h database -p
Enter password: ********
Welcome to the MariaDB monitor.
```

C'est la meilleure façon de faire : Docker peut donner une **autre adresse** à un conteneur qui redémarre, alors que son nom, lui, ne change pas.

Deux limites :

- le DNS ne marche **pas** sur le réseau `bridge` par défaut — seulement sur les réseaux personnalisés ;
- il ne traverse pas les réseaux : on ne résout pas le nom d'un conteneur branché sur un autre réseau.

## 7. Installer WordPress

WordPress est écrit en PHP, d'où l'image `php:apache`. Pour joindre la base, il lui faut l'extension PHP **`mysqli`**. Pour qu'Apache charge l'extension, on **arrête et redémarre** le conteneur, puis on vérifie que ses processus tournent avec `docker top` :

```text

UID   PID    PPID   C  STIME  TTY    TIME      CMD
root  56247  56225  0  08:29  pts/0  00:00:00  apache2 -DFOREGROUND
33    56288  56247  0  08:29  pts/0  00:00:00  apache2 -DFOREGROUND
...
```

# wget -c https://wordpress.org/wordpress-latest.tar.gz

::extrait-cours{id="rs-pare-feu" titre="Docker et le pare-feu" source="/cours/a1/virtualisation-conteneurisation/reseau/atelier#_1-docker-et-le-pare-feu"}
Docker règle le pare-feu Netfilter du noyau (`iptables`) pour publier les ports.

```bash
docker run -dit -p 8080:80 php:apache
sudo iptables -nL "DOCKER"       # ACCEPT … 172.17.0.2  tcp dpt:80
curl http://172.17.0.2           # l'adresse du conteneur, port 80
curl http://127.0.0.1:8080       # l'hôte, port publié
```

Le conteneur reçoit une adresse locale, non routable sur Internet ; Docker relaie le port de l'hôte vers celui du conteneur.
::

```bash
docker run -dit --network host php:apache
```

Le conteneur partage la pile réseau de l'hôte : **pas d'adresse IP à lui**, pas de `-p`, aucune règle dans la chaîne `DOCKER`. Peu commun et **pas sécurisé** : hôte et conteneur ne sont plus isolés.
